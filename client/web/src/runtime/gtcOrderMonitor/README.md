# GTC 订单监控

[changmen 扩展] 本模块与 `runtime/rayOrderMonitor/` 并列，由 App 分别挂载各自的登录生命周期。负责 PM GTC 原单恢复、HTTP 成交核对、WS 订阅、撤单及监控停止；自动和手动 GTC 共用同一实例。

- `lifecycle.ts` 随登录用户启动，登出、切换用户、管理端预览及页面卸载时停止。FOK/GTC 模式切换、自动下注开关和订单侧栏筛选不决定监控是否运行。
- `runtime.ts` 管理 GTC 自身的生命周期；重复启动不增加定时器。停止只释放 GTC 订阅、恢复任务及执行状态，不启停 RAY 监控、不清空 RAY 查询快照。
- `pm.ts` / `pmPolling.ts` 是 PM GTC 的唯一后台查询与撤单实现。同账号原单共用成交历史，在途原单查询不重叠；慢请求或恢复失败不阻断其它已知原单。零成交、部分成交和费用待核实按原规则持续核对，完成核对后释放订阅。
- `recovery.ts` / `recoveryPolicy.ts` 从客户端 IndexedDB 恢复执行，从 RDS 按账号和原单号读取确认结果。两个分区独立失败、退避，已知原单的官方核对不等待历史导入。
- `counterpart.ts` 消费关联对侧的事实。RAY 只消费现有查询快照，不写 RAY 监控状态；其 HTTP 查询、账号调度、展示状态和订单监控生命周期仍由 `rayOrderMonitor` 独占。其它场馆保留已有对侧核对方式。
- RAY 已有最终财务记录的本地核对失败后，按恢复退避规则重试（5 秒起，最多 5 分钟），不增加场馆查询；成功或停止 GTC 后清除重试状态。PM 查询每次异步返回后重新核对当前会话及账号凭证，失效请求不继续更新或计次。
- `coordinator.ts` 只按原规则关闭恢复后的首次发送窗口，不签单、不发送场馆订单、不重放另一腿，也不设置新的重试、补单或卖出规则。

[changmen 扩展] 2026-10-27：GTC 已退出新自动套利；本模块继续兼容已有双腿执行及手动 GTC。新 GTC 下单仅由显式手动入口使用 PM 单笔能力。`orderModes/gtc/executionState.ts` 保留执行命令、事实和会话校验，`localStore.ts` 在 IndexedDB 同一事务中提交执行更新和已确认结果队列。发送许可必须先提交成功，再调用原场馆发送；刷新和同源多标签页共用已消费许可，恢复只查询原单，不重发。

`stores/account/gtcOrderSync.ts` 独立消费结果队列，只有 CONFIRMED 且费用已核实的成交及明确 FAILED 修正进入 RDS `orders`。挂单、授权、撤单命令、查询错误和对侧执行状态留在客户端；取消余量不删除已确认的部分成交。同步失败保留本地队列并退避重试，旧请求完成不能清掉新累计成交。普通同步仍处理对侧订单、PM 赛果和卖出，既有金额、手续费与卖出现金合并规则不变。监控不保存订单，不刷新订单侧栏。

[changmen 扩展] `stores/account/gtcCounterpartSync.ts` 在正常拉单同步中消费 IndexedDB 已确认的对侧原单号，按用户、账号、场馆和原单号补齐 Link 与执行归属，保存本轮最新订单。该批原单保存成功后不再重复走普通保存；失败时保留正常订单更新，并随下轮正常同步重试关联。已有占位 Link 通过精确绑单入口修正，不能抢绑其它执行；已识别订单的人工改绑仍由普通合并器保留。刷新从客户端原执行恢复关联，不重发任何下注。

旧 RDS 执行记录通过 `Pm_GtcList` 只读导入一次，保留已消费许可；新执行不调用 `Pm_GtcCreate` / `Pm_GtcCommand`。盘口历史准入在导入完成前保持原来的失败阻断。没有删除历史执行表或历史订单。场馆事实读取和签单仍归 `packages/venue-adapter/polymarket/gtc/`。

客户端恢复范围是同一浏览器、同一站点及登录用户；清除站点数据、换浏览器或换设备不会恢复新客户端执行记录。RDS 订单结果仍可查询，同源多标签页防重不等于跨设备的执行协调。

`orderMonitoring/` 和 `orderModes/gtc/runtime.ts` 的旧监控入口只再导出本模块，兼容旧消费者，不产生第二套查询或定时器。
