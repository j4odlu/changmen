# RAY 订单监控

[changmen 扩展] `runtime.ts` 是唯一 RAY 后台订单监控调度和查询入口，负责原单恢复、待关联订单定位、HTTP 查询、状态保存和终态退出。登录会话启动，登出、切换用户、管理端预览或页面卸载时停止。普通、GTC 和体育 RAY 原单使用相同查询链路；查询不依赖 GTC 状态、下注主循环、套利开关、比赛列表或订单侧栏。

- 每 5 秒按投注账号查询一次 `/v2/order`，同账号多笔原单共用请求；在途请求不重叠。账号处于下注确认窗口时暂缓，窗口结束后继续。
- 每 60 秒通过 `Client_GetPlayerOrder({ rayMonitorOnly: true })` 恢复数据库未结原单，不限制日期；已知单号额外返回终态。恢复失败在下一轮重试，不阻止已知原单查询。
- 已知原单按账号和场馆单号精确匹配；首次确认后的待关联上下文沿用原时间、金额、赔率及文本评分规则，只绑定唯一候选。首次出现的匹配原单保存并绑定 Link 后，进入统一状态查询。失败会重试，不保存或绑定无关订单。
- `Client_SaveOrder({ rayMonitorOnly: true })` 使用数据库受保护的 UPDATE：不新建、不改绑、不修改买入时间、不覆盖持久化 GTC 身份，原单已终态时不回退。
- `win / lose / return / reject` 为终态，保存成功后结束监控。任务按用户保存在 sessionStorage，数据库恢复支持关闭页面后重新登录。
- 首次拒单检测仍按原下注等待和确认流程执行。它结束后只交接上下文；独立监控发现后续拒单时，`autoMakeup.ts` 按原扩展开关、自动补单开关、成功腿锚点、用户取消及队列冲突规则交给现有补单队列，不直接下注。
- 旧旁路查询及主循环 tick 已移除；`contexts.ts`、`contextStore.ts`、`match.ts` 不设置定时器或查询场馆，只消费唯一查询返回值。旧监控时长偏好已弃用，所有原单持续观察至终态。
- `contextStore.ts` 从旧 `changmen:ray-reject-monitor:v1:<user>` 迁移关联和补单依据，移除旧时间限制，保存成功后删除旧缓存键；普通原单缓存也继续兼容恢复。

`lifecycle.ts` 管理自身登录生命周期，`api.ts` 负责后台恢复与状态保存，`state.ts` 为共享展示状态。`orderMonitoring/rayState.ts`、`raySettlement.ts`、`rayLifecycle.ts` 仅兼容旧导入。GTC 消费已有 RAY 查询快照，不额外增加账号查询。

这是客户端模块，持续运行期间需要保持页面会话。后台恢复和受保护保存需要同时部署配套服务端代码。
