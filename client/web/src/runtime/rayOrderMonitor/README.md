# RAY 订单监控

[changmen 扩展] `runtime.ts` 统一负责提交后发现订单、用户端原单恢复、HTTP 查询、本地状态更新、拒单事件和终态退出。后台只有一个按到期时间唤醒的定时器、一个按账号的有效在途请求表；提交后展示与持续监控共用该调度。原业务监控保留 5 秒心跳；显示查询到期时可额外唤醒，但只更新显示，不提前执行业务观察或推迟业务查询间隔。监控不保存订单到 RDS，不调用订单持久化绑单或 `Client_GetOrderList`。登录会话启动，登出、切换用户、管理端预览或页面卸载时停止。普通、GTC 和体育 RAY 原单使用相同业务查询链路。

- [changmen 扩展] 主循环 RAY 提交成功后唤醒统一监控，立即查询 /v2/order，随后每 5 秒核对；同账号的发现订单与持续监控共用请求锁，同一用途不重叠，不等待或阻塞下注回执。正常监控具备原业务依据时，可以接替尚未返回的纯展示请求；旧请求逻辑作废，其回包不再更新监控及订单记录，也不能清理新请求的锁。其他已有后台请求在途时等待下一轮新查询，发出时间早于本次成功回执的旧响应不能用于定位本次订单。`submissionDisplay.ts` 负责提交身份和真实订单的只读展示，不单独设置定时器。
- 提交记录不是订单。提前显示必须有提交前已完成、非空且请求开始距提交不足 30 秒的场馆查单快照，排除快照、现有订单栏及已定位提交中的旧单号后，仅有一个新增 order_number，且场馆 match_id、odds_id、投注金额和赔率精确吻合。30 秒仅用于限制基线陈旧程度，依据当前普通套利的最小间隔；不修改下注间隔或拒单等待配置。此检查仍依赖场馆列表完整及时，不把列表差分等同于服务端返回本次提交的订单身份。
- 无快照、空快照、快照陈旧、原生身份缺失、数值不一致或多个新增单号时不提前挂到 Link，等待正式同步。多候选或同账号有多个尚未定位的提交时停止猜配，不根据候选消失或遍历顺序恢复归属。不会将提交后的查询追认为提交前快照。原 adapter 在非 200 响应时也会返回空数组，因此空快照不能证明“没有旧单”；首次使用或真实空账号也保守等待正式同步。
- 场馆真实订单按账号和 order_number 保存一份只读显示记录，首次定位后始终按同一单号更新；字段、内部查询 ID 和业务状态取自查单结果，H5 Pending / Open 等显示继续沿用原投影，不再强制生成“确认中”。正式列表同账号同单号优先，按账号和 Link 收到正式订单后停止相应展示查询，不能回退终态或产生重复行。
- H5 原生缓存的发布资格在同账号的新查询开始时交接，不等新响应完成才拒绝旧回包。新查询失败时保留最后已接受的快照，不让旧在途响应恢复发布资格；只控制显示缓存，adapter 返回的订单、首次拒单检测及业务状态映射保持原样。
- OrderView 仅投影已确认的真实订单，不插入订单业务 store，不修改账号统计。DisplayOnly 是未持久化记录的操作保护，禁止改绑和卖出，并非另一种订单状态；日期、账号筛选及管理端隔离保留。
- 请求用途在发出时确定：提交成功唤醒或尚无业务监控依据时只读 adapter，仅更新显示，不向拒单检测/GTC 的共享快照发布结果，不调用拒单观察、补单、保存、绑单或侧栏刷新。正式确认后符合原监控条件的请求沿用原后台 reader，可同时更新真实订单显示和原业务监控。展示请求跨过正式确认窗口也不会升级为业务回包。正常监控请求跨越新提交或新业务上下文交接时跳过业务处理，等待新请求。首次拒单检测仍按原等待、独立查单、判断及绑定执行，不共用后台在途请求；不把提前定位的单号写入 BetResult 或改变正式绑定规则。
- 正式拒单结果和补单进度继续由原业务上下文显示；提前查询只更新已定位原单的 UI，不提前结束拒单等待、不触发补单或落库。
- 确认窗口之外，统一监控每 5 秒按投注账号查询 `/v2/order`，同账号多笔原单及待显示订单共用请求；正常监控请求之间不重叠。交接时底层暂不支持取消旧请求，网络上可能短暂存在一旧一新两个请求，仅新请求保留处理资格。账号 active 时只有提交后显示需求可发只读查询，原单的拒单/结算业务观察仍暂缓；窗口结束后按原规则继续。真实订单或正式列表确认终态后停止对应需求，不为已经终态的显示行重复查单。
- 每 60 秒通过 `Client_GetPlayerOrder({ rayMonitorOnly: true })` 恢复数据库未结原单，不限制日期；已知单号额外返回终态。恢复失败在下一轮重试，不阻止已知原单查询。
- 已知原单按账号和场馆单号精确匹配；首次确认后的待关联上下文沿用原时间、金额、赔率及文本评分规则，只接纳唯一候选。`monitorBound` 表示客户端已确认身份，`bindingSaved` 仅表示同步模块或数据库恢复已确认持久化 Link，两者分开。
- `localOrders.ts` 更新客户端已有订单的状态、赔率、投注额和盈亏，并重算当前列表统计。保留账号、Link、买入时间及 GTC/POD 身份；不新建账本行、不回退终态、不发 HTTP 请求。
- 订单落库统一由 `stores/account/venueOrders.ts` 的正常同步负责。成功保存后，`rayOrderBindings.ts` 处理已确认原单的持久化关联及失败重试，不重复保存订单或刷新侧栏。尚未持久化关联的终态上下文保留在 sessionStorage，供正常同步完成关联。
- `win / lose / return / reject` 为终态，客户端观察到终态后结束监控，不等待 RDS 保存。任务按用户保存在 sessionStorage；数据库仅用于恢复已保存的原单。
- 首次拒单检测仍按原下注等待和确认流程执行。它结束后只交接上下文；独立监控发现唯一确认原单的后续拒单时，`autoMakeup.ts` 按原扩展开关、自动补单开关、成功腿锚点、用户取消及队列冲突规则交给现有补单队列，不直接下注。
- 旧旁路查询及主循环 tick 已移除；`contexts.ts`、`contextStore.ts`、`match.ts` 不设置定时器或查询场馆，只消费唯一查询返回值。旧监控时长偏好已弃用，所有原单持续观察至终态。
- `contextStore.ts` 从旧 `changmen:ray-reject-monitor:v1:<user>` 迁移关联和补单依据，移除旧时间限制，保存成功后删除旧缓存键；普通原单缓存也继续兼容恢复。

`lifecycle.ts` 管理自身登录生命周期，`api.ts` 只负责读取恢复数据，`state.ts` 为共享展示状态。`orderMonitoring/rayState.ts`、`raySettlement.ts`、`rayLifecycle.ts` 仅兼容旧导入。GTC 消费已有 RAY 查询快照时不再保存订单或刷新列表；首次下注后的 fresh 确认链路保持原保存及刷新。

这是客户端模块，持续运行期间需要保持页面会话。RDS 的订单状态在正常订单同步时更新，不随五秒监控查询写入。
