## 一条验收链

`release.yml` 仍在一个 validate job 中读取计划，运行原组件检查，再执行所需的完整审计和 PostgreSQL 演练。全部成功、源码稳定后才封包和上传 `verified-release`，现有前后端发布 jobs 继续依赖 validate。

不是读取某个外部工作流的绿色状态，也不嵌套派发同并发组的审计工作流；检查在同一 checkout 中直接执行，避免结果属于另一提交或相互等待。独立数据库工作流与发布入口复用同一个 runner；手动专项审计入口继续保留且不能发布。

`change-plan.mjs` 的 `requiredChecks` 决定追加哪些检查，不增加降低风险或跳过保护的命令行开关：

| 发布情形 | 完整 22 阶段 | 临时 PostgreSQL 五组 |
| --- | --- | --- |
| 已知基线的低风险前端 UI 自动发布 | 不追加 | 不追加 |
| 前端执行/预检等原高风险路径 | 必需 | 涉及数据输入时必需 |
| 后端运行代码 | 原高风险或控制输入变化时必需 | 必需 |
| 共享包、依赖及跨端架构改动 | 必需 | 后端或数据输入涉及时必需 |
| 手动发布或未知基线 | 必需 | 必需 |
| 不涉及应用发布 | 不追加在线发布审计 | 保留原适用检查，独立 DB workflow 按其触发规则执行 |

日常 `check:change` / PR 检查继续离线，551 项保护照常执行。手动单端选择保留原发布组件，但未知风险按保守方式检查，不能通过手动选择逃避完整审计；这种检查会只读访问生产双端来源。低风险自动前端路径继续不要求后端在线。

第一批保留原组件检查，不做重复测试折叠。必要审计增加后 validate 上限改为 60 分钟，不放宽任何失败条件。后续减少重复执行须另行证明完整覆盖，不能直接删除 551 项或原审计阶段。

## 结果与候选绑定

- 原有提交、源码稳定、计划、构建身份和制品哈希校验保留。
- 完整审计和数据库报告增加相同的 `identity`：commit、candidateTree、inputFingerprint。完整审计保留原 22 阶段，并核对阶段名称/顺序/结果，而不只计数；同时绑定实际生产基线、captureId、发布兼容组合与原不可变参考。
- 数据库 runner 依次执行 `schema-compatibility`、`history-schema`、`rds-cli-isolation`、`rds-assets-standalone`、`deploy-account-preservation`。全部使用临时本机数据库，不是对生产 RDS 执行迁移。
- 缺失、失败、超时、源漂移、错误提交/文件树/指纹、重复/缺少阶段、生产基线变化均阻断封包。新检查开始时清除或覆写先前成功结果。
- `release-evidence.mjs` 封存所需 `full-acceptance.json` / `database-acceptance.json` 并记录各自 SHA-256；运输前再检查内容、哈希及候选绑定，先于 SSH 和密钥使用。已封存报告被替换也会拒绝。
- 最终候选仍须提交，再由实际 Actions 对该提交运行验收。本地 dirty 候选的通过报告不能直接用于生产封包。

## 失败定位

`release-summary.mjs` 在 validate 的 always 步骤写入 Actions Job Summary：提交、范围、顺序、必要检查、每项耗时，以及失败阶段、退出码、超时/信号。缺失报告、候选不一致、未完成封包、后续上传/清理失败均不能显示为可据此放行。

原 `failed-acceptance` 附件增加 `output/database-compatibility/`，同时保留完整审计与组件验收报告。摘要只读取结构化状态，不复制原始日志、环境或凭证。成功的必要验收报告随 verified-release 一同封存。
