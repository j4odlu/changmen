# validate 耗时优化

> 本文为 2026-10-19 优化记录。2026-10-25 已合并跨 runner 编排、按模块收窄检查并取消重复类型检查；当前操作规则以 [独立部署](./INDEPENDENT_DEPLOYMENT.md) 为准。

[changmen 扩展] 本批仅调整验收脚本、测试和说明。经典 `legacy` FOK 的业务源码、下注语义及固定 551 项历史基线保持不变。

按用户确认，通用发布已移除固定 551 项及整套 22 阶段 FOK 专项的强制依赖。FOK 是 PM 的下注模式，历史版本取证与整仓专项审计由独立入口按需执行。组件发布范围、后端先行、数据库兼容和产物身份校验保留。

业务边界为 PM 下注：FOK/GTC 是提交给 PM 的订单类型，代码分目录用于组织差异，不代表两个独立业务系统。GTC 的挂单跟踪、部分成交、撤单等生命周期可单独处理；准备、签名和提交等公共能力仍需保留经典 FOK 已确认的行为，不能借合并组织方式增加拒单条件或改变自动准备能力。

## 已落实的执行归属

后续发布链路拆分为 `plan → checks(controls / backend / frontend) → validate → deploy`。三组检查在独立 runner 并行执行，每组内部维持必要顺序（路由编译在后端测试之前，前端测试在构建之前），全部成功后才汇总、封包和部署。后端先行的发布顺序保留。

计划任务只读取一次当前生产版本，并绑定本次 Actions run/attempt、候选 commit/tree/源码指纹及计划指纹。检查任务不接收部署凭据；汇总任务不安装依赖或重建前端，而是核对各组结果及产物 SHA 后沿用已经验证的 dist。缺失、重复、失败、过期、跨提交、跨运行的检查结果及被替换的构建/数据库证明均不能通过汇总。最终封包继续执行既有 commit、源码指纹、运行版本元数据和归档校验。

仅修改 `validation-plan.mjs`、`verify-change.mjs` 及其两个测试文件时，运行已有的 `validation-control` 与部署消费者测试，不再触发与该修改无关的整套 PM 依赖故障注入。其它未知或共享验证实现变更仍回退到验证目录全量回归，独立完整专项及日常检查的原有覆盖不变。

对照记录：9 月 30 日 run 36666427315 完整部署约 3 分 35 秒；10 月 5 日 run 37329145821 前端从触发到完成约 3 分 43 秒，后端并行完成。优化前本次 run 39150736893 共 13 分 49 秒，其中 validate 11 分 21 秒：验证目录回归 212.3 秒、前端 220.2 秒、数据库 73.2 秒、构建 55.2 秒、后端 52.1 秒。该记录用于定位串行累加，后续并行链路的实际收益以新 Actions 记录为准。

并行链路的本机复核：验证目录 95 文件 / 2,555 项、发布控制 103 项、运输与激活失败回滚集成、公共边界与 24 步 catalog-smoke、生产构建均通过；Node 专用保护 9 项及手动 FOK 差分/固定 551 项通过。汇总测试包含前端单端、无需发布、全量发布、缺失/重复/失败/超时/被终止结果、跨提交/运行/计划结果、产物修改及失败任务重跑。同一固定计划的成功结果允许随 GitHub 失败任务重试继续使用；重新生成计划会分配新 UUID，旧结果不能混用。检查与汇总 runner 的 Node 版本由计划任务固定。

- 通用发布仍通过 `verify-change.mjs` 执行验证控制、对应组件的边界/路由/业务测试和构建。改到验证脚本时执行验证脚本自身的回归；常规应用发布不因此运行整套专项。
- `verify-fok-release.mjs` 和手动 Special release audit 工作流保留独立 22 阶段审计。没有新建通用入口来重新包装专项。
- 普通发布不执行 `fok-551` 或 `complete-release`，不读取或复用旧 FOK 报告，也不要求 `full-acceptance.json`。报告中的 FOK 实际检查条数为 0；封包、运输和摘要不再要求 551。
- 日常离线检查及修改 PM 共用链路时的原兼容回归要求保留，固定清单与基线不变。独立专项仍分别核验两个不同历史基线。
- 后端通用发布仍运行包含公共检查的 `test:backend -- --force`；独立专项的 `checks` 与 backend 阶段避免重复同一公共检查。
- 数据库兼容的五组演练、同提交/源码指纹封存和运输前校验保留；常规检查失败、源码改变、旧构建、归档改变或数据库证明缺失仍阻断发布。
- 本机完整验收发现直接调用精确源码校验时未应用既有的 CRLF/LF 归一化；已在同一校验入口补齐，并验证 CRLF 源码能通过、CRLF 中的实际端口篡改仍被拒绝。原固定文件和基线没有替换。
- 外层和完整验收的每个阶段输出开始、通过/失败及耗时，子进程详细日志继续写入原路径。

## PM 审计

每次审计创建独立的只读扫描快照，同次审计的初始依赖图和扩展 loader 依赖图共享文件内容、路径解析及 import 提取结果。每张依赖图的遍历、来源归属、违规判断和未知依赖清单仍独立计算。TypeScript loader 绑定分析继续执行。

快照不跨审计调用保存；故障注入修改源码、添加文件、改变 package exports 或删除入口后，下一次调用重新读取。回归覆盖这些变化及扩展图与独立扫描结果的一致性，原有真实入口故障注入继续运行。

本机同一源码的单次 PM 审计：优化前约 5.50 秒，优化后约 3.28 秒；938 个扫描文件及完整序列化报告一致。文件读取从 3,013 次降至 1,131 次，exists 查询从 124,296 次降至 9,827 次。该数据是本机审计测量，不能直接视为 Actions 整体提速比例。

## 验证范围

### 2026-10-25 验证器自测计算优化

针对 run `40150320443` 中验证目录自测的 423.1 秒，进一步减少重复计算：公共依赖检查与 PM 检查共享同次扫描快照；loader 分析复用当前 TypeScript program 的词法符号、按传播轮次失效的值计算及预收集的传播节点。绑定名称只做排除筛选，候选仍按原有词法作用域解析，保留别名、遮蔽、CJS、动态载入及未知输入拒绝。

精确 token 计算按完整输入文本缓存，每张表最多 512 项、400 万字符，返回数组保持调用方独立。完整迁移校验只在本次调用内复用读取结果；只读历史测试复用基准夹具，每项变异和缺失覆盖仍在夹具之外注入。后续校验重新读取文件，真实 CLI 故障注入继续执行。历史证据 JSON、原始哈希、固定 FOK 清单及测试隔离方式未改变。

本机单次 PM 审计从 3.87 秒降到 2.15 秒，1,077 个文件的完整序列化报告一致；同组 loader 自测从 16.3 秒降到 10.3 秒。新增回归覆盖缓存结果被调用方修改、字符串内部空白、无效语法、长 re-export 链收敛、Unicode/转义名称与默认函数、跨根快照拒绝以及后续源码修改/缺失。整体收益以最终提交的 Actions 实测为准，不用本机局部测量代替 CI 发布凭证。

本机最终完整验证：171 个文件、3,740 项自测全部通过，耗时 286.5 秒；Node 专用 9 项及公共边界检查通过。测试数量增加 7 项，原有用例和真实 CLI 拒绝检查保留。

根目录 `scripts/check-team-boundaries.mjs` 显式归为 CI 工具，修改它仍执行验证目录完整自测，单独修改不选择前后端发布。该规则使用精确路径；混入真实应用修改仍按对应组件检查和发布，未知脚本继续保守处理。另补一项真实计划回归，避免工具优化被误判为全量应用发布。

前端进程模式已对照运行：原 forks 模式约 160.4 秒，threads 模式约 173.6 秒；两轮均为 518 个文件、4,703 项通过及 4 项既有跳过。threads 在本机没有收益，因此不修改现有模式、文件隔离或全局测试桥接。

前端全套、真实验证目录故障注入、发布编排控制、两组 FOK 保护及数据库兼容演练的本机结果记录在忽略目录 `output/validate-*`。正式发布继续由最终提交对应的 Actions 重新验收和封包。
