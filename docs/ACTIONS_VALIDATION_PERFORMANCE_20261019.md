# validate 耗时优化

[changmen 扩展] 本批仅调整验收脚本、测试和说明。经典 `legacy` FOK 的业务源码、下注语义及固定 551 项历史基线保持不变。

按用户确认，通用发布已移除固定 551 项及整套 22 阶段 FOK 专项的强制依赖。FOK 是 PM 的下注模式，历史版本取证与整仓专项审计由独立入口按需执行。组件发布范围、后端先行、数据库兼容和产物身份校验保留。

业务边界为 PM 下注：FOK/GTC 是提交给 PM 的订单类型，代码分目录用于组织差异，不代表两个独立业务系统。GTC 的挂单跟踪、部分成交、撤单等生命周期可单独处理；准备、签名和提交等公共能力仍需保留经典 FOK 已确认的行为，不能借合并组织方式增加拒单条件或改变自动准备能力。

## 已落实的执行归属

- 通用发布仍通过 `verify-change.mjs` 执行验证控制、对应组件的边界/路由/业务测试和构建。改到验证脚本时执行验证脚本自身的回归；常规应用发布不因此运行整套专项。
- `verify-fok-release.mjs` 和手动 Special release audit 工作流保留独立 22 阶段审计。没有新建通用入口来重新包装专项。
- 普通发布不执行 `fok-551` 或 `complete-release`，不读取或复用旧 FOK 报告，也不要求 `full-acceptance.json`。报告中的 FOK 实际检查条数为 0；封包、运输和摘要不再要求 551。
- 日常离线检查及修改 PM 共用链路时的原兼容回归要求保留，固定清单与基线不变。独立专项仍分别核验两个不同历史基线。
- 后端通用发布仍运行包含公共检查的 `test:backend -- --force`；独立专项的 `checks` 与 backend 阶段避免重复同一公共检查。
- 数据库兼容的五组演练、同提交/源码指纹封存和运输前校验保留；常规检查失败、源码改变、旧构建、归档改变或数据库证明缺失仍阻断发布。
- 本机完整验收发现直接调用精确源码校验时未应用既有的 CRLF/LF 归一化；已在同一校验入口补齐，并验证 CRLF 源码能通过、CRLF 中的实际端口篡改仍被拒绝。原固定文件和基线没有替换。
- 外层和完整验收的每个阶段输出开始、通过/失败及耗时，子进程详细日志继续写入原路径。

## PM 审计

每次审计创建独立的只读扫描快照，同次审计的初始依赖图和扩展 loader 依赖图共享文件内容、路径解析及 import 提取结果。每张依赖图的遍历、来源归属、违规判断和未知依赖清单仍独立计算。TypeScript loader 绑定分析继续执行。

快照不跨审计调用保存；故障注入修改源码、添加文件、改变 package exports 或删除入口后，下一次调用重新读取。回归覆盖这些变化及扩展图与独立扫描结果的一致性，原有真实入口故障注入继续运行。

本机同一源码的单次 PM 审计：优化前约 5.50 秒，优化后约 3.28 秒；938 个扫描文件及完整序列化报告一致。文件读取从 3,013 次降至 1,131 次，exists 查询从 124,296 次降至 9,827 次。该数据是本机审计测量，不能直接视为 Actions 整体提速比例。

## 验证范围

前端进程模式已对照运行：原 forks 模式约 160.4 秒，threads 模式约 173.6 秒；两轮均为 518 个文件、4,703 项通过及 4 项既有跳过。threads 在本机没有收益，因此不修改现有模式、文件隔离或全局测试桥接。

前端全套、真实验证目录故障注入、发布编排控制、两组 FOK 保护及数据库兼容演练的本机结果记录在忽略目录 `output/validate-*`。正式发布继续由最终提交对应的 Actions 重新验收和封包。

拆分前的性能优化阶段曾完成独立完整验收 22/22、临时 PostgreSQL 兼容 5/5；验证目录 95 个文件 / 2,560 项及前端 4,703 项通过、4 项既有跳过。这些是该阶段源码指纹的历史结果，不作为后续发布凭证。拆分后的发布编排、封包及运输回归另行验证；正式发布仍由最终提交的 Actions 执行。提交与发布状态以 Git 和对应提交的 Actions 为准。
