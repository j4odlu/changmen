# 前端 后端 RDS 解耦执行方案

日期：2026-10-15。状态：第一轮已以 `d3fd4a0a` 发布；第二轮管理用户 SQL 收口及防回退检查已以 `87b96fde` 发布，验收见 [第二轮验收](audits/2026-10-15-decoupling-round2/ACCEPTANCE.md)。

第三轮已以 `9aa9159c` 完成剩余业务查询收口、发布和线上验收：正 EV 仪表盘与 Predict.fun 体育 relay 身份查询。冻结的维护诊断与只读运行版本观察单列保留；本轮验收见 [第三轮验收](audits/2026-10-15-decoupling-round3/ACCEPTANCE.md)。

第四轮推进批次 3：数据库升级兼容与代码回退演练；业务实现、生产结构和发布激活行为保持。执行规范见 [数据库升级兼容](DATABASE_UPGRADE_COMPATIBILITY.md)，共享包是否拆分的依赖核对见 [共享包边界](SHARED_PACKAGE_BOUNDARIES.md)。

目标是让内部实现变化留在所属层，减少无必要的跨端修改和同步发布。保留 Vue 客户端、Node 服务端、PostgreSQL 与现有 monorepo，依次完成核心接口兼容测试、数据库访问收口、数据库升级兼容验证和发布范围细化。

本方案承接当天架构修复。已有修复是否进入候选版本和生产环境，需要在第一批明确；不能把工作区存在代码等同于生产已生效。第一轮已按后续授权实施核心接口回归和登录、在线信息数据访问收口，已随 `d3fd4a0a` 完成提交与生产发布。

## 目标与边界

| 改动 | 预期修改范围 | 必须证明的条件 |
| --- | --- | --- |
| 页面样式、布局、纯展示 | 前端 | HTTP 请求和业务行为保持 |
| 后端内部业务实现 | 后端 | 同一请求的响应与持久化语义兼容 |
| 数据库索引 | 数据库增量脚本 | 查询结果不变，写入约束与执行计划符合预期 |
| 数据库存储字段调整 | 数据层与增量脚本 | 业务方法及 HTTP 输出保持，旧后端仍可运行 |
| 新增可选响应字段 | 提供方先发布 | 旧消费者忽略新增字段，新消费者处理字段缺失 |
| 全新业务功能 | 按真实数据流协作 | 明确哪些层新增能力，分开安排发布顺序 |
| 双端共享协议或注册信息 | 共享包及实际消费者 | 运行时消费和构建依赖均已验证 |

“无需修改另一端”“无需发布另一端”和“无需验证另一端”分别记录。后端内部改造仍可能需要前端兼容验证，但不应为了通过测试修改前端。

保留现有 A8 调用顺序、表单编码、字段大小写、envelope、轮询及错误提示语义。新增 parity 注释继续使用 `[A8 可证实]`、`[changmen 推测]`、`[changmen 扩展]`，不把 changmen 的数据库实现描述为 A8 服务端实现。

账号继续以 players 为持久化真相；订单和资金等待持久化确认；采集按原策略允许异步写。保持电竞与体育的数据隔离、单 backend 进程约束、matcher 唯一合场写路径以及既有 FOK/GTC 分工。

## 批次 1 建立核心接口兼容测试

### 范围和落点

首轮覆盖以下链路，先完成主路径，再扩展全部 action：

| 链路 | action 或分支 | 必须覆盖的情况 |
| --- | --- | --- |
| 账号 | `Client_GetData` 和 `Client_SaveData` 的 ACCOUNT；`Client_GetAccounts`、`Client_SaveAccounts` | 数组与 JSON 字符串层次、空覆盖拒绝、归属校验、凭证字段保留、持久化失败 |
| 比赛 | `Client_GetMatchs` | 空列表、ID 类型、Bets/Sources、可选 PM/PF 字段、结束赛事处理、既有消费者读取 |
| 采集 | `API_SaveMatch`、`API_SaveBet`、`API_SaveLiveTimer` | 外层表单与内层 JSON、非法数据、browser/VPS 写入归属、原响应语义 |
| 订单 | `Client_SaveOrder`、`Client_SaveOrderBind`、`Client_GetOrderList` | 分页与别名、状态与金额、保存失败、重复保存既有规则、电竞体育隔离 |
| 会话 | `Client_Login`、`Client_RefreshToken` | cookie 与 legacy 分支、鉴权失败 envelope、既有刷新流程 |

修改落点：`packages/api-contract/src/`、该包测试和 fixtures，`server/backend/core/esport-api/` 的 HTTP/handler 测试，以及对应客户端 API 测试。复用 `core/account/order/dto.js` 的既有映射，不建立第二套订单转换器。

### 实施步骤

1. 固定旧消费者样本：记录来源版本和期望结果，区分 A8 证据与 changmen 扩展。样本期望值不由被测新实现自动生成。
2. 为核心 action 建立请求与响应类型映射，并区分浏览器逻辑参数、线上表单字段、解析后的业务输入。ACCOUNT 的 `Key` 决定 `Value` 语义，不能用一个过宽对象掩盖差异。
3. 核对当前真实协议后再协调 DTO 与 schema。例如 `ClientMatchDto.ID` 与出站校验当前宽严不同，先确认已有消费者如何处理，不能直接收紧线上解析导致兼容中断。
4. 测试环境严格验证核心响应；线上保留已有宽松校验，新增强拒绝需单独证明兼容。新增未知字段可保留，字段缺失、类型改变和错误语义变化须明确报错。
5. 对核心 API 包装器逐步采用 action 对应的参数和返回类型。保留底层 transport 和旧入口，使 HTTP 次数、顺序、序列化、await 关系和重试语义不变。未覆盖 action 暂留兼容入口，但新代码不能绕回任意字符串调用。
6. 补充核心 OpenAPI 请求、响应和错误描述；接入默认 `test:api-contract`，保留 URL 测试及已有出站测试。核对 `.ts` 源文件与编译 `.js` 的真实加载关系，沿用既有构建流程。

关键验收：更改必需字段类型、移除字段、把失败改为成功、改变表单编码的负向样本必须失败。只对共享类型通过编译不算 HTTP 契约通过，测试必须覆盖真实解析/序列化和 handler 输出。

完成此批时不需要改表。先固定行为，再动实现；如样本揭示真实缺陷，单独做有失败回归的修复提交。

## 批次 2 收拢数据库访问

### 第一项 用户登录和在线信息

来源：`server/backend/core/account/user_login_meta.js`、`user_presence.js`。数据方法落入现有 `server/db/rds/profile_store.js`，通过数据库包公开入口导出。

1. 先为当前读写和并发边界建立测试，再抽出按业务命名的方法，例如 `recordUserLoginMetadata`、`advanceUserLastActiveAt`；最终名称按现有导出约定确定。
2. 登录时间、IP 与在线时间只修改自己拥有的 JSON 字段。保证旧快照不会覆盖并发写入的其它 preferences 字段，并明确同字段时间的新旧策略。仅把整对象 UPDATE 搬到 db 不满足要求。
3. 盘点所有写入 `profiles.preferences` 的路径，包括后台设置，统一规定 patch 与整体替换的使用范围。已有每用户队列不能替代跨进程的数据库并发保护。
4. 在线状态的 debounce 和错误处理保持原语义；持久化边界若需调整，单独提交并验证。旧 sessions 导入先保留既有路径语义，不随 SQL 抽取新增自动导入。

验收：登录信息与在线时间并发更新互不覆盖；无关偏好保持；失败和缺失用户按明确结果返回；原在线窗口和写入频率保持。

### 第二项 管理用户和权限

来源：`core/account/admin_service.js`、`admin_maintenance.js` 中实际使用 SQL 的业务。复用现有 profile/user 数据方法；新增持久化实现按领域放在 `server/db/rds/`，不新建通用 ORM 或万能 repository。

鉴权、操作者权限与 HTTP 错误映射仍归后端业务层。数据层负责查询、锁、唯一约束和需要原子完成的变更；不能把原事务拆成多次互不关联调用。

按用户创建、名称更新、密码更新、权限与删除依次迁移。权限、删除和资金关联路径各自独立验收，保留归属检查、最后管理员保护及原有缓存失效行为。

### 第三项 剩余业务查询

将 `core/esport-api/value_bet_service.js`、`sport_predictfun_fetch.js` 等剩余直接 SQL 逐个迁入所属数据模块。订单已有 DTO 映射先固定回归，不顺便重写 PM/GTC、财务统计和首单编排。

业务层逐步消费稳定的业务记录；数据库行字段名仅在数据适配层解释。迁移时先保持已有方法返回形状，避免一次更改所有消费者。

### 防止回退

扩展 `scripts/check-team-boundaries.mjs`，检查业务模块对连接池、`pg`、db 内部路径和 SQL 执行入口的直接使用。第一版用按具体位置登记的历史例外，只允许减少；每次新增或扩大例外都视为边界变化。

结构核验、初始化和明确的只读诊断可以保留指定数据库访问入口，禁止整目录豁免。检查测试应覆盖别名导入、动态 import、底层相对路径和间接 re-export 等实际使用形式；文本 SQL 搜索只作辅助盘点。

验收：迁完的业务模块不直接操作表；只在数据层调整查询实现时，既有 HTTP 契约和业务测试仍通过；没有为补测试而修改前端。

## 批次 3 验证数据库独立升级

本批先建立流程和测试，不为架构整洁新造表或重命名业务字段。保留 `check-rds-schema.mjs` 与 `rds-schema-check.mjs` 的只读职责。

1. 每项将来的数据库变化都列明前置结构、目标结构、受影响数据、锁影响、旧代码兼容性和恢复方式。增量脚本只执行目标变化，不扫描重放历史 SQL。
2. 先新增可选列、表或索引，再部署能兼容旧数据的代码；必要回填单独执行并可断点恢复。只有在旧版本退出回滚窗口后，才安排删字段或收紧约束。
3. 结构要求来自经过测试的固定清单；不能从生产结构直接录制并认定为正确。新增清单继续核对 checksum、约束、索引有效性、函数和触发器要求。
4. 在临时 PostgreSQL 验证空库初始化、已有基线增量升级、旧后端读取新结构、新后端读取旧数据，以及新后端在缺少必需结构时于激活前失败。
5. 对升级后的数据库回退代码进行演练。常规代码回退保留兼容新增结构；涉及数据转换的恢复必须有单独策略，不把自动逆向 DDL 当作通用回退。

兼容要求按发布顺序制定：新后端不必能在缺失必需字段的旧库上启动，但必须提前明确阻断；新前端若需要后端新增能力，应保持旧功能可用或明确安排后端先发布。

验收：日常部署仍不写业务数据和迁移账本；涉及结构变化的维护流程在进程切换前执行候选只读核验，缺必需结构时中止；兼容新增结构不会迫使前端修改；历史账号、权限与序列状态不受检查影响。第四轮证明命令与流程约束；第五轮将生产库、建库脚本和检查规则统一为一套标准；候选已接入激活前只读闸门，不接受旧结构豁免。上线状态单独以本轮发布证据确认。

## 批次 4 缩小发布范围

当前 `scripts/deploy/classify-deploy-scope.mjs` 将全部 `packages/` 变化归为 full。此处最后优化，避免在兼容测试建立前过早省略必要组件。

修改落点：`classify-deploy-scope.mjs`、`change-plan.mjs` 及对应测试；需要调整验证选择时修改 `scripts/verification/validation-plan.mjs`。复用现有发布系统。

1. 建立包入口的运行时和构建消费者清单，覆盖 Node loader、动态加载、adapter 瘦包同步、Vite alias、workspace、lockfile 和生成产物。
2. 只对证明为浏览器专用的实现加入 frontend 规则；`registry`、`loader`、共享 manifest、契约与未分类路径仍保守处理。不能仅凭文件扩展名或目录名称判断。
3. 每项分类规则附可复现证据及反向用例：若浏览器专用实现新增服务端或构建消费者，检查必须阻断原分类，要求重新评估。
4. 保留从各组件实际已部署版本到候选版本的累计差异计算。不能只比较本次 commit，遗漏此前未发布的组件变化。
5. 将需要运行哪些检查和需要发布哪些组件分开。后端独立发布仍运行必要的旧前端兼容测试；原发布保护、源码基线与完整验收不通过分类调整绕开。

| 演练 | 预期结果 |
| --- | --- |
| 仅修改页面展示 | 发布前端，backend 进程不重启 |
| 仅修改后端 SQL 实现且协议保持 | 发布后端，前端产物版本保持 |
| 已证明浏览器专用的 adapter 实现变化 | 发布前端；证据不足则 full |
| 共享 manifest、loader 或协议变化 | 按实际消费者验证；首轮保留 full |
| 前端本次有改动，后端仍有未部署旧差异 | 根据两个已部署版本正确纳入待发布组件 |
| 未知路径、不可确定的旧版本、依赖证据过期 | 执行保守规则或明确阻断，不能静默缩小范围 |

验收：发布计划的每个组件选择都有路径及消费者依据，能从测试与版本记录验证；独立发布成功不能只靠脚本输出一个 scope 字符串。

## 批次 5 总体验收

固定旧消费者、旧后端和旧结构的具体版本，新旧指明确版本，不随开发中的 HEAD 自动移动。

| 组合 | 验收重点 |
| --- | --- |
| 旧前端和新后端 | 账号、比赛、订单、鉴权的原行为保持 |
| 新前端和旧后端 | 原功能可用；新增可选能力有缺省处理 |
| 新前端和新后端 | 核心主路径及失败路径通过 |
| 旧后端和兼容新增结构 | 代码回退后可正常工作 |
| 新后端和缺失必需结构 | 激活前清晰失败，原进程与数据保持 |

写操作的旧新对比使用隔离测试库和场馆 stub；禁止在真实下注、保存订单或合场写库路径双跑。比较结果包含数据库状态、HTTP 请求次序和缓存发布顺序，避免只比较页面截图。

既有测试入口继续使用：

```text
npm run check:boundaries
npm run test:api-contract
npm run check:change:plan
npm run check:change
```

新增契约和边界测试须接入正式入口。改前端至少运行 `typecheck:frontend` 或 `app:build`；涉及事务和 schema 时使用现有 `scripts/testing/` 临时 PostgreSQL 测试方式。具体测试范围由实际候选及现有检查器决定，不因本方案手动降级。每轮实施的实际验证结果记录在对应验收文档中。

更新 `docs/TEAM_BOUNDARIES.md`、`docs/DATA_STORAGE.md` 和契约 README，使文档与最终实现一致。尤其核对账号和配置的持久化确认策略，避免继续使用旧的异步保存描述。

最终交付记录：候选版本、各批次文件范围、测试结果、接口兼容矩阵、迁移前置条件、发布组件和回退方式。生产完成状态只能由对应候选的真实发布验收确认。

## 建议提交顺序

| 顺序 | 提交内容 | 主要效果 |
| --- | --- | --- |
| 1 | 范围清单和固定协议样本 | 明确基线，防止跟着新实现改期望值 |
| 2 | 核心 HTTP 契约测试与正式测试接线 | 在重构前发现跨端协议变化 |
| 3 | action 类型映射和核心 API 包装器接入 | 编译期发现请求参数和返回类型误用 |
| 4 | 登录及在线信息的数据方法和并发回归 | 第一组业务与数据库隔离示范 |
| 5 | 管理用户查询与写入逐项收口 | 表结构知识集中到数据层 |
| 6 | 剩余业务 SQL 与新增边界检查 | 阻止耦合重新增长 |
| 7 | 数据库升级兼容测试与操作规范 | 数据库升级和代码发布分开 |
| 8 | 已证明的浏览器专用发布分类 | 减少不必要的后端重启 |
| 9 | 新旧版本兼容和发布回退演练 | 验证能分开发布和恢复 |
| 10 | 精确候选验收及文档同步 | 形成可执行的维护规则 |

提交 5、6 按事务领域拆成更小提交。提交 3 如果触及受保护入口，先验证最小改动与原冻结要求的兼容性；无法证明等价时保留入口，先交付测试和新增类型，不修改原保护基线。实际排期在批次 0 的接口和 SQL 清单完成后按范围确定。

第一轮以提交 1、2、4 为最小可交付范围：核心接口有回归保护，登录与在线信息成为数据库边界样板。其余批次依次扩展，避免为了所谓“完美架构”开展大规模搬目录、拆微服务、更换数据库或重写投注流程。
