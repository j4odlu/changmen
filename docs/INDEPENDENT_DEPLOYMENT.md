| 组件 | 发布动作 | 失败处理 |
|---|---|---|
| 前端 | 验证已验收的静态制品，原子切换 `dist`，检查页面及版本 | 恢复上一版静态入口 |

## Actions 入口与发布范围

[changmen 扩展] 2026-10-25：推送 `master` 后，一个 `validate` job 读取生产基线、判断组件范围、执行检查、构建并封包。取消 plan/checks/collect 的跨 runner 编排、分组报告和中间制品传递。两个可复用部署 workflow 消费同一份已验证制品，不重复构建。组件独立发布和联动时后端先行的规则保持不变。

| 变更 | 发布选择 |
|---|---|
| `client/web/**`、四个 `client/packages/` 客户端包、`client/devtools/**` | 前端 |
| 后端运行代码、`server/venues/**`、RDS 运行接口 | 后端 |
| 前后端各自独立的变更 | 两端独立发布 |
| 共享包、根依赖、跨端 API 或部署运行脚本的联动变更 | 涉及两端时，后端成功后再发布前端 |
| RDS SQL、历史迁移/回填脚本、数据库维护入口 | 不自动发布应用，也不自动执行维护 |
| 仅文档、workflow、`scripts/verification/**`、`scripts/testing/**`、发布规则和发布测试 | 不因此发布应用；仍执行适用验证 |

分类保守处理未知路径。共享包同时用于浏览器和 Node，属于合法共享依赖，不因部署拆分而复制或修改业务代码。

目录分类以已完成的物理隔离为依据，覆盖当前全部 24 个 workspace。`packages/shared`、`packages/api-contract`、Node/Vite 共用的 `devtools/runtime-tooling`、根 package/lock 及共享运输/验收实现仍按双端处理；未知客户端包仍按双端处理。依赖审计清单中的 `publishScopeOptimizationEnabled:false` 继续表示未启用整仓依赖图推断，不影响这里明确登记的目录规则，也不宣称剩余动态输入已经消除。

所有 master push 进入统一验证任务，发布 job 只在组件受影响时启动。纯 CI 修改不会制造应用发布；若某端此前发布失败，计划仍会基于该端实际生产提交补足差异。删除及跨目录重命名按旧路径、新路径分别计算，不能借重命名漏掉任一组件。隔离启动测试自身的修改仍触发 Linux 八进程验收，不因此重启生产。

自动计划读取 VPS 已发布目录和成功记录，对比每端已发布提交，补足上次失败/部分发布留下的差异。计划读取本身不请求后端 HTTP、PM2 或 RDS；记录缺失/不一致时停止，避免猜测版本。手动入口：Actions → **Validate and release** → Run workflow → `frontend` / `backend` / `full`，仅允许 master。手动单端保留所选组件，执行对应组件测试；手动后端/full 保留数据库兼容演练，手动纯前端无需数据库。FOK 完整专项仍为独立入口。`full` 明确按后端、前端顺序执行。

不相关的前端发布不检查后端是否在线；涉及双方联动时才核对后端候选版本。API 仍须兼容旧前端：先增加兼容能力，再发布前端，最后另行清理旧接口。先后顺序本身不能使破坏性接口变更安全。

## 必要检查与回滚

日常只使用 `npm run check:change`，可用 `npm run check:change:plan` 预览范围。检查和发布复用同一份目录归属规则：

| 变更 | 日常检查 |
|---|---|
| 仅文档 | 不执行代码检查 |
| 前端页面、store、FOK/GTC 执行、浏览器 adapter 和客户端包 | 边界/契约检查、完整前端测试、生产构建（包含类型检查） |
| 后端、matcher、collector、RDS | 路由编译、后端及共享依赖测试（包含边界/契约检查） |
| 两端独立改动、共享或未知输入 | 对应两端检查；共享和未知输入保守覆盖两端 |
| 检查/部署工具 | 工具自身回归；仅工具改动不追加应用全套测试 |

前端构建已运行 `vue-tsc -b`，日常链路不再单独重复类型检查。验证入口的回归仅在入口或计划实现/测试改动时运行；其它验证器按本次改动、传递文件引用及策略输入选择相关自测，日志与验收报告记录实际套件。未知验证器保守覆盖当前门禁套件，不回退整套历史审计。Node 专用自测仅随对应实现/测试变化运行。普通业务修改不运行历史 FOK 551 项、完整 22 阶段审计或检查器自身回归。

日常边界检查直接检查当前源码：依赖方向、PM 动态载入/loader、安装声明、退役入口、兼容门面、公共资源契约和 SQL 校验保留；移除对当前业务实现的历史整文件哈希要求。冻结清单保持原字节，并保护迁移后的真实实现；命中仍需显式解冻并完成对应行为回归，不再默认运行整套迁移等价证明。仅历史证据 JSON 的修订不执行旧源码证明，当前门禁实际使用的策略输入仍选择相关自测。

历史迁移审计保留为明确入口：

```text
node scripts/verification/check-historical-migrations.mjs
npm exec --call="node scripts/verification/run-self-tests.mjs --all"
```

手动 **Special release audit** workflow 执行历史迁移审计及既有 22 阶段专项。原有历史验证器和负向用例保留；历史审计失败不能替代、放行或削弱本次业务回归。

发布阶段额外对后端制品执行 Linux 安装和八进程启动验收。临时 PostgreSQL 五组兼容检查只随 RDS、数据访问/鉴权/订单等相关业务、共享数据契约、根依赖或数据库检查工具的变更执行；未知输入和手动后端/full 保守保留。普通 UI、可观测性和发布编排改动无需数据库兼容演练。Linux 安装验收自身使用临时 PostgreSQL，即使本次不需要五组数据库检查也会准备工具。PR 的独立数据库工作流仅覆盖数据相关路径，手动诊断入口保留。

同一 runner 直接记录本次提交、文件树、输入指纹和所有检查结果，再封存前端构建及已经通过 Linux 验收的后端归档。失败、缺项、输入变化或制品变化会阻止封包和发布；运输前仍核对提交和归档校验值。删除中间分组报告不影响这些校验。

历史迁移/FOK 证据的原始清单和哈希保留。原地演进的检查/部署控制文件在历史视图中读取既有基线，迁移过的冻结检查入口读取其原始 workspace 迁移提交；当前行为由相关自测、workflow、封包及失败阻断回归验证。历史审计仍执行运行代码与实际迁移文件的原有历史校验；日常发布保留当前结构和行为检查，以及已部署 SQL 的不可变校验。

前端检查实际页面、主 JS 和构建身份；切换保留上一版自身的 hashed assets，供已打开页面继续懒加载。后端在触碰运行进程前完成运行依赖安装、预编译路由校验和只读连接检查；不再做整库结构快照比较、历史 SQL 重放、账号导入/owner 回填、证书建表或 timer 清理。发布后检查 HTTP、内嵌 matcher 心跳、8 个进程各一个实例、PID/状态/准确 cwd 和入口，以及运行版本身份。保持单实例 esport，不启动独立 matcher 或暂停的 SXBet。

后端失败使用已安装的上一版恢复，不重新构建、不迁移数据库。受管旧版本必须有保存的验收身份；缺失时在替换进程前停止。恢复后再次核对健康、进程和旧版本身份，不能把 PM2 命令成功等同于恢复成功。首次接管旧目录没有历史制品证据，只能核对健康和进程路径。

TERM、HUP、INT 在切换期间触发恢复；健康验收完成后，在写入成功记录至退出回滚保护的短暂提交阶段忽略这些信号，防止新记录与旧运行版本不一致，写入失败仍触发回滚。SIGKILL/主机断电无法由 shell trap 恢复，需要运维处理。每端有独立 flock 锁，Actions 发布代次排队，旧代次不能覆盖较新成功版本。失败同代次可重试。

[changmen 扩展] 传输使用每次生成的唯一 `/tmp/changmen-<release-id>.<random>` 目录。上传/校验失败由本机退出钩子补做远端清理；激活和回滚结束后由远端包装脚本自行清理。两者共用目录内的 flock，仍有任务占用时保留输入，拒绝非法路径和软链接，不删除版本目录、持久 storage 或发布状态。清理失败仅告警并保留原发布退出码；已有激活/回滚输出继续进入 Actions 日志。SSH 完全不可达或 SIGKILL/主机故障下不保证即时清理，告警列出需要后续核查的精确临时路径；本批不扫描或清理历史目录，不调整组件分类、安装、发布先后或 workflow。

## RDS 维护

RDS 是独立持久层。普通应用发布及回滚均不修改数据库结构，也不运行维护脚本。仅修改维护文件不会重启应用；同时修改业务代码时，仍按业务代码选择应用组件。

有实际结构需求时，先评审具体 SQL、现状、备份和验证方法，确保新旧应用均兼容，再单独执行所需迁移。数据回填也单独执行和验收。历史 `apply-rds-schema.mjs` 包含历史迁移逻辑，不能作为日常生产发布步骤重复运行。

后端既有 `npm run check:rds-schema` 是离线 SQL 覆盖诊断，不是线上结构验收，也不代表 RDS 已执行某次迁移。应用健康检查无法替代有意变更数据库时的专项验证。
