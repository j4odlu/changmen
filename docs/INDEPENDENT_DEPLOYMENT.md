# 前端、后端与 RDS 独立发布

[changmen 扩展] 2026-10-19：通用发布已移除默认 FOK 551 项检查及 22 阶段专项依赖。组件测试/构建、数据库兼容、候选与产物身份校验继续执行；FOK 专项保留独立入口。此前专项接入/复用的记录以 [当前验收归属](./ACTIONS_VALIDATION_PERFORMANCE_20261019.md) 为准。

[changmen 扩展] 生产统一从 GitHub Actions **Validate and release** 发布。本机只开发、验证、commit/push 和只读核验。部署层保持三项职责：

| 组件 | 发布动作 | 失败处理 |
|---|---|---|
| 前端 | 验证已验收的静态制品，原子切换 `dist`，检查页面及版本 | 恢复上一版静态入口 |
| 后端 | 独立版本目录安装运行依赖、验证预编译路由，数据库 `SELECT 1`，启动既有 8 个进程并检查健康/版本 | 恢复上一版进程并核验恢复结果 |
| RDS | 另行评审并执行具体结构或数据维护 | 按该项维护方案处理，不随应用回滚 |

## Actions 入口与发布范围

推送 `master` 后，plan job 固定生产基线、候选提交和检查计划；controls、backend、frontend 三组在独立 runner 并行执行所需检查；validate job 核对全部结果及构建产物后封包。两个可复用 workflow 只消费已验收制品，不重复构建。没有对应检查的组不启动。

| 变更 | 发布选择 |
|---|---|
| `client/web/**`、四个 `client/packages/` 客户端包、`client/devtools/**` | 前端 |
| 后端运行代码、`server/venues/**`、RDS 运行接口 | 后端 |
| 前后端各自独立的变更 | 两端独立发布 |
| 共享包、根依赖、跨端 API 或部署运行脚本的联动变更 | 涉及两端时，后端成功后再发布前端 |
| RDS SQL、历史迁移/回填脚本、数据库维护入口 | 不自动发布应用，也不自动执行维护 |
| 仅文档、workflow、`scripts/verification/**`、`scripts/testing/**`、发布规则和发布测试 | 不因此发布应用；仍执行适用验证 |

分类保守处理未知路径。共享包同时用于浏览器和 Node，属于合法共享依赖，不因部署拆分而复制或修改业务代码。

目录分类以已完成的物理隔离为依据，覆盖当前全部 24 个 workspace。`packages/shared`、`packages/api-contract`、Node/Vite 共用的 `devtools/runtime-tooling`、根 package/lock 及共享运输/验收实现仍按双端处理；未知客户端包仍按双端处理。依赖审计清单中的 `publishScopeOptimizationEnabled:false` 继续表示未启用整仓依赖图推断，不影响这里明确登记的目录规则，也不宣称剩余动态输入已经消除。

所有 master push 仍进入计划阶段，发布 job 只在组件受影响时启动。纯 CI 修改不会制造应用发布；若某端此前发布失败，计划仍会基于该端实际生产提交补足差异。删除及跨目录重命名按旧路径、新路径分别计算，不能借重命名漏掉任一组件。隔离启动测试自身的修改仍触发 Linux 八进程验收，不因此重启生产。

自动计划读取 VPS 已发布目录和成功记录，对比每端已发布提交，补足上次失败/部分发布留下的差异。计划读取本身不请求后端 HTTP、PM2 或 RDS；记录缺失/不一致时停止，避免猜测版本。手动入口：Actions → **Validate and release** → Run workflow → `frontend` / `backend` / `full`，仅允许 master。手动单端保留所选组件，执行对应组件测试及数据库兼容演练，不自动接入 FOK 完整专项。`full` 明确按后端、前端顺序执行。

不相关的前端发布不检查后端是否在线；涉及双方联动时才核对后端候选版本。API 仍须兼容旧前端：先增加兼容能力，再发布前端，最后另行清理旧接口。先后顺序本身不能使破坏性接口变更安全。

## 必要检查与回滚

发布前执行边界检查，以及变更范围要求的后端测试、前端类型检查/测试/构建；后端、数据相关及未知/手动发布保留临时 PostgreSQL 五组检查。FOK 551 项和完整 22 阶段审计保留独立入口，不作为通用发布的自动前置条件。各组结果绑定相同 Actions run/attempt、提交、文件树、输入指纹和计划；缺失、重复、过期或失败均不能封包。前端制品和数据库证明核验 SHA 后进入最终封包，运输前继续核对提交与归档。细节见 [当前验收归属](ACTIONS_VALIDATION_PERFORMANCE_20261019.md)。

[changmen 扩展] 第二批将需要的完整审计移至等价组件检查之前；组件项引用本次审计中实际成功的同一命令和工作目录，保留全部逻辑检查与 22 个实际执行阶段。引用还绑定运行标识、环境摘要和报告内容哈希，并在封包/运输前复核。551 入口保护和数据库检查继续独立执行；日常/PR 和低风险自动前端保持原离线计划。见 [验证复用清单及限制](ACTIONS_VALIDATION_REUSE_20261018.md)。

[changmen 扩展] 数据库检查去重：`master` push 的五组临时 PostgreSQL 检查统一由发布验收链执行，独立 `Database compatibility` 工作流仅保留原路径过滤的 PR 和手动入口。原 push 路径覆盖全部迁入发布计划；原触发范围内即使只改旧 SQL/维护入口、不发布应用，也照常执行五组并绑定本次提交、文件树和输入指纹，缺失或失败仍不能封包。应用组件选择和后端先行规则不变，不因为去重而发布原本不应发布的应用；新 RDS 路径原有的保守分类本批不调整。PR、手动诊断与最终发布各自验证，不跨工作流借用绿色状态或缓存数据库通过结果。

前端检查实际页面、主 JS 和构建身份；切换保留上一版自身的 hashed assets，供已打开页面继续懒加载。后端在触碰运行进程前完成运行依赖安装、预编译路由校验和只读连接检查；不再做整库结构快照比较、历史 SQL 重放、账号导入/owner 回填、证书建表或 timer 清理。发布后检查 HTTP、内嵌 matcher 心跳、8 个进程各一个实例、PID/状态/准确 cwd 和入口，以及运行版本身份。保持单实例 esport，不启动独立 matcher 或暂停的 SXBet。

后端失败使用已安装的上一版恢复，不重新构建、不迁移数据库。受管旧版本必须有保存的验收身份；缺失时在替换进程前停止。恢复后再次核对健康、进程和旧版本身份，不能把 PM2 命令成功等同于恢复成功。首次接管旧目录没有历史制品证据，只能核对健康和进程路径。

TERM、HUP、INT 在切换期间触发恢复；健康验收完成后，在写入成功记录至退出回滚保护的短暂提交阶段忽略这些信号，防止新记录与旧运行版本不一致，写入失败仍触发回滚。SIGKILL/主机断电无法由 shell trap 恢复，需要运维处理。每端有独立 flock 锁，Actions 发布代次排队，旧代次不能覆盖较新成功版本。失败同代次可重试。

[changmen 扩展] 传输使用每次生成的唯一 `/tmp/changmen-<release-id>.<random>` 目录。上传/校验失败由本机退出钩子补做远端清理；激活和回滚结束后由远端包装脚本自行清理。两者共用目录内的 flock，仍有任务占用时保留输入，拒绝非法路径和软链接，不删除版本目录、持久 storage 或发布状态。清理失败仅告警并保留原发布退出码；已有激活/回滚输出继续进入 Actions 日志。SSH 完全不可达或 SIGKILL/主机故障下不保证即时清理，告警列出需要后续核查的精确临时路径；本批不扫描或清理历史目录，不调整组件分类、安装、发布先后或 workflow。

## RDS 维护

RDS 是独立持久层。普通应用发布及回滚均不修改数据库结构，也不运行维护脚本。仅修改维护文件不会重启应用；同时修改业务代码时，仍按业务代码选择应用组件。

有实际结构需求时，先评审具体 SQL、现状、备份和验证方法，确保新旧应用均兼容，再单独执行所需迁移。数据回填也单独执行和验收。历史 `apply-rds-schema.mjs` 包含历史迁移逻辑，不能作为日常生产发布步骤重复运行。

后端既有 `npm run check:rds-schema` 是离线 SQL 覆盖诊断，不是线上结构验收，也不代表 RDS 已执行某次迁移。应用健康检查无法替代有意变更数据库时的专项验证。

| 内容 | 路径 |
|---|---|
| 前端版本 | `<root>/.releases/frontend/<release-id>` |

| 成功记录/验收证据 | `<root>/.deploy-state/` |
| 持久配置与 storage | 原 `<root>/server/backend/.env`、`storage`，版本目录通过链接引用 |
