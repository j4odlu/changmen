# Matcher 与用户比赛显示一致性修复方案

[changmen 扩展] 2026-10-19。状态：未实施。本次只完善方案文档。已有取证见[审计报告](audits/MATCH_PUBLICATION_CONSISTENCY_AUDIT_20261019.md)。

## 修复后用户应该看到什么

本次解决的是：matcher 已确认场馆比赛不在当前采集结果中，用户却仍看到该场馆旧盘口，或多看到一场没有任何有效来源的比赛。

规则只有三条。这里的“有效来源”指合场记录所关联的场次，仍存在于可信的当前平台比赛快照中；不是看赔率缓存里有没有数字。

| 当前有效来源 | 用户比赛列表 | matcher 已合场列表 |
| --- | --- | --- |
| 两个或更多 | 显示比赛，只显示有效来源盘口 | 显示同一比赛，标明同样的有效来源 |
| 一个 | 仍显示比赛，只显示这一来源盘口 | 仍显示同一比赛，失效挂载可以另外标注 |
| 零个 | 不显示比赛 | 不计入已合场可见列表，原始记录仍可供运维查询 |

赛前与进行中使用相同规则。盘口锁盘仍显示锁定，不等于场次失效。参考赔率、比分及用户个人筛选另按现有功能处理。

### 用本对话的两场比赛验收

| 比赛及当时情况 | 修复后用户看到什么 | 修复后 matcher 看到什么 |
| --- | --- | --- |
| 原 #8189 FURIA vs BB Team：OB 已失效，PM 仍在 | 比赛保留，只有有效的 PM 盘口；OB 行不再出现 | 同一比赛保留，PM 有效；详情可注明原 OB 挂载失效 |
| #8208 Team Cobra vs New Growth：OB、RAY 都已失效 | 整场不再出现，即使还没到计划开赛时间 | 也不计入可见已合场列表；数据库原记录不被本次读取删除或结束 |

比较 matcher 时，取 ID 已匹配与队名已匹配两栏的完整比赛集合；不把单个分类栏或带搜索条件的数量当成用户完整列表数量。

## 现在为什么会不一样

两端已经共用 client_matches，但后续处理不同：用户接口把未结束的旧合场记录继续下发，matcher 页面又独立检查当前平台来源。于是同一份旧记录，在两个页面得到了不同的展示结果。

本次把这一步检查放在两端共用的服务端读取过程中：读取合场记录和当前平台比赛，先清除失效来源的展示内容，再把结果交给用户接口和 matcher。无需新建另一套合场系统或数据库发布状态。

## 具体改哪些地方

| 位置 | 要做的改动 |
| --- | --- |
| matcher 的公共服务端能力 | 提供一套来源检查与展示清理方法，输入为现有合场记录和可信的平台比赛索引，返回清理后的列表；由 workspace 公共入口提供给 backend |
| backend 的 Client_GetMatchs 读取路径 | 下发上述清理结果，不再把失效平台盘口原样发送给用户；响应仍为现有数组格式 |
| matcher 的 dashboard 数据组装 | 使用同一个方法确定已合场列表与数量；原始挂载另用于诊断详情 |
| matcher 页面 | 按服务端结果展示，不再用另一套条件筛掉单来源比赛或重新决定业务可见数量 |

backend 不得被 matcher 反向导入，数据库仍走 @changmen/db。若当前数据读取方法无法区分失败与成功空结果，仅为此入口补必要的明确成功标记或严格读取能力。

清理只作用于返回数据的副本：去掉失效平台的 Matchs、Bets.Sources 及对应展示 Reverse 项。其它平台的盘口 ID、主客方向、地图归属和价格不变。原始数据库记录、人工绑定与反转设置不变，不能原地修改共享缓存。

这样，本轮没有重新合出的旧记录也会被检查，不需要修改合场聚类算法。

## 分三步做 每步都能停

### 第一步 把上述规则做成可验证的方法

实现共同方法并补测试，暂不接入线上两个页面。直接用三馆变两馆、两馆变一馆、全部失效、来源恢复和锁盘等样本验证输出，包含本对话的两类案例。

完成标准：同一份输入只得出一个确定的可见比赛集合；失效平台盘口被清除，正常盘口方向和 ID 不变；原始输入没有被修改。

停在这里：只有方法和测试完成，线上行为不变，用户原问题尚未修复。

### 第二步 用户接口和 matcher 同时改用这个方法

完成上表中的两端接入，移除 matcher 页面重复的存活与两馆门槛判断。必须同时验证列表减少对已有补单、待确认订单、补绑、旧手动窗口和候选对象的影响，不得仅检查卡片是否消失。

完成标准：本对话两类样本得到前表中的结果；正常比赛不丢失，主客不颠倒；两个页面不再分别决定哪些比赛有效；订单相关行为回归和经典 FOK 兼容检查通过。检查不通过则不启用接入，不把未验证的问题留给第三步。

停在这里：主要修复已完成，两端继续按现有轮询工作，不需要等待新推送服务。两端接入作为一个完整交付，不能只接好一端就算完成。

回滚方式：撤回两端对共同方法的调用及对应页面改动，恢复原完整路径。没有数据迁移，也无需重建比赛或清空订单；原来的偶发差异会随回滚恢复。

### 第三步 用实际比赛确认修复并收尾

在第二步必要测试通过后，核对实际页面请求和只读数据。记录检查时间、比赛 ID 及页面筛选，确认来源变化与两端刷新后的结果。

完成标准：相同输入的比赛 ID、有效来源和盘口引用一致；实际数据稳定且双方完成刷新后没有持续差异；没有新增正常盘口或订单处理回归。不同请求时刻允许短暂差异，不要求本机实时赔率与 matcher 诊断文案完全相同。

停在这里：满足标准即结束本次修复。有残余问题就针对具体比赛另行定位，不自动追加新状态机、推送或持续监控工程。

## 这次保留哪些现有行为

- 保留现有数据库表、合场写入算法、轮询与版本缓存，不新增发布状态机、新版本协议或通知服务。
- 保留现有结束兜底和身份分配规则。隐藏只是读取时不返回，不提前写 ended，不删除原始比赛。
- 原记录尚活跃时，来源恢复便可以重新显示；若已被现有生命周期标结束，仍按原规则处理。本次不保证恢复已结束记录的原 ID。
- 不整馆清空赔率缓存，不向经典 FOK 新增拒单条件、历史查询等待或手动准备要求；有效盘口的下注、确认、补单与绑定规则保持兼容。

## 失败处理与验收边界

新增的平台来源读取失败时，不按空快照删除比赛或盘口，沿用既有合场读取结果并记录降级。本方法不缓存一份只随 client_matches 版本变化的清理结果，否则平台删除时又可能读到旧结果。

审计中已有的服务端查询失败可能误结束、用户 API 业务失败可能被当成空列表，继续单独记录和安排修复，不扩展成本次两个前置阶段。但新方法自身不能把失败当作来源消失。

第二步交付前运行相关行为测试、边界和 API 契约检查；改前端则运行 typecheck:frontend 或 app:build；影响共用链路则检查经典 FOK 等价及 VPS 固定保护，不更换基线。此前审计结果不能代替实施后的测试。

如果必须修改订单业务语义才能通过接入验收，则停在第一步已完成状态，单独说明原因再评估范围，不把列表修复自动扩大成订单系统重构。
