[changmen 扩展] 2026-10-25 先行工作：在 matcher 比赛卡片显示用户页已有的 PM 比赛状态。来源为 VPS PM Sports 采集服务写入的 `client_matches.pm_sport`；首次有效 WS 状态前由 Gamma 补充，之后由 Sports WS 接管。仅增加状态展示，独立验收后可停；下文的有效比赛统一产出与读取三步仍待实施。

## 一句话说明

**matcher 决定哪些比赛和盘口当前有效，并把完整结果保存下来；用户接口和 matcher 已合场页面直接读取该结果。**

这里的 matcher 是后端中的合场模块。matcher 页面是查看合场结果和诊断资料的浏览器页面。API 负责读取和返回数据，不再根据平台快照另做有效性判断。

目标链路：

```text
平台采集数据 → matcher 计算并保存当前有效结果
                         ├→ 用户接口 → 用户页面
                         └→ matcher 已合场页面
```

## 业务规则

“来源有效”指关联的场次仍存在于可信的平台比赛快照中，沿用已有采集宽限。是否锁盘、赔率缓存是否有数字，都不能代替场次有效性判断。

| matcher 本轮确认的情况 | matcher 保存的当前结果 | 两端展示 |
| --- | --- | --- |
| 至少两个有效来源 | 比赛及有效来源的盘口 | 都显示 |
| 已有合场只剩一个有效来源 | 保留该比赛，仅保留剩余来源盘口 | 都显示单来源比赛 |
| 已有合场全部来源失效 | 明确记录当前不展示，不沿用旧有效结果 | 都不显示，不等计划开赛时间 |
| 真实结束或人工强制结束 | 按现有生命周期处理 | 都移出当前列表 |
| 必需采集快照读取失败 | 本轮不提交新结果，不把失败当成来源消失 | 继续使用上次成功保存的结果 |

单来源保留适用于已有合场的赛前和进行中记录；新赛事的跨平台聚类门槛不变。盘口锁定仍按现有方式显示锁定。

本对话案例的目标很具体：原 #8189 在 OB 消失、PM 仍在时，两端都保留比赛，但用户不再收到 OB 盘口；#8208 在 OB、RAY 都消失时，matcher 写明当前不展示，两端都不再显示该比赛。

## 最小保存方式

client_matches 既用于保留比赛身份，又承担用户列表数据。目前只读 ended_at IS NULL 会把需要保留的旧身份也当成有效结果。要让用户直接读取 matcher 的结论，需要把这两种用途分清。

建议在现有 client_matches 中增加一个 `current_result` JSON 字段，表达 matcher 已经计算好的当前结果。字段为设计提议，尚不存在于实现；不复用已退役的 list_status。

| 字段内容 | 含义 | 读取方式 |
| --- | --- | --- |
| SQL NULL | 尚未由新版 matcher 计算 | 正式切换前必须补齐，不能当成已确认失效 |
| visible=true，match 为当前比赛对象 | 本轮确认有效；match 含现有线协议的 ID、Matchs、Bets、Reverse 等 | 直接返回 match，仍保持 API info 为数组 |
| visible=false，match 为空 | 本轮确认没有有效来源，当前不展示 | 不进入用户和 matcher 的当前比赛列表 |

这是 matcher 的一份保存结果，不建立新表、新服务、复杂状态机或独立版本协议。原有比赛身份、关联和人工设置继续按既有方式保存；当前结果不代替这些恢复与诊断资料。

matcher 必须在一次成功事务中同时更新本轮结果和相应合场数据，提交成功后再失效既有列表缓存。两端共用现有提交后读取机制；重启和独立 matcher 页面也能从数据库恢复同一份结论，不依赖某个进程的临时列表。

已有比分、赛前参考价等附加数据可以继续按现有路径补充，但不能通过这些附加数据增加有效比赛或恢复失效盘口。实际保存字段与 DB 访问都归 @changmen/db；API 不直接执行 SQL。

## 具体修改集中在哪里

| 位置 | 要完成的工作 |
| --- | --- |
| matcher 的 compose 与保存链路 | 每轮产生完整的当前有效结果，并处理上轮保留但本轮未合出的记录 |
| @changmen/db | 在现有记录保存并读取 current_result，保证事务、缓存、重启和全空有效结果可正确处理 |
| Client_GetMatchs | 直接读取 matcher 已保存的当前结果；保留原响应形状，不再查询平台表过滤比赛 |
| matcher 数据组装与页面 | 当前比赛列表和计数读取同一结果；原始挂载只作诊断，不再由页面决定当前有效集合 |

不新增此前提出的“两个页面读取时共同清理”分支。有效性判断只在 matcher 的产出环节执行。

## Matcher 需要补上的两个缺口

**部分来源失效：** 已有比赛不能因不足两馆而整场跳过更新。matcher 要保留有效来源，重新产出其盘口，清掉当前结果中的失效平台 Source 和对应有效挂载；保持其它平台的主客方向、盘口 ID、地图和价格规则。原始绑定与人工反转意图仍保留。

**全部来源失效：** matcher 要显式写 visible=false。不能仅让本轮输出少一行、数据库却继续留下上轮可下发的结果；也不能把“本轮没合出来”一概当成比赛已结束。

来源恢复时，matcher 重新计算当前结果。原身份尚未 ended 时沿用该身份；已被现有生命周期标结束的记录不自动复活。本次保持现有真实结束、来源缺失结束兜底和身份分配规则，不承诺修复所有历史 ID 更替问题。

## 三步实施 每步完成都能停

### 第一步 补齐 matcher 产出与保存

完成 current_result 的兼容增量、matcher 计算、未合出旧记录的处理和事务保存。仅保存新版结果，用户接口和 matcher 页面暂时仍用旧路径，不提前切换任何一端。

完成标准：用离线和隔离测试证明两馆变一馆、全部来源消失、恢复、锁盘、读取失败、写入失败和成功空集合都有明确结果；旧身份与人工设置不丢失。写入失败不发布半份结果，读取失败不写假失效。新字段 SQL NULL 与 visible=false 可区分。

停在这里：新产出已具备，线上消费者仍用旧规则，原展示差异还可能存在。可以暂停，不需要立刻做第二步；兼容字段可保留，关闭新增写入即可撤回本步。

### 第二步 用户接口和 matcher 页面直接读取结果

两端一起切到 current_result。去掉平台存活的二次判定，以及清理后单来源又被页面“两馆门槛”隐藏的逻辑。ID/队名分类只作展示组织，完整当前集合不能因分类未知而丢失比赛。

切换前必须确认所有需下发的现存活跃记录已有新版计算结果，不能将 SQL NULL 当作无效而批量隐藏；旧版本写者停止或升级，切换期间只能由兼容写者更新结果。单纯 max(built_at) 变新不代表全部记录已补齐。新增读取失败不能变成成功空数组。

当前代码已有 RAY 风险比赛排除。保持该业务保护，由 matcher 的当前有效结果统一体现，不能因用户接口改成直接读结果而放开风险比赛；matcher 可以另列风险诊断。其它个人筛选、权限及附加行情仍保持既有职责。

完成标准：同一份已提交结果经过 API 后，与 matcher 当前列表的比赛 ID、有效挂载、盘口引用一致；API 保持原数组契约，不再访问平台快照判断有效性。列表减少时，待确认订单、补单、补绑、旧手动窗口和候选对象的兼容回归通过，不能只验证卡片消失。

停在这里：主要问题已解决，可长期使用现有轮询，不依赖第三步或新增推送。两端切换是一个完整交付，不能只切一端便宣布完成。

回滚方式：两端整体恢复原读取路径，暂停新增产出并保留附加字段。回滚不删除身份、批量恢复 ended、重建订单或清空补单；旧模式的偶发差异可能重新出现，应记录清楚。

### 第三步 实查并收尾

核对 matcher 成功提交的一轮结果、用户 API 响应和 matcher 当前列表。检查本对话两类案例，以及来源恢复、正常锁盘与服务重启。使用样本补足自然运行没出现的情况，不在生产主动制造采集或下单故障。

完成标准：相同已提交结果对应的完整比赛集合一致；双方刷新后没有持续差异；正常盘口、主客方向及已有订单处理没有回归。允许平台变化等待原有 matcher 周期和页面轮询后才反映，不要求两个浏览器在同一毫秒刷新。

停在这里：满足要求即结束本次修复。剩余差异按具体比赛定位，不默认扩展为推送、全量状态机或持续监控工程。

## 验收重点与范围限制

- 必须验证本轮未重新合出的旧记录也有明确当前结果，不能只清理本轮正常合出的比赛。
- 新 matcher 产出依赖的比赛、盘口、计时快照必须能区分读取失败和可信空结果；这是正确生成结果的必要条件，不独立扩成失败保护工程。
- 不复制原有错误读取路径作为新结果回退；保存失败时保留上次成功结果，读取新结果失败时明确失败，不能假成功空列表。
- 现有赔率缓存可以继续用于即时价格，但有效盘口引用只来自 matcher 当前结果；保留数据不代表继续展示失效盘口。
- 涉及真实退出列表的订单行为要有针对性回归，不因展示变化撤销已提交执行，也不向有效盘口新增拒单门控或手动准备要求。
- 不重写匹配阈值、主客算法或下单算法，不新增通知服务。读取端失败传播及历史身份问题中与本次接入无关的部分仍作为独立缺陷处理。

实现时按涉及模块选择行为、边界和 API 契约验证；修改前端必须运行 typecheck:frontend 或 app:build。文档中的历史审计测试结果不代替本次实施后的检查，不因历史任务默认执行无关专项。
