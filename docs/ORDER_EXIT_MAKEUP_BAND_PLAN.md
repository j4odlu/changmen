# 指定订单复用补单上下沿方案

[changmen 扩展] 2026-10-30。状态：未实施设计。按本轮用户澄清收窄为“把现有上下沿策略应用到指定订单”；不建设通用退出引擎。配套 [源码与设计审计](./audits/ORDER_EXIT_MAKEUP_BAND_AUDIT_20261030.md)。

## 1. 要做的事情

用户在一笔已有订单上点击“上下沿管理”，系统把这笔订单视作“已成的一腿”，在现有补单链路里寻找另一腿：

```text
指定已有订单 → 对应原赛事/盘口/方向 → 生成对侧补单任务
           → 现有上下沿判断 → 现有账号选择与预检
           → 现有下注、确认、绑单及出队
```

高于上沿就对冲锁利，处于带内就等，低于下沿就接受亏损对冲；对冲场馆不限 PM，范围是当前同一合场盘口里已经支持交易的场馆。不是增加一种新的入场策略，也不是搜索任意相关盘口。

原始 UI 范围保留：在未绑单、未结算的 PM 买单上增加入口，是否显示由扩展 tab 配置。已有其他场馆订单也可在转换信息完整时使用同一接入方式，但不因为算法通用就默认给所有订单开放。默认显示值为实施建议，尚未确认。

## 2. 直接复用什么

| 现有模块 | 直接复用的职责 |

不先抽象跨平台通用模块，不新增独立收益模型、自动卖出/买入路线比选、常驻服务、独立 RDS 计划表或全新的状态机。新任务只增加必要的来源和原单关联信息。

第一版建议沿用当前补单配置与开关，在启用界面明确展示“是否补单、上下沿模式与参数”；上下沿未开启时不把新任务悄悄降级为普通 `makeProfit` 策略。关闭现有补单开关后停止新补单，但已经受理的原单继续核对。原有自动补单及手动补单的默认行为不变。

## 3. 最小接入改动

### 3.1 把已有订单转换为补单任务

需取得：原单身份 `owner + provider + playerId + orderId`，现有 `matchId/betId`、已成方向、真实已成金额及赔率、原单对应账号。

- 从可靠的平台原始 ID、成交/提交关联及现有合场数据找回盘口上下文；不能仅凭比赛名称、盘口文案和 `Home/Away` 字面值猜测。
- `target` 是已成方向的对侧，不是照抄原订单方向。
- `betMoney/betOdds` 表示已成腿；补单金额继续由 `LoseOrder.getBetMoney()` 求出。金额按现有链路要求转成 Plan CNY，保留原币事实。
- 新任务标记为“指定订单上下沿”，保存原单身份。不能按现有 `isCreateOrder=true` 的手动补单创建，因为现有候选逻辑会跳过它的上下沿判断；新入口使用 band 管理语义，原手动入口不变。
- 原单未绑时，使用现有绑单协议为原单和新补单建立明确关联；不能直接把 hash/create_at 占位 Link 当成已确认的最终绑定。启用任务后即使原单不再显示未绑，任务仍按原单身份跟踪。

当前 [OrderRow](../client/web/src/types/order.ts) 并未提供完整的 `matchId/betId/target`，因此“能显示订单”不等于“必定能转换为补单任务”。找不到可靠映射的历史/外部订单显示不可用原因；这是接入需要补的证据，不要求为此新建整套映射系统。

### 3.2 避免覆盖和重复下单

现有队列以 `betId` 为键，同盘口第二笔任务会覆盖第一笔。最小版本建议：一个盘口同时只允许一个补单/上下沿任务；入队前检查冲突，不覆盖已有任务。同一原单重复点击只展示当前任务。这个限制必须在 UI 明示；若要求同盘口多笔原单同时独立管理，再单独做队列键改造，不在本期默认扩大范围。冲突检查覆盖统一入队入口及后续自动任务生产者，不能只在按钮检查一次；已有受理回执不能被替换或丢弃。

同盘口已有自动补单、原订单仍 pending、原 BUY 挂单还有未成交余量、订单已结算/已平仓、账号无归属或进入管理员预览时不能创建新任务。PM 首期优先支持未发生部分平仓、且真实成交成本与支付可核对的完整原单；部分平仓订单需要按剩余金额及实际支付换算后再开放，不能使用原始金额重复对冲。

任务存储沿用现有前端队列，并补充 owner 与原单关联的序列化/恢复校验；不是把订单列表或 sessionStorage 当作新的账本。换用户、切账号、恢复后必须重新验证原单及任务是否仍有效。第一版只允许一个活动页面管理此类任务，通过浏览器互斥及共享原单占用记录阻止另一个页面接管未决动作；不扩建跨设备协调。PM 已有 [提交日志](../client/packages/venue-browser/polymarket/submission/recovery/pmSubmitJournal.ts) 的 Web Locks 和持久未知单保护继续复用，但不能当作其他场馆也已有同样保护。

### 3.3 原仓位变化、暂停和收尾

在预检前和提交前重读原单，校验已成数量、已卖出数量、已有对冲及在途卖单；原仓位发生变化或事实不明时暂停该任务。任务持有期间，手动卖出与其他自动退出入口应检查同一原单的管理占用；不允许原单已被卖出仍按旧金额补单。

复用现有已受理原单的确认与恢复，受理不等于已完成对冲。刷新或请求超时后先续查原订单，不重新下注。用户取消或关掉开关，只停止后续新动作，不丢弃已受理回执。

指定订单任务离盘、取消或失败时应显示原因、保留原单可追踪性，不自动触发现有“套利失败自动卖出”作为额外动作；该行为属于原自动套利任务，应以来源标记分流。分流必须覆盖消费循环和 store 内手动取消、批量清理，不能只拦截一个回调。对冲完成后原单仍存在，展示“已对冲/锁定收益”，不能标记成“PM 已卖出”。

## 4. 沿用上下沿口径

原公式和参数继续使用：

```text
赔率系数模式：以已成腿的打平赔率 × 上下系数判断
总体利润率 = [min(已成腿返还, 补单腿返还) - 两腿总投入] / 两腿总投入
```

继续严格越界才触发，恰等于上下沿时等待。最高候选在带内时，不选择更差的候选制造止损。新入口仅允许可证明可计算的任务；数据不足时暂停，不借旧 `null → makeProfit` 回退悄悄离开用户选择的上下沿策略。旧调用方的兼容回退继续保留。

本期只比较“买入另一腿”的候选，因此不需要另建一个分母来混合排序原仓卖出与反向下注。界面沿用“补单后总体保底利润率”标签，不称为“原本金亏损率”。

例如原单成本 40，对冲再花 70，两侧最低返还 100，则净亏损 10、总体利润率约 -9.09%，不是原本金口径的 -25%。PM 费用、金额取整及实际到账份额要按已支持平台的真实支付复核；无法从真实成本与支付可靠转换成现有两腿输入时不启用，不能用提交限价倒算或将未知费用当零。未知费用也不能触发下沿。

只接受现有盘口映射下的严格互补结果。平局、加时、不同让分线、取消退款等规则必须对应；当前没有完整覆盖证据的玩法不开放。相同主客名称、相同 Link 不等于结算互补。

## 5. 原需求中的 PM 止盈挂单

“指定订单走上下沿反向对冲”和“PM 预挂止盈卖单”是两个动作。前者能大量复用现有补单代码；后者的 GTC SELL 支持仍需单独补齐，不因复用了 band 就自动具备。

保留用户原先要求的 PM 止盈卖单作为配套能力，不在本期增加卖出与各场馆对冲的通用自动比选。若同一原单已有本功能的止盈挂单，开始反向补单前先撤本单止盈单、核对期间成交、重算剩余敞口。无法确认撤单及剩余量时不发送补单。首期不支持部分平仓的任务如在撤单期间发生部分成交，暂停并显示原因，不能全额对冲。

止盈挂单目标仍按用户选择的盈利空间换算。其价格/利润口径独立明确展示，不直接把 PM 卖出收益率当作补单总体利润率。若只交付指定订单的上下沿对冲，不需要为它增加 PM FAK 卖出或买反边后自动合并能力；这不表示 PM 预挂止盈已经交付。

PM 官方允许等量 Yes/No 合并，说明卖本边与买互补边可有相同经济效果，但两种 API 操作及现金需求不同；买反边不应伪造为卖出记录。[官方持仓说明](https://docs.polymarket.com/concepts/positions-tokens)

## 6. 生命周期与最小交付顺序

- 前端运行、账号可用且补单开关开启时执行，关闭客户端后停止。session 内恢复沿用原队列能力，不承诺跨设备或后台持续监控。
- 原订单日期切换或侧栏过滤不代表取消任务；若当前合场盘口已经离盘，沿用现有可执行范围并明确显示暂停/结束原因，不为此增建历史行情服务。
- 扩展显示开关只隐藏新增入口，不自动删除任务；任务仍能在现有补单管理位置查看和取消。
- 第一阶段完成原单转换、入口与配置、冲突检查、来源及归属记录，接入现有 band/执行/确认/绑单流程。
- 第二阶段单独补齐 PM GTC SELL 止盈挂单及与该任务的撤单协调；不是第一阶段的直接复用部分。

工作量判断：第一阶段属于局部功能接入，已有完整盘口上下文的订单更容易；主要缺口在订单转换和防重复，不在重写上下沿。PM 止盈挂单是额外工作，不能把两块混成一个大型通用仓位项目，也不能把两块都估成“只加按钮”。当前没有实测工时，不承诺天数。

## 7. 审计与验收重点

| 范围 | 必须验证 |
| --- | --- |
| 原单转换 | 原单真实成本、赔率/支付、币种、反方向；找不到映射不猜；PM 原挂单余量及部分平仓不误接 |
| 现有上下沿 | 两模式、严格边界、带内等待、未知输入、新入口不回退 makeProfit；旧自动/手动补单与即时重试不变 |
| 任务隔离 | 同原单防重复、同 betId 不覆盖、已有自动任务冲突、来源/owner 序列化及恢复 |
| 原单变化 | 手动卖出、已有对冲、部分成交、换用户或账号变化导致暂停，不能继续按旧金额下注 |
| 提交确认 | 普通与 PM/PF pending 原单续查、刷新/超时、明确拒单、取消后仍确认已受理订单 |
| 绑单及入账 | 原单与新腿正确关联，收益只计一次；取消/离盘不误触发套利失败卖出 |
| PM 止盈配套 | GTC SELL、撤单期间成交、部分成交后不全额补单、停止入口与实际挂单状态分别展示 |

本次只形成方案和审计，不修改交易代码。后续实施按实际改动执行 `npm run check:change`；涉及前端至少类型检查或构建。纯文档不运行代码回归，不追加无关历史 FOK 专项。
