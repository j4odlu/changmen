# 下单进度的只读判定依据

[changmen 扩展] 本次实现范围是实时页面、后台诊断和精确证据查询。判定输出不作为下注、拒单、补单、余额或订单状态写入的输入。

## 数据与调用边界

- `packages/shared/order_progress_evidence.ts` 是纯函数模块，只接收事件和已按用户隔离的订单白名单。没有 HTTP、数据库、store、定时器或场馆调用。
- 原始观察协议仍为 v1，上传事件格式、队列重传、下注入口与订单写入路径不变。`ProgressProof` 是展示/诊断返回结构，不上传为观察事件。
- 每次判定复制事件与订单字段，保留事件原本的编号、来源和时间。RAY 旧记录不再转换成另一种来源的事件。
- 预检、提交、绑定及 PM delayed / RAY 已绑定拒单使用共享规则；其他平台沿用原有只读展示，并附上所用事件。
- 后台精确查询支持 `eventId`、`executionId`、`attemptId`。全部经过原有用户可见范围校验，SQL 参数化并限制用户；按事件查询时优先保留请求的事件，避免上下文截断丢失锚点。
- 判定依据保留在内部结构和后台查询返回中，页面不增加逐行展开依据的入口。

## 判定与时间

| 判断 | 直接依据 |
| --- | --- |
| 预检结果与赔率 | 当前检查的结果；再次开始检查后不引用旧结果 |
| 接口受理 / delayed | 当前尝试的提交回执 |
| 整轮拦截后的未提交 | 同用户、同 Link、同执行的预检结束记录；已有提交起点或返回时不覆盖实际提交证据 |
| 保存成功 | 当前尝试的绑定回执 |
| PM delayed 后订单状态 | 同用户、同执行、同尝试、同平台账号订单的回执，或唯一匹配的当前订单记录 |
| RAY 当前拒单补充判断 | 原编排事件、同尝试绑定回执、唯一匹配的当前订单记录 |
| 超时策略 | 本地策略事件；不升级为官方取消或拒单 |
| 补单队列 | 相应队列事件；出队不证明成交 |

当前订单记录在内部依据中与事件分开保留，不能借用历史事件的时间。订单记录未提供状态更新时间/历史版本时，阶段不显示虚构时间。事件接收时间缺失时，不虚构上传确认。

证据不足时显示缺口。合法的 RAY `none` 后续拒单更新保留原语义；PM 矛盾回执及 RAY 当前拒单与历史结算相矛盾时保留多项依据并提示核查。份额记录不额外解释为整笔成交。

## 验证

回归覆盖预检赔率隔离、重复检查、整轮预检失败、delayed 原订单关联、补单/重试隔离、当前状态未知时间、原事件不被改写、矛盾证据保留、字段白名单、用户授权及参数化查询。既有 `checkArbLegs`、`executeArbBet`、`betGatewayObservation` 和绑定测试用于验证业务路径兼容。

## 尚需独立实施的来源采集

本次没有给旧订单补造历史状态，也没有修改冻结的下注适配器。持久化订单状态变更历史、记录每次预检与提交的显式因果关系、采集实际请求发送边界、扩展部分成交数量协议，以及上传队列的持久性升级，仍需分别设计、兼容发布与验证。当前展示不会声称这些数据已经存在。
