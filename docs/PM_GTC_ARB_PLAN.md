### 1.4 FOK 隔离的验收口径

| 场景 | 有效执行模式 / 行为 |
| --- | --- |
| FOK，钱包未启用真实 GTC 协调且没有待恢复 GTC | 完整沿用原 FOK 路径，不新增 GTC 持久化、查询或等待依赖 |
| 当前占位版本选择 GTC | 实际仍 FOK，仅保存测试偏好和弹出提示 |
| 正式版本恢复旧的 GTC 测试偏好，尚未确认启用 | 明示“测试配置未激活，实际仍 FOK”；不自动升级为真实交易 |
| 正式 GTC 已确认启用且能力核验通过 | 仅自动套利首次 PM BUY 进入专用 GTC 路径 |
| 已确认启用 GTC，但构单、协调或恢复能力失效 | 阻断该次新 GTC，不静默改发 FOK |
| 同钱包已正式启用 GTC 协调，其他账号别名仍选择 FOK | 后续跨模式协调设计，当前未交付；当前 GTC V1 在预留前拒绝同用户多别名 |
| 钱包有未解决真实 GTC，用户切回 FOK | 当前旧 GTC 继续核对、取消及人工接管，FOK 仍原路径；跨模式自动发送互斥未接入 |

后两项按最新“FOK 不受任何影响”约束调整了本次实施范围。GTC 间的独立钱包锁不能约束原 FOK、手动或外部交易并发；需要此保证时须另行实现共享授权，而不能把它描述为已有能力。下文相关共享协调要求仍是后续设计。

## 2. 首期业务语义与首次双腿执行

### 2.1 三种状态分别保存

| 维度 | 回答的问题 | 例子 |
| --- | --- | --- |
| PM 原单进度 | 实际成交多少，余量是否仍有效？ | 零成交挂单、部分成交挂单、全量成交、部分成交后撤单、待核实 |
| 双腿结果 | 两条腿是否完成原计划？ | 首轮执行中、两腿完成、套利未完成、结果待核实 |
| 操作责任 | 后续交易由谁决定？ | 首轮自动执行、人工接管、人工恢复待核验 |

单独 success 布尔值不能表达以上状态。若兼容旧返回值而将部分成交表示为 success=true，必须同时携带实际量、是否全量、人工接管标识及 GTC 来源，并由所有消费者识别。不能只改 success，再增加一次 toast。

### 2.2 状态与处理表

| PM 事实 | 本腿展示 | 首期处理 |
| --- | --- | --- |
| 明确受理、零成交、live/delayed | 已挂单 / 待撮合，尚未成交 | 持续核对，首轮结束后交人工；不计入实际成交金额 |
| 有可靠撮合证据、部分成交、余量有效 | 已部分成交 · 挂单中 | 按实际量认定已有成交，提示人工；不按整笔失败重试 |
| PM 全量成交，另一腿按原规则完成 | 全部成交 | 无未核实结果或影响完成的拒单事件时，整组可显示两腿完成 |
| PM 全量成交，另一腿失败、未提交或未知 | PM 全部成交，套利未完成 / 待核实 | 整组转人工，不自动补另一腿或卖出 PM |
| 部分成交后余量明确撤销 | 部分成交 · 余量已撤销 | 保留实际成交，未完成部分交人工，不自动补回 |
| 明确拒绝或明确终止且零成交 | 未成交 / 下单失败 | 按事实展示；该 GTC 执行不进入旧自动恢复路径，另一腿已有结果仍需核对 |
| POST 超时、ACK 无效、是否受理不明 | 提交结果待核实 | 查询原尝试，保留身份与阻断；禁止自动重发或另签新单 |
| 明细缺失、查询失败、数量矛盾、FAILED | 成交 / 订单状态待核实 | 保留已核实事实及缺失证据，不把未知当作零成交 |

MATCHED 延续现有业务撮合口径，不新增等待全部链上 CONFIRMED 才显示“已有成交”的门槛；同时展示确认进度，永久 FAILED 需要核对并修正事实。

### 2.3 首次两腿的明确选择

保留现有串行 / 并行设置和首轮目标数量，V1 不增加根据部分成交动态缩量、换方向或追单策略。双方最终准备须在任一腿发送前完成。

- **串行，PM 为第一腿：** 有可靠部分或全部撮合证据时，可继续一次原计划的第二腿；仅受理且零成交、或 PM 提交未知时，不据此提交尚未发出的第二腿。不能无限等待 PM 全量成交，结束首轮并转人工。
- **串行，PM 为第二腿：** 第一腿按原流程满足继续条件后，提交一次 PM 原单；PM 未全量完成则整组转人工。
- **并行：** 两个首次请求按原设置提交，分别核对；不得将已在途的另一腿描述为已取消。
- **首轮结束后：** 任一腿部分成交、有效挂单、失败、未提交或未知，即转人工；两腿都完成时按原业务核验结束。后续 RAY 等发现另一腿拒单时，同一执行也转人工。

用户在首轮执行期间先请求“取消PM挂单”时，保存撤单意图并将整组转人工；尚未进入发送授权的第二腿不再提交。已授权或已在途的请求继续核验，不能宣称用户撤单已撤回这些请求。发送授权须检查最新撤单意图，不能继续消费撤单前缓存的成功结果。

PM 第一腿部分成交后，第二腿仍按原计划全量提交，可能形成敞口。这是 V1 保留首轮执行方式的明确取舍，不是“部分成交即可保证套利”。只有首次第二腿属于上述允许动作；即时 retry、换账号再试、补单和自动卖出都不属于首次第二腿。

例：不计费用，PM 计划 100 份、单价 0.40；另一腿成本 50、获胜返还 100。全量完成时成本 90、任一结果盈利 10。若 PM 仅成交 60 份、花费 24，另一腿全量完成，则 PM 获胜时收益为 60−74=−14，另一结果为 100−74=26。页面显示套利未完成，余量交用户决定。

### 2.4 人工接管的范围

GTC 来源从首次发送前即确定，自动恢复抑制不能等卡片渲染后才生效。转人工后，以 executionId / link 为范围持续禁止：

- 即时失败腿 retry、anyOdds 换腿及更换账号再次下单；
- LoseOrder 补单、pending 结果恢复后入队、RAY 延迟拒单自动补单；
- arbFailAutoSell、补单放弃或取消路径触发的自动减仓；
- 下一轮扫描为同一未解决执行创建新订单；
- 用户手动卖出后，系统为恢复原计划数量自动买回。

已有请求和原单继续核对。限制只作用于 GTC 来源执行，不能全局关闭普通 FOK 原有扩展。后续到账、刷新、切回 FOK 或迟到事件，都不能解除人工责任并重开旧执行。

尤其是 PM 第一腿初次零成交、首轮已经结束并转人工后，稍后首次 maker 成交也只更新原单事实，不重新提交尚未下单的第二腿；后来 PM 全量成交同样不能绕过接管状态。第 2.3 节允许继续一次第二腿，只适用于首轮仍在执行且未被撤单意图或人工接管阻断的情况。

### 2.5 首轮决策只发生一次

保存固定 `originalLegId`，按首次准备绑定场馆、目标侧和账号。现有 placeArbLegs 会依据成功结果交换 A/B 展示位置，不能用可交换的 A/B 判断“原 PM 第一腿”、第二腿是否已发或撤单对象。

串行 PM 第一腿的初次结果按以下顺序收口：

1. 初次事实核验上限暂定 10 秒，自 PM 首次发送授权起计算并持久保存期限；只限制首轮是否继续，不代表订单有效期、撤单期限或最终核验完成。现有 `waitSec` 是提示 / 拒单等待参数，不直接当作 GTC 决策时钟。实施时按支持路由验证该上限，失效或超时转人工。
2. 已明确受理且当前零成交 / delayed 时，立即结束本轮并转人工，不另设等待 maker 成交的窗口。ACK 有撮合线索但实际量尚不可靠时，只核验该次提交已有证据；不能无限等待。
3. 在期限内取得本单可靠正成交量，且尚未收口、没有撤单 / 人工意图时，允许一次原计划第二腿授权。授权同时校验冻结准备仍有效及自动开关未关闭；准备失效则转人工，不重新拉簿、改价或重新签另一目标。
4. 第二腿授权、首轮收口、撤单意图之间采用服务端原子状态检查。授权记录绑定固定腿和 attempt；WS、轮询、刷新、两个设备同时处理同一成交，都不能再次获得第二腿授权。
5. 收口后迟到证据只修订订单与整组事实，不再执行首次第二腿。已授权但回执丢失的第二腿按原尝试恢复核验，不能按“未看到结果”再次提交。

部分成交提示可立即出现，责任文案须区分“首轮仍在执行，第二腿待核验”与“首轮结束，已转人工”，不能一边宣称全部交人工、一边启动尚未授权的交易。零成交已受理不占实际成交次数；首笔可靠成交按原单幂等计一次，后续 trade 不增加下注次数。

### 2.6 GTC 结果不能直接复用完整成功的副作用

GTC 专用结果至少携带：是否受理（含未知）、固定腿 / attempt 身份、实际撮合量、是否全量、余量及其可信度、首轮决策状态、人工责任和事实版本。受理、已有撮合、结算确认、整组完成分别判断；`not_attempted`、明确失败、在途和未知不能合并成零成交失败。

| 消费者 | GTC 的 V1 行为 |
| --- | --- |
| 双腿 place / settle / finalize | 只按第 2.5 节授权首次第二腿；整组完成须两腿独立核验 |
| 即时 retry / LoseOrder / pending 恢复 / RAY | 接入执行来源与持久人工责任，保留检测，禁止重新下单与减仓 |
| PM 乐观订单保存 | 进入实际事实保存分支，不让计划金额或 FOK 整笔默认值覆盖部分成交 |
| 次数、限额、lastOdds 等成功标记 | 区分发送占用与实际成交；逐项明确更新条件，同单增量不可反复触发 |
| Publisher 的传统 Betting 广播 | V1 不为 GTC 发布该交易指令；不能用计划金额广播部分成交，也不能每次增量驱动跟单 |

当前 publishBettingEvent 使用 option 的计划 betMoney / odds，协议没有累计成交、修订或去重身份。GTC 挂单增量若直接复用，可能让订阅端重复跟单。因此 V1 的 GTC 执行不参与传统 Publisher 下单广播，并在配置说明中明确；普通 FOK 广播保持原样。若后续需要 GTC 跟单，另行设计并验收累计事实与指令幂等协议。

## 3. 模式配置与 GTC 正确构单

### 3.1 模式配置

沿用扩展 Tab 的现有“PM 自动套利下单模式”，正式版本更新说明与 GTC 文案，不再增加第二套模式配置：

| 选项 | 提示 | 默认 |
| --- | --- | --- |
| FOK | 全部成交或不成交，沿用当前流程 | 是 |
| GTC | 仍需全量盘口预检；余量继续挂单，未完成时交用户处理 | 否 |

沿用配置保存接口。新执行冻结模式、来源、账号、钱包、方向、价格、数量和路由；已有 GTC 不因配置修改变成 FOK，也不自动撤销。

环境不支持持久恢复、最小互斥、事实查询或正确构单时阻断新 GTC，显示原因，不静默降级为 FOK。普通 FOK 保持原路径。

**测试偏好与正式启用分开。** 正式版本须在现有配置流程中让用户明确确认：将真实提交 GTC、部分成交仍有组合敞口、零成交也可能留下有效挂单、V1 不自动补单 / 平仓，且 GTC 不参加传统 Publisher 广播。保存 owner、策略版本与确认时间，不能从 pmArbOrderMode=GTC 自动生成确认；不在订单栏新增激活或恢复按钮。

用户切回 FOK 后，重新选择真实 GTC 须再次确认；旧执行按冻结来源处理。当前占位版本不新增上述确认字段或任何交易门控。客户端 / 服务端缺少正式版本能力时，不得仅凭已保存字符串启用 GTC；已确认启用的请求失败也不回退为另一模式重发。

正式启用同时建立钱包协调范围，向用户说明同钱包自动入口的影响。只有在没有未知 / 活跃 GTC、旧执行已完成恢复核验、相关在途请求已收口后，才能退出协调并回到普通 FOK 原入口；不能仅改某个账号的字符串就解除共享约束。

### 3.2 数量、预算与共享预检

审计时安装 SDK 为 @polymarket/clob-client-v2 1.2.0：现有 FOK 使用 buildMarketOrder()，BUY amount 为名义金额；GTC 使用 buildOrder() 的 price / size，发送 orderType=GTC、postOnly=false。实施时复核实际安装版本，不直接套用官方新 unified SDK 示例。

保留原盘口获取、允许价格、全量深度、缓冲、余额、tick 和最小量检查。共享预检后增加最终数量与收益复核，不在发送前另拉簿或改价。共享预检相同不表示最终 GTC 准备必然成功。

保存原目标份额 Q_target、下注本金 B、冻结限价 L、预检量 Q_checked 及实际签出的金额 / 数量。使用十进制串或定点整数，最终编码满足：

    0 < Q <= Q_target
    Q <= Q_checked
    最终签名名义金额 <= B

按合法精度向下取整，不增加目标或本金；签名域、钱包、协议、tick 和最小量须匹配。未知兑付单位或不能证明最终量时准备失败。费用不参与份数计算、准备门控或发送前收益判断，取整差额可见，不强行补齐。历史 `allInBudget` 字段仅为持久化兼容保留，新单值等于下注本金上限。

### 3.3 首次双腿收益复核

固定份额 GTC 与金额型 FOK 的实际返还不同。最终数量和成本复核属于首期订单正确性，不能由“用户负责余量”替代。

任一腿 POST 前，用最终份额、每份兑付 V、另一腿冻结准备及统一估值币种计算：

    PM 预计返还 = Q × V
    PM 最大成本 = 最终名义最大支付（不计费用）
    最差净收益 = min(PM 预计返还, 另一腿冻结返还下界)
                 - (PM 最大成本 + 另一腿冻结成本上界)

按原初次套利收益门槛判断，不套用补单止损规则。失败时两腿均不提交，不增加 PM 金额或调整另一腿。该复核描述按准备边界完整执行时的收益，不保证实际两腿都成交。

审计构造例：另一腿成本 100、返还 204；PM B=100、L=0.51、快照价 0.49，Q=196.07。金额型估值净收益为 4，但固定份额即使全按 0.49 成交，最差净收益为 −0.0043，按限价成本上界更差，应阻断首次提交。

## 4. orderId、tradeId 与成交账本

### 4.1 一笔原单，多次成交

**同一笔 GTC 原单的 orderId 保持不变；后续新增撮合可产生更多关联 tradeId。订单栏持续更新同一条 PM 主记录。**

| 示例过程 | orderId | 新增 tradeId | 累计撮合量 | 尚未撮合量 |
| --- | --- | --- | --- | --- |
| 挂单 100 份 | O1 | 无 | 0 | 100 |
| 成交 30 份 | O1 | T1 | 30 | 70 |
| 再成交 20 份 | O1 | T2 | 50 | 50 |
| 再成交 50 份 | O1 | T3 | 100 | 0 |

示例不表示一次消息或撮合必然只对应一个结算明细。撤单后重新创建的订单有新的身份，不能覆盖 O1；原单成交仍归 O1。

一条 trade 可涉及多个 maker order，tradeId 不是订单主键。成交明细关联自己的 orderId，并保留官方 bucket / 明细标识，避免错误合并或重复累加。

### 4.2 去重与角色

- 同 tradeId 的 MATCHED、MINED、CONFIRMED 等更新修订同一事实，不算再次下注，不重复增加数量。
- maker 只读取 maker_orders 中精确 order_id 对应的 matched_amount、价格和角色，不能取整笔 trade.size 兜底。
- taker 也核对本单身份、资产、方向和实际量；立即 taker 与随后 maker 均归原单。
- order.size_matched 为累计核对锚点，不能再与 trade 明细相加。
- 永久 FAILED、费用更正或矛盾进入核验；核实修正可减少聚合数量 / 成本并记录原因，不能永久取 max。

### 4.3 最小事实字段

| 字段组 | 保存内容 |
| --- | --- |
| 执行身份 | owner、executionId、link、attemptId、模式、固定原始腿及人工责任 |
| 官方订单身份 | accountId、真实钱包 / 链 / 资产、orderHash、orderId、condition / token、方向 |
| 计划与签单 | 目标量、签单量、限价、最大支付、冻结准备及取整残差 |
| 成交明细 | tradeId、bucket / 明细标识、本单关联、角色、量、价、费、结算状态 |
| 聚合进度 | 已核实撮合量、确认量、失败 / 待核实量、尚未撮合量、有效挂单余量、实际累计支出 |
| 核验与恢复 | 官方状态、终止证据、完整性、observedAt、factsRevision、提交状态、首轮期限 / 收口 / 授权、撤单意图 / commandId / 核验阶段与阻断原因 |

原单按官方身份域（链 / 协议 / 官方 owner 或认证域 / 真实 maker / orderId）唯一 upsert，绑定业务 owner；accountId 是关联与展示属性，不能因同钱包存在两个账号别名生成两份原单事实。资金门控使用第 7.2 节资金身份，两个身份键用途不同。其它同 token 订单或外部持仓不能算入原单。新 UUID / bigint 按字符串传输，避免 Number 精度损失。

最小执行记录还须保存固定腿身份、首次第二腿授权 / 收口状态、决策期限、人工责任生效版本、实际成交计次标记，以及自动恢复确认。展示行换序不能改变这些事实。

### 4.4 初次零成交与纯 maker 成交路径

**初次零成交且已确认挂簿时，全部未成交数量都是本原单的挂单余量；后来被其它主动订单吃掉时，本单以 maker 身份成交。** 不需要另建 maker 订单，不切换 orderId，也不重新签名或提交。

| 原单路径 | 实际成交角色 | 处理 |
| --- | --- | --- |
| 初次零成交，确认 live 挂簿，后续被吃单 | 后续成交为 maker | 原单从 0 更新为部分 / 全量成交，逐条取本单 maker 明细 |
| 初次吃掉一部分已有流动性，余量挂簿再被吃 | 前段 taker，后段 maker | 两种角色按真实量、价、费共同累计到同一原单 |
| 初次无成交但仍处于 delayed | 尚不能确定全部为 maker | 延迟结束仍可能先吃单为 taker，只有实际挂簿后被吃的量按 maker |

GTC 配置本身不保证 maker，方案仍采用 postOnly=false；角色由各次真实撮合决定。没有初始 tradeId、回执 tradeIDs 为空或一次查询为零，也不等于原单拒绝或终止。

零成交已受理时必须立即建立可恢复的原单进度记录并按 orderId 跟踪，不能等出现首条 taker trade 才开始监控。maker 成交里 taker_order_id 通常属于对方订单，本单从 maker_orders.order_id 定位并读取 matched_amount；只按 taker_order_id 过滤会漏掉纯 maker 成交。

纯 maker 也按实际份额与价格更新本金，不能因没有初次成交金额或 maker 合法零手续费跳过保存。按当前官方费用规则，maker 不收成交手续费；只有角色及适用规则已核实才记合法零费，缺失证据仍标待核实。下注前不预留费用，新单在核对本单 taker 成交时查询费用；后续 rebate 不抵扣尚未核实成本。

示例：O1 买 100 份，初次 0 成交且 live；后来 T1 中 O1 的 maker 明细为 30 份，再后来 T2 为 70 份。原单显示 0→30→100，成本按两次实际价格累计；若首轮已转人工，第二腿仍由用户处理，系统不因新增成交自动恢复交易。

## 5. 订单栏持续更新与人工提示

### 5.1 同一行随事实更新

保留双腿分组、时间和原操作布局。PM 行下增加“PM 挂单进度”卡片，优先使用既有 row-actions 插槽；普通 FOK 无新数据时不占高度，RAY 卡片位置不变。

零成交已受理单也必须可访问，但计划 / 预留金额不能计入实际成交支出。新增 trade 更新原单的实际量、金额、均价和余量，不新建重复业务订单，不重复累计下注次数。

    PM 挂单进度                         部分成交 · 挂单中
    已成交 60 / 100 份，挂单剩余 40 份
    实际成交金额：…   实际均价：…   最后核验：…
    套利未完成，已转人工处理；剩余挂单仍可能成交。
    [取消PM挂单]
    仅撤销本单未成交余量；保留已成交，撤单后不会自动补单。

首期只新增“取消PM挂单”一个按钮，不新增“取消补单”或自动补单候选。已有手动卖出入口保留；卖出不会自动撤销买单余量，须明确提示。其它人工处理可在官方界面进行，系统继续同步原单。

### 5.2 展示口径

| 字段 | 展示口径 |
| --- | --- |
| 目标 / 原单总量 | 冻结计划与签单量分别保存，取整差异可查看 |
| 已成交量 | 有可靠撮合证据的本单累计量；确认中 / 已确认 / 异常分别注明 |
| 挂单剩余量 | 仍有效的官方余量；不能核实时显示待核实 |
| 未完成量 | 尚未撮合数量；撤销后不能继续显示为有效挂单 |
| 实际金额 / 均价 | 实际支出及加权价格，不用计划金额或限价冒充 |
| 费用 | 已知值、可信估值或待核实；合法零与请求失败分开 |
| 整组状态 | 两腿完成、套利未完成或待核实；PM 全量不单独决定整组完成 |
| 更新时间 | 最近成功核验时间；查询失败显示同步异常及旧事实时间 |

成交 30 / 100 后撤余量，应显示“已成交 30，未完成 70，挂单剩余 0，余量已撤销”，不能显示整笔失败或全部成交。尚未撮合量与有效挂单余量是两个字段。

真实原币事实另存，展示估值采用明确汇率快照。费用未核实不显示全成本精确值，收益未核实不显示保证盈利；限价与实际均价分开。

### 5.3 提示与可访问性

首次部分成交或需接管时发一次明确通知，订单行保留持续提示，不能只有 toast。通知按执行与事件去重，后续正常增量不反复提醒成新下注。

新增最小“活跃 / 待核实 PM 订单”入口，覆盖跨日、筛选隐藏、比赛离盘、零成交及 POST 未知无官方单号。长单号可完整查看，窄屏不溢出。

无 orderId 时以 attemptId / 经验证 orderHash 展示，不伪造已受理单。卡片折叠、行卸载和筛选不停止监控。

后续全量成交可更新 PM 本腿；人工责任不因此自动解除。两腿后续都核实完成可更新整组状态，但不能重开旧执行的 retry 或补单。

### 5.4 唯一新增按钮：取消PM挂单

**操作范围为当前 PM 行绑定的精确原单，仅撤未成交余量。** 不撤账号其它订单，不撤另一腿，不卖出已成交仓位，不自动补剩余差额，也不停止订单事实监控。

按钮在 GTC 进度卡片中直接可见，无需展开。已知 orderId、归属核实且尚无可靠终态时允许精确撤单，包括当前余量待核实；不能因为轮询暂时失败或余量缓存过期就使用户无法尝试撤单。余量未知时说明“剩余量待核实，撤单后继续核对”。全量、明确已撤、可靠无余量时禁用并说明原因。无官方单号、订单归属未核实或凭据不可用时禁用，不按时间、金额猜测撤单对象。官方明确当前 delayed 阶段不可撤时显示该原因，允许阶段变化后重试。

1. 校验用户、账号、真实钱包与 orderId 归属，固定 attemptId / 原单；持久保存本单撤单意图及整组人工责任后调用精确撤单接口。保存失败显示“撤单请求未保存”，不宣称已撤。
2. 点击后进入“撤单中 / 撤单待核对”，同单请求去重，重复点击不产生补单或新订单。用户请求立即阻断尚未授权的首次第二腿，已授权请求按第 2.3 节核对。
3. 检查回执中的本单 canceled / not_canceled，并补查原单及关联成交。HTTP 200、查空、404、缺席开放单列表不能单独证明余量终止。
4. 撤单期间新成交仍记入同一 orderId，更新实际量、金额和费用。确认余量终止后显示“余量已撤销”；若竞争中已全量成交，显示“已全部成交，无挂单可撤”，不伪称撤销了成交。
5. 撤单结果与成交核验分别展示。余量确认终止但明细或金额尚不完整时，显示“余量已撤销，成交待核实”，保留恢复与自动运行约束。
6. not_canceled、超时、查询失败或官方当前延迟阶段不可撤时，显示原因并继续核对，不能乐观清零余量。允许条件恢复后用户重试；不盲目全账号撤单或自动追单。

撤单意图持久保存，刷新或换设备后仍能看到待核对结果；原单再次确认有效时提示重试，不静默丢弃意图。重复操作须返回同一原单当前结果，不能用新 attempt 代替撤单。

撤单核实成功后仍按原人工接管规则处理未完成组合。零成交撤单不等于整组无风险；另一腿可能已有成交。不能直接复用带自动卖出副作用的 cancelMakeupManually，也不能在撤单成功回调中触发 retry、LoseOrder、RAY 补单或 arbFailAutoSell。

撤单 command 与 BUY attempt 分开保存：一个 command 不重复派发；用户对明确失败 / 仍有效的原单重试可生成新 command，但始终绑定相同 orderId。撤单响应丢失时先核对原单；仍有效且用户再次请求时可重试精确 CANCEL，禁止的自动重发 BUY 规则不应变成永久禁止用户撤单。

## 6. 持续核验、增量保存与恢复

### 6.1 独立 GTC 进度路径

GTC 不复用 FOK 的整笔终态 watcher 与挂单超时撤销政策。不能因原 FOK grace 超时撤 GTC，也不能把部分成交解释为拒单而追单。

发单前准备用户 WS，受理后由 store / service 管理进度。默认每 5 秒补查活跃原单，同单单飞、同账号共享成交发现，网络失败退避；5 秒为拟定调度值，不是最终一致性或订单超时保证。

同账号增量窗口 / 游标保留重叠去重，已知 tradeId 精确补查。查询须表达 items、nextCursor、complete、truncated、observedAt 及错误。页数上限、重复游标、异常空页或字段缺失不能伪装为完整无成交。

可用完整本单关联 ID、明细及官方累计量一致证明已核对，无需每次扫整个账号历史。WS 不替代 REST 恢复，固定等待或两次相同值不证明最终状态。

### 6.2 实际记账随成交更新

GTC 增加按来源 / factsRevision 区分的保存分支。审计复现零手续费成交 60→100 时，现有函数更新份额与 pmStakeUsdc，却保留首次 bet_money；此为 V1 必须处理的记账缺口。

- 累计份额、实际名义支出、费用与展示金额同步更新，合法零费也允许更新成本。
- 计划、最大支付、挂单预留另存，不计为已成交金额。
- 订单累计快照与 trade 明细不能双重累加。
- 有效更高版本修订聚合；迟到旧快照不得倒退，核实更正可按原因减少错误值。
- RDS 事实、聚合和展示金额一致保存；失败显示未同步并保留阻断，不能只更新卡片宣称完成。
- 旧 PM / FOK 同步不得覆盖 GTC 版本化聚合；缺版本写入按明确兼容策略补缺或待核验。

买入累计与卖出 / 净持仓分开。卖出不减少历史买入量，也不能继续把全部买入量显示成可卖量；无法归因的外部卖出标仓位待核实，不猜成本或自动买回。首期不建设自动对冲的完整仓位分摊账本。

### 6.3 事实版本与冲突处理

factsRevision 由持久化层在校验并合并新证据后递增，客户端提交的是基准版本与证据，不是“数字更大即可覆盖”的权威聚合。observedAt 只表示采集时间，响应晚到不代表官方事实更新；同一原单两个设备、WS 和 REST 必须进入同一合并规则。

- 单个成交按官方身份域 + tradeId + bucket / 稳定明细标识 + 本单 orderId 去重，不使用 maker 数组下标作永久身份；缺必要字段时标不完整，不制造新明细凑金额。
- 已核实新成交补入账本；同明细状态或费用变化修订原事实。旧 MATCHED 回放不能覆盖已核实的永久 FAILED；矛盾保留双方证据并再次核对。
- 官方累计撮合量、明细合计与结算状态分别保存。累计量较大但明细不足时可展示该累计量来源，成本标待核实，不用限价补造实际成本；确认矛盾不能凭取 max 消失。
- 终态与成交完整性分别判断。撤销后仍可收到撤销之前产生的成交明细，但不会据此恢复挂单、重新授权第二腿或解除人工责任。
- 身份、事实、聚合与版本同事务更新；旧保存入口不得跨版本覆盖 GTC 事实，拒绝后应重新读取并合并，不能把旧聚合改成更大版本重传。

### 6.4 生命周期与恢复

| 事件 | V1 行为 |
| --- | --- |
| 自动套利关闭 / 账号暂停 | 不发新自动单；原单继续核对，不默认撤销 |
| 配置改 FOK | 只影响允许创建的新执行，旧 GTC 按原身份跟踪 |
| 刷新 / 登录 / 另一设备登录 | 先恢复活跃、未知与人工记录，再查官方；恢复前不开放相关自动执行 |
| 关页 / 登出 | 客户端停运行，官方单仍可成交；持久保存资料，不承诺后台监控 / 通知 |
| 断线重连 | 补查原单及近期成交，恢复增量处理 |
| 比赛离盘 / 市场结束 | 保留原单和接管记录，不用旧 prune 删除，不发自动补单 |
| 删除账号 / 换钱包 / 凭据失效 | 保留原身份及恢复入口，不转移到新钱包或猜终态 |
| 手动撤单 / 卖出 / 外部变化 | 更新可核实事实，保留人工责任，不追单或买回 |
| 点击取消PM挂单后刷新 / 撤单响应丢失 | 恢复原单撤单意图及核验阶段，查询真实余量，不伪报成功或释放未知 |

终止原单仍有未确认成交时继续核对。原单无余量不表示整组完成；人工处置与自动运行恢复分别判断。

## 7. 首期最小持久化、防重复与自动运行约束

### 7.1 可以后移的协调能力

V1 不建设自动 GapTask、候选版本、补单调度、多端执行租约及完整 Reserve / ReconcileFunds 协议。人工接管替代后续交易能力，不替代首次发单身份、提交未知记录和持久恢复。

复用现有订单与数据层，增加最小 GTC 执行 / 尝试状态即可。现有表可选字段或独立关联表由实施确定，不预设重构整个模型。RDS 为关键记录真相源，本地存储只作发送身份与恢复辅助。

### 7.2 首次提交的最小原子门控

1. 任一首次腿发出前，保存 executionId、冻结双腿准备、钱包、attemptId 与来源，服务端校验归属。
2. 按 executionId 原子创建及更新独立执行；钱包身份用于归属校验，不互斥不同原单。
3. PM 发送前记录不可变签单 hash / 量 / 模式及 dispatching，只授予原 attempt 一次发送。失败不发；授权回执丢失先读状态，不重新 POST。
4. 原单的有效挂单、delayed、dispatching、提交未知或恢复未完成只限制该执行的重复发送，不阻止新 ID 的独立执行。
5. ACK / 保存失败、运输超时、查空、404 保留未知，不能另签、重发或超时释放。只有明确未发送、拒绝或可靠终态才修订状态。

本系统按原执行 ID 记录在途、未知与恢复事实。单次授权和对应原单绑定，创建另一组不修改既有执行，也不重新授权原单；同钱包在途记录不是新执行的禁止条件。

这是首次执行的持久门控，不是 V3 任务租约。localStorage、异步配置保存、单页面约定或 TTL 到期不能替代原子检查。DB 不可用时阻断新 GTC，原单保留可核实事实及同步错误。

签单 hash 精确查询能力须按钱包 / 协议 / 路由实证，无法定位时保留未知与人工恢复，不按时间、金额猜订单。不将私钥、API secret 或完整签名存入通用日志。

### 7.3 新执行与原单核对独立（2026-10-10 用户修正）

同钱包允许多组独立 GTC 执行。旧组的挂单、未知提交、人工接管及核对状态不阻止新套利；参数保存不要求先恢复旧组。本组原单及第二腿仍按自身授权和身份处理，不因新单重放旧组。

首次双腿仍执行原余额 / 限额检查与第 3 节本金预算证明。不以原单待处理代替新订单自身的余额、金额和账号规则检查，不声称提供精确多订单资金分配。

显式手动买卖保留原入口及余额 / 限额检查，提示有效 / 未知 GTC 与余量可继续成交；不自动代用户撤余量。不保证手动、官网或第三方并发资金原子分配。已知外部变化使相关余额 / 仓位证据失效并触发核对。

正常双腿全量成交并完成既有核验、未曾进入人工接管时，可结束执行并释放门控，后续自动运行无需额外人工恢复；不能仅凭 PM 全量或另一腿受理判定这个条件。

人工接管继续约束原组，不要求用户先核实或释放原组才能进行新的独立套利。另一腿“已核验”可为未提交、明确失败或实际成交，不要求补成原计划。

| 原组的事实 | 新独立自动执行 |
| --- | --- |
| 仍有有效原单、未知提交 / 在途、成交或金额矛盾 | 原组继续核对，不按此事实阻止新组 |
| 两腿全量完成、核验完整 | 原组记录完成，新组独立执行 |
| 组合未完成或保留持仓 | 原组显示实际状态，新组无需恢复原组确认 |

原组永久保留禁止自动补单 / 重试标识。余量终止、切换模式或新建订单不清除原组未知状态；参数保存也不改变原组事实与责任。

迟到拒单、FAILED 或费用修订只更新对应原单并继续核对，不阻断整个钱包新自动执行，不撤其它原单、重试旧组或自动卖出。

### 7.4 最小接口责任

| 逻辑操作 | 必须提供的保证 |
| --- | --- |
| 建立执行 / 首次发送 | owner、钱包原子门控、执行与 attempt 幂等、不可变身份、一次发送 |
| 保存 ACK / 订单 / 成交 | 身份与版本、实际金额一致持久，迟到事实不解除人工责任 |
| 保存撤单意图 / 精确撤单 / 核验 | 原单归属、意图持久、阻断未授权第二腿、同单幂等、回执与竞争成交核对；无补单副作用 |
| 读取恢复 | 不依赖比赛 / 日期，包含无 orderId、零成交、活跃、撤单待核对与人工记录 |
| 核验 / 恢复自动运行 | 终态及在途核验、余额新鲜度、人工恢复意图，不重复旧执行 |

以上为拟实施逻辑契约，不是现有 API 名称。服务端不跑套利策略、不常驻监控；直连和 VPS 均遵守最小身份及门控。

### 9.2 开放条件

首期需支持 SDK / 钱包 / 协议 / 路由的构单证据，可靠订单与成交查询，实际累计保存，钱包门控，未知恢复，精确撤单与竞争核验，自动恢复抑制，持续提示及跨日恢复的验证。首轮期限、固定腿身份、正式确认、广播隔离及人工恢复同时通过 V1-T31–T40，不能只验收 POST 和 UI。

普通 FOK 相关回归须通过。改前端后跑 typecheck:frontend 或 app:build，vitest 不替代 vue-tsc；运行匹配改动的 PM、双腿、RAY 接入、保存、门控、恢复及 check:boundaries。触及冻结 PM 路径时按确定范围显式放行，不修改冻结清单。

客户端与服务端共同核验能力，失效阻断新 GTC，保留旧单及恢复资料。生产真实订单 / 余额口径受控验证；本文修订不授权本轮真实下注或撤单。

开放按已验证的钱包 / 协议 / 认证读写范围 / 路由限定，不默认所有现有 PM 账号均支持。查询凭据须能读取本次发出的原单与成交；仅能提交但无法恢复或精确撤单的组合不开放。出现重复授权、计划金额覆盖实投或绕过人工责任时，关闭新 GTC 授权并继续核对旧单；关闭能力不自动撤单、卖出或清除记录。

## 10. 后续版本的演进要求

### 10.1 V2：系统内人工操作闭环

在 V1 已有“取消PM挂单”及精确核验基础上，完善人工处置状态、恢复条件、卖出 / 仓位事实和余额约束，不重复规划首期已交付的按钮。

V2 延续仅撤指定余量、**不自动补单**的语义，不能沿用原文档 v2 的撤单后进入缺口补单行为。

“取消补单”只有 V3 真正存在自动任务后提供。停止 / 撤单不默认卖已有仓位，不调用旧取消入口的自动减仓副作用。按钮范围和说明随功能版本更新。

### 10.2 V3：自动缺口与候选规则

自动补齐前独立保存执行来源、固定目标侧任务和每次 attempt。配置只影响新尝试；GTC 来源切 FOK 或其它场馆仍不能退回整腿零成交公式。

对既有业务已支持的完整结算范围，R 为参考侧实际返还，P 为目标侧实际返还，C 为两侧实际成本，N 为新候选成本，P_new 为新增返还：

    D = max(0, R - P)
    补 PM 目标份额 = D / 每份兑付
    最差净收益 = min(R, P + P_new) - (C + N)
    组合收益率 = min(R, P + P_new) / (C + N) - 1

在途 / 未知不是实际覆盖，但阻断同侧重复提交。另一腿失败由原客户端方向编排读取最新 PM 实际覆盖，不拿计划或首次静态 anchor 作永久锚点。

例：PM60→100，另一腿补60在途，不能再发100；确认覆盖60后只重算新增40。V1 只更新并提示，不执行此策略。

保留既有参数优先级：是否补单、入队限制、makeProfit、赔率系数或总体利润率上下沿；上下沿开启替代普通盈利门槛，候选排序及带内等待保持原规则，未知费用不能触发下沿止损。

无新增费用且恰好补齐时，打平参考为 D / (R−C)，普通利润参考为 D / (R/m−C)，m 为原 makeProfit。分母非正或费用区间无法确定分支时等待 / 人工处理，不回退旧公式；执行仍按含费、真实取整判断。

GTC 来源金额型 FOK 须证明价格改善时覆盖上界不超过 D 与原容差；不能证明就阻断，不偷偷切模式。手动卖出等变化转 manual_hold，不自动买回；历史买入、净覆盖与卖出回款分别归因。

### 10.3 V3：执行、停止与资金协议

RDS 事务建立 execution / targetSide 唯一任务、不可变 attempt、幂等命令、事实 / 候选版本、执行租约和一次发送授权。租约过期只能接管核对，不能判原单失败或重发 BUY。

授权为在途边界：stop 先保存则拒绝新授权；授权先完成则核验原尝试，后来确认 GTC 按停止意图精确撤余量。直连已授权签名不能靠另一端 stop 保证物理发送撤回。迟到 ACK / 事实不覆盖 stop。

资金键仍为链 / 资产 / funder，协调共享入口；实测余额为总额还是净额，防重复扣预留。prepared、dispatching、未知、有效余量与费用承诺分类，原单未知或撤单后余额未同步不得提前释放。

V3 另建完整矩阵：多端 stop / 授权竞争、在途失败、增量覆盖、RAY 锚点、GTC→FOK 上界、费用区间、卖出归因、资金与双按钮恢复。V1 可上线不代表已具备这些能力。
