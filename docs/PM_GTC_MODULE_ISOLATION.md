# FOK / GTC 执行模块与公共订单链路

[changmen 扩展] 2026-10-10，按用户明确的“GTC 只是下注模式”修正。此前把报表、统计和订单展示也分成两套的设计已撤销。

## 原则

下单入口冻结本次模式，FOK、GTC 分别执行自己的预检和提交。成交后两者都是普通订单，进入同一个 OrderStore、订单列表、账号统计和原有汇总消息。金额、手续费、币种换算、取整、余仓和盈亏继续使用原规则。

GTC 没有自己的统计报表、订单统计 store 或完整订单卡片副本。公共 OrderList 只按原单的 GTC 身份附加挂单状态、详情与取消操作；当前配置不能改变历史订单身份。

| 职责 | 归属 |
| --- | --- |
| FOK 准备、预检、提交、重试、补单 | 接入前原 FOK 执行链 |
| GTC 准备、预检、签单、提交、持续核对、撤单、恢复 | 独立 GTC 执行模块及其状态 |
| 金额、手续费、汇率、取整、余仓和盈亏 | 原有公共订单规则 |
| 成交订单列表、账号统计、汇总消息 | 原有公共订单链路，两种模式一起统计，每个原单一次 |
| 成交后的人工卖出与卖出恢复 | 原有公共卖出逻辑，保存入口按原单身份分发 |
| FOK 自动补单 / 自动卖出扫描 | 只读自身执行身份的原单；不接管 GTC |
| GTC 尚未进入订单库的挂单 | 临时进度展示；原单出现后撤下临时卡，不计入普通成交统计 |

## 入口与数据边界

自动入口为 `client/web/src/orderModes/router.ts`，手动入口为 `stores/betting/execution/manual.ts`。FOK 原自动执行链和手动执行体保留；GTC 不调用 FOK 私有预检缓存、补单队列或收尾动作。

`Client_GetOrderList` 继续返回完整普通订单页，保留原有分页、日期分组和汇总路径。GTC 字段适配到普通订单数据形状：买入总成交份额用于原有余仓算法，旧 GTC 赔率按原有成交价规则回退。适配只作用于已确认的 GTC 原单，不改变 FOK 数据。

场馆整账号快照可能包含两种模式，公共保存入口继续调用原服务，不查询 GTC。公共 writer 复用原严格读取中的历史元数据保留模式；相同 Link 不构成执行身份，卖单从同场馆的父买单继承。已核实 GTC PM 买单使用其已有 SQL 保护成交成本，FOK 保存不依赖该 SQL。GTC 专用成交核对仍在自身模块，最终进入同一 orders 表和公共读取链路。

公共 `OrderHost.vue` 展示原 `OrderView`，只另外保留缺少已入库原单的 GTC 挂单进度。不会把同一已入库订单交给两个列表。

## 适用范围

GTC 当前自动执行支持含一条 PM 腿的双边组合。不支持或准备失败时结束本次尝试，不隐式回落到 FOK。手动 GTC 允许多次下单，不因已有挂单或历史盘口次数限制新的人工决定。

## 验证

`npm run check:fok-parity` 与接入前 `219535c8` 比较原执行核心、金额规则、OrderStore、人工卖出和保存代码。公共 OrderList 的比较只去除新增的模式详情入口；FOK 自动卖出扫描只替换订单输入入口，执行体保持一致。

隔离检查禁止 GTC 调用 FOK 私有下单 / 补单 / 收尾逻辑，同时禁止重新添加 GTC 专用报表、统计 store 和订单卡片副本。公共订单回归覆盖混合模式一次统计和汇总、卖单不重复计次、已入库原单只展示一次及 FOK 执行动作不接管 GTC。

所有自动验证不发送真实买入、卖出或撤单。

## 2026-10-10 修改前设计审计（历史快照）

用户要求再次核对“FOK 与接入前完全一样”。`scripts/verification/audit-fok-gtc-current-design.mjs` 对照 `219535c8` 输出 `output/fok-gtc-current-design-audit.json`：检查的 53 个关键文件中，45 个仅忽略换行后完全一致，8 个有改动。这个范围不能被称为整个仓库逐字一致；原 FOK 核心一致，也不等于所有公共输入与故障行为都完全一致。

审计确认以下边界仍需收紧：

- 自动模式实际由 `pmArbOrderMode` 与本版本激活标记共同决定；配置为 GTC 但标记缺失时会进入 FOK。
- 手动入口在显示模式选择之前就调用公共账号选号；选号仍使用公共账号日订单上限和轮换索引。
- 普通账号统计包括两种模式，FOK 的公共账号日上限因此也会计入 GTC；盘口级 FOK 成功历史仍独立。这是规则未变、公共输入改变的具体区别。
- 普通保存请求在到达原 FOK writer 前增加身份读取；严格读取失败会直接拒绝，原 writer 不会被调用。
- 恢复生命周期仍观察旧 `gtcOrderProjection`。公共 OrderStore 已加载 GTC 原单，但参加提示缺失时不会自动启动恢复，尚未完全实现“只凭历史原单身份恢复”。

按钮条件自身按原单身份和状态判断，不读取当前新下单配置；但按钮依赖恢复记录可用，因此还受上述恢复入口问题影响。

仓库另有 `pmMapOutcomeStore.ts` 的胜方显示规则改动（只认官方胜方，忽略旧价格依据）；它不是 GTC 分流代码，但与该基线存在差异，不能纳入“整个界面与基线一致”的声明。

以上是前一次只增加审计材料的历史记录；本轮修复结果见文末，不能用这些历史问题描述当前实现。
