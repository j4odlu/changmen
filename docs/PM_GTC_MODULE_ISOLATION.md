# FOK / GTC 执行模块与公共订单链路

[changmen 扩展] 2026-10-10，按用户明确的“GTC 只是下注模式”修正。此前把报表、统计和订单展示也分成两套的设计已撤销。

## 原则

下单入口冻结本次模式，FOK、GTC 分别执行自己的预检和提交。成交后两者都是普通订单，进入同一个 OrderStore、订单列表、账号统计和原有汇总消息。金额、手续费、币种换算、取整、余仓和盈亏继续使用原规则。

[changmen 扩展] 2026-10-10，按用户明确要求取消下单费用预留：下注金额只表示本金。GTC 按本金 / 限价向下取合法份数，最小量和签单本金上限照常检查；提交前不查询费率、不因未知费用阻断，不把费用纳入自动套利发送前的收益判断。成交后的实际手续费仍进入原有记账和盈亏链路，新单仅在核对本单 taker 成交时读取费率；查询失败保留费用待核实。旧单已有费用证明继续用于财务核对。历史 `allInBudget` 字段名为兼容保留，新单值只表示下注本金上限。

GTC 没有自己的统计报表、订单统计 store 或完整订单卡片副本。公共 OrderList 只按原单的 GTC 身份附加挂单状态、详情与取消操作；当前配置不能改变历史订单身份。

[changmen 扩展] 2026-10-10 全面检查补充：新自动套利不等待全量旧单恢复，也不读取全局恢复就绪状态。仅在用户启用同盘口计次、上笔赔率或反向账号排除时，查询本用户、本盘口的成交历史；该查询不做历史订单元数据修复。手动 GTC 不依赖历史恢复。同钱包的其它账号（包括凭证异常的无关账号）不阻止本次所选账号创建订单。后台恢复逐单隔离异常，一张旧单失败后继续核对其它原单；新执行仍必须成功持久化自身计划及一次性授权后才能提交。

[changmen 扩展] GTC 成交证据保存仅查询本批执行 ID 和登录用户归属，不触发全量历史执行读取、500 条历史截断或历史标记修复。其它旧单的修复异常不能影响本次确认/入库；场馆原单 ID、选用账号、对侧原单归属检查继续保留。同盘口历史恢复也只更新本次所选且启用了历史限制的账号计次，其它账号的旧记录异常不拦截新单。

| 职责 | 归属 |
| --- | --- |
| FOK 准备、预检、提交、重试、补单 | 接入前原 FOK 执行链 |
| GTC 准备、预检、签单、提交、持续核对、撤单、恢复 | 独立 GTC 执行模块及其状态 |
| 金额、手续费、汇率、取整、余仓和盈亏 | 原有公共订单规则 |
| 成交订单列表、账号统计、汇总消息 | 原有公共订单链路，两种模式一起统计，每个原单一次 |
| 成交后的人工卖出与卖出恢复 | 原有公共卖出逻辑，保存入口按原单身份分发 |
| FOK 自动补单 / 自动卖出扫描 | 只读自身执行身份的原单；不接管 GTC |
| GTC 尚未进入订单库的挂单 | 临时进度展示；原单出现后撤下临时卡，不计入普通成交统计 |

## 入口与数据边界

自动入口为 `client/web/src/orderModes/router.ts`，手动入口为 `stores/betting/execution/manual.ts`。FOK 原自动执行链和手动执行体保留；GTC 不调用 FOK 私有预检缓存、补单队列或收尾动作。

`Client_GetOrderList` 继续返回完整普通订单页，保留原有分页、日期分组和汇总路径。GTC 字段适配到普通订单数据形状：买入总成交份额用于原有余仓算法，旧 GTC 赔率按原有成交价规则回退。适配只作用于已确认的 GTC 原单，不改变 FOK 数据。

场馆整账号快照可能包含两种模式，公共保存入口继续调用原服务，不查询 GTC。公共 writer 复用原严格读取中的历史元数据保留模式；相同 Link 不构成执行身份，卖单从同场馆的父买单继承。已核实 GTC PM 买单使用其已有 SQL 保护成交成本，FOK 保存不依赖该 SQL。GTC 专用成交核对仍在自身模块，最终进入同一 orders 表和公共读取链路。

公共 `OrderHost.vue` 展示原 `OrderView`，只另外保留缺少已入库原单的 GTC 挂单进度。不会把同一已入库订单交给两个列表。

## 适用范围

GTC 当前自动执行支持含一条 PM 腿的双边组合。不支持或准备失败时结束本次尝试，不隐式回落到 FOK。手动 GTC 允许多次下单，不因已有挂单或历史盘口次数限制新的人工决定。

[changmen 扩展] 2026-10-10，按用户明确要求移除同钱包未完结 GTC 对新套利的限制。自动及手动新订单均独立创建；旧单的挂单、未知提交、人工核对及成交修订只约束旧执行，不阻止新的独立套利或参数保存。服务端按 executionId 事务锁与记录版本维护幂等和一次性授权，不以 walletKey 互斥不同订单。参数保存不再核对或恢复旧组；旧单继续逐笔监控、核对与展示。

## 验证

`npm run check:fok-parity` 与接入前 `219535c8` 比较原执行核心、金额规则、OrderStore、人工卖出和保存代码。公共 OrderList 的比较只去除新增的模式详情入口；FOK 自动卖出扫描只替换订单输入入口，执行体保持一致。

隔离检查禁止 GTC 调用 FOK 私有下单 / 补单 / 收尾逻辑，同时禁止重新添加 GTC 专用报表、统计 store 和订单卡片副本。公共订单回归覆盖混合模式一次统计和汇总、卖单不重复计次、已入库原单只展示一次及 FOK 执行动作不接管 GTC。

所有自动验证不发送真实买入、卖出或撤单。

## 2026-10-10 修改前设计审计（历史快照）

用户要求再次核对“FOK 与接入前完全一样”。`scripts/verification/audit-fok-gtc-current-design.mjs` 对照 `219535c8` 输出 `output/fok-gtc-current-design-audit.json`：检查的 53 个关键文件中，45 个仅忽略换行后完全一致，8 个有改动。这个范围不能被称为整个仓库逐字一致；原 FOK 核心一致，也不等于所有公共输入与故障行为都完全一致。

审计确认以下边界仍需收紧：

- 自动模式实际由 `pmArbOrderMode` 与本版本激活标记共同决定；配置为 GTC 但标记缺失时会进入 FOK。
- 手动入口在显示模式选择之前就调用公共账号选号；选号仍使用公共账号日订单上限和轮换索引。
- 普通账号统计包括两种模式，FOK 的公共账号日上限因此也会计入 GTC；盘口级 FOK 成功历史仍独立。这是规则未变、公共输入改变的具体区别。
- 普通保存请求在到达原 FOK writer 前增加身份读取；严格读取失败会直接拒绝，原 writer 不会被调用。
- 恢复生命周期仍观察旧 `gtcOrderProjection`。公共 OrderStore 已加载 GTC 原单，但参加提示缺失时不会自动启动恢复，尚未完全实现“只凭历史原单身份恢复”。

按钮条件自身按原单身份和状态判断，不读取当前新下单配置；但按钮依赖恢复记录可用，因此还受上述恢复入口问题影响。

仓库另有 `pmMapOutcomeStore.ts` 的胜方显示规则改动（只认官方胜方，忽略旧价格依据）；它不是 GTC 分流代码，但与该基线存在差异，不能纳入“整个界面与基线一致”的声明。

以上是前一次只增加审计材料的历史记录；本轮修复结果见文末，不能用这些历史问题描述当前实现。

## 2026-10-10 GTC 成本与平仓金额校准

[changmen 扩展] GTC 专用事务以原执行记录核实的累计买入份数与含费成本为依据。部分成交撤单只保留实际成交成本；人工卖出按原单平均成本分摊，余仓结算按「卖出净回款 + 剩余份额兑付 - 原始含费成本」计算，不累加旧纸面盈亏。卖单流水按准确 ID 合并，晚到的旧快照不能清掉另一笔卖出。

GTC 手动卖出在原人工卖出保存步骤选择 GTC 专用保存：本卖单 CLOB 已确认交易与钱包 SELL 流水的交易哈希、资产和份数全部匹配后取净回款，不再次扣手续费。缺少净回款时保留原卖出恢复记录并显示具体原因，不重发卖单；没有 GTC 原单标记的人工卖出继续原保存路径。卖单的摊销成本不能当作回款，GTC 历史流水回填遵循同样规则。

金额回归覆盖手续费晚到、后续新增买入、部分及全部卖出、剩余仓位胜负结算、同单重复同步及事务回滚。当前账号实际只有两张已全部成交的 GTC 财务订单，没有部分成交撤单或手动卖出实单样本；这些分支用回归测试和 PostgreSQL 会话临时表验证，不发送真实买入、卖出或撤单。

此前严格源码快照验收记录是当时结果。本轮源码已有此前预检诊断改动和 GTC 专用平仓入口变化，不能将历史逐字一致结果当作本轮验证；金额回归、GTC 隔离、客户端/服务端边界与前端构建分别核验。

## 2026-10-10 同步异常与查询停止条件

[changmen 扩展] 登录服务和原单查询失败使用独立的本地同步提示，不写入空订单事实，不改变已确认的成交、费用、订单状态和盈亏。下一次成功核对自动清除提示；已结算原单被主动复查时产生的查询异常仍会自动重试，恢复后再次停止场馆查询。历史遗留的登录/查询错误按同步异常展示；真实成交数量、价格或费用冲突仍保留订单核对提示。

原单终态、余量为零、成交明细完整且成交和手续费已确认后，停止 PM 原单查询与该原单的 WS 监听。比赛结束不能独立证明挂单结束；尚有挂单、未知提交、未确认成交或未知费用时继续核对。对侧订单只按原执行 ID、场馆、账号及订单 ID 判断结算，不能借用同场其它订单的状态。全部原执行已收尾且财务订单结算后，每分钟仅同步历史与财务记录，发现新的执行后恢复快速核对。

数据库旧日志的 `getBrowserSession: Connection terminated unexpectedly` 确认是数据库连接中断使本系统会话读取失败；历史日志不足以逐次归因。新增仅针对幂等会话读取/续活的断连重试一次及带时间、错误码、连接龄和池计数的日志；下注、财务写入和事务均不自动重放。持续故障仍返回临时服务异常，不撤销登录会话。本机 TUN/Bitz 配置属于项目外部运行环境，项目启动和运行均不读取、检查或修改代理软件配置。

本地前后端已更新。只读运行核验 65 秒内三笔旧执行版本号不再增长，没有数据库/会话断连日志；同时观察到用户新开的独立 GTC 套利双腿成交。四张现有 GTC 买单成本和盈亏审计无差异。验证记录见 `output/gtc-sync-runtime-audit.json` 与 `output/gtc-lifecycle-audit.json`。测试涵盖故障恢复、并发注销、完整成交/部分成交撤单的停止条件、结算身份和新单唤醒；未发送测试买入、卖出或撤单。
