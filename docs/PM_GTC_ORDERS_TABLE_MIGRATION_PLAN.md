## 1. 最终模型

**一条 PM 签单原单，对应一条 `orders` 行，完整执行控制附在该行上。** 准备中就持久保存该签单的控制信息；受理、成交、核对、结算持续更新同一行。传统场馆对侧订单继续保存自己的场馆订单，关联现有执行身份，不承载第二份控制状态。

**增量兼容约束：只在原 `orders` 上增加字段，不改名、删除或修改任何既有字段的类型、默认值及含义，原主键、唯一键和外键保持。** 迁移已有财务行时只写新增控制列，不重算或覆盖原金额、赔率、状态、时间、raw 及身份。生产只安装列、未安装新删除触发器或索引；用户最新授权允许在实际旧版兼容验收通过后，为原指定 37 条已有财务订单附加非权威控制副本，资格仍 TRUE。没有对应订单的记录仍不插入，不创建 FALSE 行、不启用完整兼容、不切换读写、不撤旧表。旧源继续更新，旧硬删也可删除副本，故完整回填及控制切换仍须后续消费者保护、排空和核对；正常业务对原财务字段的更新继续按原规则执行。

现有 `applyGtcCommand` 的 `ack` 明确要求回执订单 ID 等于 `plan.orderHash`，只允许大小写差异。因此使用签单 hash 作为稳定原单身份，不生成假的 `gtc-pending:*` 数据库订单 ID，不在受理时换键。现有财务行保留主键 `orders.id` 和原 `order_id` 拼写。发现非大小写差异、同原单多执行、同身份多行或原归属冲突，预检报错，不自动合并授权、删除记录或猜测 Link 归属。

新增专用列如下；生产已执行 [仅增列脚本](../scripts/migrations/pm-gtc-orders/phase2-add-columns.sql)，六个控制列默认 NULL，`financial_ready` 默认 TRUE。后文控制索引、记录 CHECK、财务视图和删除触发器属于后续完整 schema，生产此次均未创建：

| 列 | 语义与兼容 |
| --- | --- |
| `execution_kind` | 固定 `pm-gtc-v1`；无控制的普通订单为 NULL；不是传统场馆的下单模式 |
| `execution_id` | 原 UUID，全表非空唯一；保持原 API、锁键、恢复、计次和关系标识 |
| `execution_wallet_key` | 原 `wallet_key` 完整值；同钱包多个原单仍允许，不新增钱包互斥 |
| `execution_active` | 原表 `active`，须与原 record 的 `!released` 一致 |
| `execution_record` | 原 `record jsonb` 全量保留，包括未知历史字段；仍用同一个状态机读取与更新 |
| `execution_updated_at` | 原 BIGINT 更新时间；迁移不刷新为“现在”，不改变最近 500 条恢复顺序 |
| `financial_ready` | NOT NULL，既有订单及普通 writer 默认 TRUE；此前没有财务行的控制原单为 FALSE |

`user_id` 对应原 owner，`player_id` 对应原 PM 账号；既有 `(user_id, order_id, player_id)` 唯一键保持。`execution_id` 增加独立部分唯一索引；owner/updated_at 和 wallet/active 增加与旧查询等价的部分索引。控制列必须全 NULL 或完整有效，身份与 record.id/owner/walletKey 交叉校验，约束不能靠重建 record 修复冲突。`revision` 继续取完整 record 内原值，避免引入第二份可漂移的版本权威。

执行控制放在专用列，普通 `raw` 全量覆盖不会删掉它；客户端 `SaveOrder` 无权建立或改写控制列。附加快照仍是兼容字段，不替代完整控制记录或场馆事实。

`financial_ready=FALSE` 行的旧非空金额列可以使用数据库默认零，但零不代表成本、费用、赔率或盈亏已经核实。所有原财务/统计/选号/余额/拒单/补单消费者必须先限定原财务集合；展示由真实控制事实解释未知值。只有原 `resolveGtcFinancialOrder` 及原成交/FAILED 资格满足时才晋升为 TRUE，算法、输入、费用与份额解释不变。准备中、受理零成交、部分事实不全及费用未知都不能因为并表而提前进入旧财务集合。

### 锁与事务必须单独验收

旧 GTC 保存先 SHARE 锁执行行，再 UPDATE 锁财务原单；并为同一行后不能机械保留“先 SHARE 再 UPDATE”，两个保存事务可能同时持有 SHARE 而发生升级死锁。阶段四须对 GTC 原单按原执行 ID 排序，一开始取得需要的写锁，复用已锁定记录，保留 UUID advisory lock 和 revision 校验，不扩大到钱包或所有订单。

命令、财务升级、对侧身份更新及结算仍在同一事务提交；任一失败整体回滚，不能让控制成功而财务部分失败。FALSE→TRUE 表示原财务资格成立，但通知必须按实际旧调用路径保持：普通 writer 仅首次成功 COMMIT 后调用 inserted hook，UPDATE/回滚不调用；原 GTC mutate 及专用列表 writer 本来没有普通 inserted hook，晋升不新增这类通知。控制占位 INSERT 也不发通知。不能将资格晋升一概解释为需要新增通知。

必须用实际 PostgreSQL 并发测试验证：同执行命令竞争、重复授权、两个保存事务、保存与 facts/卖出并发、批量锁顺序、取消 late result、目标回填版本漂移、COMMIT/ROLLBACK 故障；SQL 文本和 mocked query 测试不能代替锁验证。

## 5. 回填与切换程序

### 无对应订单的记录：下一步边界（2026-10-11）

[changmen 扩展] 最近一次生产核对是在原 37 条回填时：68 条旧执行中，39 条已有订单、29 条无对应订单；只处理了原指定 37 条。29 是当时快照数量，执行迁移前须重新只读核对，不能当作当前固定批次。

无对应订单的记录需要 INSERT 新行。实际 VPS 版本的 `orders_store.js` 日期分页、账号查询、后台 COUNT 和统计直接读取 `orders`，未识别 `financial_ready`；删除仍为硬删，首次入库按原 INSERT 判断。因此仅给新行标记 FALSE 不能使旧版忽略它，也不能用零金额、假状态或假日期证明旧版行为不变。原 37 条的验收只覆盖既有 TRUE 行附加六列，不能用于批准这些新行。

实施顺序如下：

1. **兼容准备与验收。** 本机订单兼容及缺订单回填执行器已实现并实测，执行控制继续读写 `pm_gtc_executions`。全部订单消费者按财务资格限定原集合，保护删除、普通 upsert、原 GTC 财务晋升及首次入库 hook。现有阶段二集成测试保留原 40 项并新增 24 项，覆盖缺订单回填与旧源写入/新财务入库竞争、来源漂移、重复执行、断点和回滚，共 64/64 通过。新工具为 `backfill-pending.mjs` 与默认离线、仅允许隔离本机执行的 `backfill.mjs`，已有 37 条复制器不支持 INSERT，未直接扩用。
2. **兼容发布后回填。** 另行授权并完成生产结构与所有活动消费者的兼容发布、验证后，才允许创建 FALSE 行；新旧实例混跑期间不插入。这一步仍保留旧表为唯一执行控制权威，不切换下注、拒单检测、补单或恢复来源。完整删除触发器会改变当前旧版硬删行为，不能在旧版仍运行时直接安装。

### 完整回填与控制切换

1. 应用前验证现有 VPS 实际版本与空扩展结构兼容，包含 SELECT */RETURNING * 返回形状、首次入库 hook 及原增删改查；新增列不代表这些接口自动保持形状。DDL 只在维护窗口执行，设置明确锁等待/事务超时，遇到冲突回滚。旧版仍运行时不创建 FALSE 行，仅允许实际版本验收通过且明确授权的既有 TRUE 行附加控制副本；所有活动消费者升级并启用兼容后才进入完整回填。不要在第一个下注请求里 ALTER 或建立索引。
2. 从只读一致性快照审计全量执行身份、owner/profile、完整 record 和原单唯一性。缺失或冲突全量报告，不跳过后宣称迁移完成；历史孤儿及重复执行由单独数据处置解决，不能自动重置授权。
3. 独立迁移批次基于旧源版本及目标哈希执行 CAS；已迁一模一样记录为 noop。不得覆盖较新目标，不更新财务字段或旧源，失败保存检查点后可重试。回填期间旧表继续唯一控制权威，禁止两源择新/失败回退到另一源。
4. 准备切换时停止接收新首次执行，允许已开始的首次流程按原规则完成；等全部开放授权窗口结束及在途事务排空，再完成最后控制核对。未确认的场馆提交不能因此重新发送。长期挂单无需等到全部结算，场馆事实在恢复后继续按原方法核对。
5. 通过隔离演练明确新旧实例排空和单一控制源切换流程；冻结期间后台持久化排队，最终锁定/核对来源并切换全部实例。锁超时或版本漂移则放弃切换、继续旧源，不能部分实例读新而其它实例写旧。不能在尚开放的首单截止窗口里用迁移等待拖延裁决。
6. 切换后只有 orders 控制写源；旧表保持只读备份用途，不自动创建或恢复为权威。验证恢复集合、排序、最近 500 截断、未结 RAY、手动单、历史卖出父单、财务投影和每项规则。
7. 只有阶段五门槛满足后才执行物理 DROP。保持独立备份和带来源校验的恢复工具，最终系统中无旧表运行依赖。

回填阶段不在原首单事务增加同步双写或触发器。旧源更新与回填竞争通过源版本、重扫及切换前最终冻结核对处理，不把旧快照当成实时权威。迁移审计与回填不是交易授权来源。

## 6. 回退与完成定义

- 切换前：旧源继续唯一权威；可以停止回填，保留新列和已复制的非权威控制。不能因为回填失败清除原执行身份、计次、授权或财务行。
- 切换后、删表前：不能直接启动旧版本或读只读旧表。先排空新写源，把 orders 中最新完整 record、active 和原更新时间反向同步到旧表并核对，再做单一源切回。否则已消费授权可能被重放。
- 删表后：从备份恢复旧 schema，再基于 orders 最新控制重建、校验并切换；备份本身不是最新权威。并表撤回不撤回已经发生的成交、卖出、取消、计次或对侧订单。
- 财务删除、账号移除、用户删除、历史反向恢复都须覆盖；控制记录不能随普通财务清理丢失，也不能仅因控制行存在恢复已删除财务的资格。

完成必须同时满足：全部旧执行完整迁入、每个执行唯一原单承载、原财务集合和执行规则一致、只读写 orders、列表不依赖合成缺库原单、运维和数据库对象无旧依赖、实际旧表已删除且最终验收通过。阶段一及阶段二本地代码完成不代表已经达到这些条件。
