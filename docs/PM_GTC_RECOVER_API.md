# GTC 聚合恢复接口

[changmen 扩展] 2026-10-14：页面监控恢复统一使用 `Pm_GtcRecover`。执行记录与财务订单仍保留两张表，按认证用户、执行 ID、账号和原单 ID 关联。接口只读，复用现有归属和原单身份校验，不建表、不修订历史元数据，也不调用场馆交易 API。

请求字段：

| 字段 | 用途 |
| --- | --- |
| `discover` | 本轮是否读取新增或有版本变化的执行记录 |
| `knownRevisions` | 已持久化执行的版本，用于增量读取；不会把本地未保存的官方结果当成后台版本 |
| `monitorIds` | 本轮到期、需要恢复或尚未结算的执行 ID，单批最多 1000 个 |
| `recoverDiscovered` | 同一次响应中读取刚发现执行的关联财务原单 |
| `skipMonitorIds` | 已结算、不需要读取或仍在退避的已知执行；执行读取仍可更新这些记录 |
| `knownOrders` | 上次财务内容的稳定指纹；原单身份、状态与金额无变化时不重复传输订单行 |

响应保持普通 esport envelope。有效读取请求的外层 `success=1`，分区读取错误放在 `info` 中：

```json
{
  "executions": { "ok": true, "rows": [] },
  "orders": [
    { "ok": true, "ids": [], "unchangedIds": [], "rows": [] }
  ]
}
```

`executions` 未请求时为 `null`；失败时为 `{ "ok": false, "message": "..." }`。每个财务批次都携带 `ids`，成功时返回变化的 `rows` 和未变化的 `unchangedIds`，失败时返回 `{ "ok": false, "ids": [...], "unchangedIds": [], "message": "..." }`。客户端接纳成功分区，只有失败分区进入退避。鉴权和参数错误仍由外层失败表达；传输失败时退避本次请求包含的分区。

后台发现与每个执行的财务读取各自保持重试时限。失败间隔为 5、10、20、40、80、160、300 秒，持续失败时上限五分钟；无变化的正常读取为 60、120、240、300 秒。实际发起时刻由独立页面监控调度决定。新原单及原单身份、提交、成交或终止状态变化可触发及时读取；`observedAt` 和副本版本变化不绕过财务读取时限，失败时业务变化也不会绕过退避。

首次恢复可在一个响应中返回执行和财务订单；超过 1000 个已知待恢复执行时客户端分批，每轮执行发现只放入第一批。已结算、已确认零成交结束及未提交原单不重复读取；另一腿仍未结算时保留该执行的财务恢复。恢复结束不额外刷新普通订单列表，结算证据不随列表日期筛选丢失。

`Pm_GtcList`、`Pm_GtcMonitorOrders` 和日期分页的 `Pm_GtcOrders` 保留兼容。只有后台明确返回“未知预测市场 action: Pm_GtcRecover”时才切换旧读取路径，并在当前会话缓存该能力判断；数据库、鉴权或网络错误不会触发兼容回退。盘口范围历史读取和副本修复仍可使用 `Pm_GtcList`，不会改变一次性授权流程。

PM 官方查询、事实接纳、状态更新及撤单继续由原场馆模块独立执行，不等待聚合恢复。此次实现未迁移或合并数据表，也未调整 FOK 发送和撤单路径。
