## 模式差异的接入点

| 职责 | 当前实现 |
| --- | --- |
| 选号与业务门控 | 公共 prepare 保持线上原账号选择、资金、次数、赔率及 noSameBet 过滤；GTC 原成交历史在单腿兼容桥内独立检查 |
| PM 模式预检 | 公共 check 调用 account betGateway；仅 PM GTC 腿选择 adapter 的 `checkGtcBuy` |
| PM 签单和场馆协议 | 原 `packages/venue-adapter/polymarket/gtc` 能力，未修改 |
| 原单持久化及授权兼容 | `orderModes/gtc/arbLeg.ts` 返回单腿 validate/submit/confirm/facts/markConfirmed，以及幂等关闭与动作许可 |
| 双腿发送、顺序及等待 | 公共 place/settle；原单仅提交一次，并行任务全部返回后才关闭发送窗口 |
| 对侧原单核对 | 兼容桥调用已有精确原单读取；等待由公共 settle 完成一次，原核对接收 wait=0 |
| 进度及倒计时 | 公共拒单 tip 与 active run settling；GTC 部分成交/挂单事实不再覆盖正在运行的拒单倒计时 |
| 挂单和原单监控 | 原 PM/RAY 监控、订单/成交读取、会话停止与恢复保留 |

兼容桥仍使用已有双腿持久化身份来关联原单；这不表示持久化数据结构已拆成通用订单模型。本次没有数据库迁移。

## 保留的执行规则

- 现有 GTC 支持范围：一条 PM 腿及另一场馆的双边自动套利；没有扩展 9999 或双 PM 组合。
- PM 首腿受理不等于成交；可靠的初次原单事实、正成交量和原发送窗口共同决定是否发送第二腿。零成交、提交未知或超时不追加第二腿。
- 串行顺序与用户选 Parallel 时的并行发送仍由同一公共 place 决定。GTC 原 A/B 位置保持，以便持久化原单与挂单监控正确关联。
- PM 部分成交保持部分成交/人工处理事实，不将其标记为整组成单。关闭首次发送窗口不撤销挂单，不停止后续监控。
- GTC 原许可仍不自动重试、补单、卖出或广播跟单，也不重复登记另一套 RAY 拒单监控；公共收尾消费动作许可。
- 公共选号保持原 `BETCOUNT`、`BETACCOUNT`、lastOdds 规则，不叠加 GTC 成交历史；GTC 仍在发送原单前独立检查其历史，写入沿用原单去重。
- 对侧先发时，公共 place 要求原提交成功，兼容桥要求未进入人工停止；挂单监控提前推进到 pending/filled 不阻断 PM 第二腿。拒单、未知和人工停止仍阻断第二腿。
- 传统对侧成功进入拒单检测时恢复右上角原 tip；等待结束后重新读取精确原单，不能用等待前的缓存代替。PM 挂单详情同时保留。
- PM＋PF 等确认型对侧也由公共流程完成其原等待，再核对；PM 已有成交事实可先读取。
