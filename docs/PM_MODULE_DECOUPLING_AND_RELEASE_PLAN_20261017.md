## 3. packages 如何区分运行环境

### 3.1 推荐归属

| 类别 | 推荐归属 | 约束 |
| --- | --- | --- |
| 浏览器专属 | 新 `packages/pm-market-data-browser`：簿引擎、服务、Worker、公共数据协议；web：Vue/Pinia 装配与设置 | 服务端生产入口不得导入；可由 Node 测试，不因此成为后端运行依赖 |
| Node 专属 | 现有 `server/db`、`server/storage`、backend/collector 等 | 保持现有位置；不为统一目录外观再迁移成 `packages/node/*` |
| 双端共享 | `packages/api-contract`、`packages/shared` 中经核实的公共规则 | 协议及纯逻辑保留一份，不复制成前后端两份 |
| 包内混合入口 | `packages/venue-adapter` 的 browser 平台入口与 Node registry/loader/shared/contract 入口 | 逐入口登记环境与消费者；不能把整个包标成前端专用 |

建议采用项目自有元数据 `changmen.runtime = browser | node | universal | mixed`，混合包另外登记入口。它只是说明，**不直接授予省略后端的资格**；还须检查真实依赖、动态加载、安装和构建输入。新包的 workspace、依赖与 lockfile 调整是一次真实边界变更，首轮按原保守流程全量验收，不承诺迁移本身只发前端。

第一阶段不需要创建 `packages/frontend/`、`packages/backend/` 两个大目录。环境明确的独立包加入口约束已经足够，避免因整理目录而改动数百个 import、原固定保护路径和历史兼容入口。

### 3.2 本地簿模块的具体接口

目标依赖方向：

```text
原 PM-M / marketStream（原位置、原行为）
                  ↓ 只读 source port
web 装配层 → pm-market-data-browser → 只读 lease / 诊断端口
                  ↑                         ↓
      Worker factory / clock          动态 HTTP 对照、未来深度 UI

经典 FOK → 原 HTTP / 原准备与执行链路（保持现状）
```

建议给新包显式注入以下端口，取代 `service.ts` 对原 stream 和 quote Hub 的默认导入：

```ts
interface ReadonlyMarketSourcePort {
  observe(listener: (event: MarketStreamEvent) => void): () => void;
  subscribedAssets(): readonly string[];
}
interface BookHostPorts {
  source: ReadonlyMarketSourcePort;
  createWorker(): WorkerPort;
  allowed(): boolean;
  monotonicNow(): number;
}
```

端口只提供已有原始流、真实接收时间和已订资产，不提供 send/subscribe/reconnect，不允许引擎扩大源集合。既有 epoch、sequence、资产代次、全输入 FIFO 与 20ms 读取语义保持；不改快照/增量处理或新鲜度政策。

原始流和读簿协议只保留一份；原 `marketStreamProtocol` 可保留类型兼容入口，避免引擎与 adapter 互相导入运行实现。注入函数只存在于主线程宿主，跨 Worker 继续使用当前可序列化协议，不把回调或 source 对象通过 structured clone 发送。

具体迁移范围：

- `bookReducer.ts`、`bookStore.ts`、`passiveBookFeed.ts`、`orderedWorkerMailbox.ts` 和服务/协议迁入新包；纯核心不导入 Vue、Pinia、账号、HTTP、签名器或下单模块。
- Worker 的通用消息循环归新包；当前 `marketData.worker.ts` 中的动态消费者装配与核心分开，避免只使用簿时静态带入整套预检实现。可选消费者使用明确的诊断端口，不把账户能力带进公共簿。
- `client/web/src/runtime/pmMarketData.ts` 保留登录、模式、线路和账号授权，负责创建 source/Worker 端口；`pmDynamicWsPreflight.ts` 维持默认关闭和同步停止契约。
- `wsBook` 中的完整读、只读模拟和公共 HTTP 对照作为浏览器消费者整理；既有 `shadowObserver.ts` 与动态 HTTP 接入点保持原位置和行为，消费者从原插槽订阅，不更改实际预检返回值。
- 当前 package 子入口若需兼容，可转导出新包并在原入口装配原 source port；禁止从 adapter 反向导入 `client/web`。不能产生旧、新两套单例或 Worker。

**原 `realtime/ws.ts`、quote Hub、经典 FOK 生产文件首轮冻结。** 优先利用已有 observe/构造注入能力，不新增原行情钩子，不添加经典等待、拒单、历史查询或手动准备要求。若某个迁移动作必须触碰这些路径，该批次应拆开说明并走既有完整保护，不能称为无影响的位置整理。

[B 批已实施](./audits/PM_BROWSER_MODULE_EXTRACTION_AUDIT_20261017.md)：核心、服务、FIFO、协议及通用 Worker 循环已迁入新包；HTTP 对照、新鲜度和执行模拟作为 adapter 浏览器消费者保留，通过显式诊断端口接入。web 使用独立 `orderBookSource` 入口和自身 Worker 工厂，旧构造与 Worker 组合入口保留兼容。新包核心只允许包内依赖和明确的 SDK 类型导入，原 PM-M、quote Hub 和经典 FOK 源码未改。

## 5. 保留完整来源保护，允许前后端版本不同

**不能靠删掉 `sourceFingerprint` 的 packages 路径来获得“无后端影响”。** 当前完整来源指纹、精确 archive SHA、candidate tree、输入稳定性和产物绑定继续保留。

新增独立、版本化的 `componentInputFingerprint` 及其入口证据，仅用于选择组件及说明影响；它不替代现有完整来源指纹或551保护。`release-evidence.mjs`、`verify-runtime.mjs` 和运行诊断应明确两种含义，版本不支持或证据不全时保守拒绝缩小范围。

先通过一次完整受控发布让基础设施支持新证据，再启用缩小范围；不能要求仍不支持该证据的旧后端凭空证明无影响。既有人工组件选择也只能扩大实际需要发布的集合，不能用 `--publish=frontend` 或 workflow 输入跳过已识别的后端变化。

例如仅发布浏览器簿改动：

- 前端由 F0 更新为 F1；后端保持 B0。后端旧发布目录、已加载来源及 PID 保持不变。
- 核对前端 F1 的产物与运行身份；后端仍与其实际 B0 身份及契约核对。不能要求两端 SHA 永远相等，也不能将未发布的后端标记改写为 F1。
- 后续 push 继续以每个组件的真实线上版本为基线，累积比较 B0→候选的后端相关变化；不能只看最近一次 push，也不能因上次前端已更新而漏掉尚未发布的后端改动。
- 共享契约变化必须验证 F1/B0 等实际组合，若不兼容则升级联动发布。前端回滚只切前端发布目录，不能顺带回滚后端或数据库。

现有后端完整 Git archive 可先保留，不立即为缩包裁剪文件。未选择后端时不生成、不传输、不激活后端 archive；选择后端时继续完整封存。产物瘦身是另一项工作，不与本轮省略后端发布混在一起。

还需核对 `deploy-server-remote.sh` 的旧路径分类和瘦包同步：它们不能在已选择 frontend-only 的流程中再触发 root install、后端编译或 PM2 重启。远端激活仍校验当前计划、批准组件、archive SHA、实际运行身份与失败回滚，不能仅信任调用方传入的字符串。
