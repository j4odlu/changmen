## 2 P1 必须优先修订的问题

### A01 缓存来源不足以证明原始报价新鲜度

位置：执行方案第 38、101 至 123、174 至 180 行。

方案选定 `getPmQuoteEntry().clobPrice` 为原始卖一来源，同时要求保留真实接收时间、区分初值与重连。当前缓存只存 `time` 和 `http/mqtt`，无法可靠区分 HTTP 种子、实际 HTTP book 纠偏、业务层赔率回写，也没有每条原始卖一的接收时间和连接代次。

代码证据：`saveTokenQuote` 第 25 至 33 行使用 `Date.now()` 写入缓存，HTTP 种子与 book 纠偏在缓存中均为 `http`；纠偏来源只另记于诊断指标。`markets/collect.ts` 第 65 至 72 行存在保留旧 `clobPrice`、重新写入缓存时间的路径。赔率读写桥的 `writeVenueOdds` 和 `BetOption.updateOdds` 也会把业务写入变成带当前时间的缓存条目。PM 总线 `PolymarketMarketQuote` 只包含 assetId 和 bestAsk，接收者无法从该对象恢复源 timestamp。

因此，缓存时间很新不等于这次卖一刚从市场收到；给缓存快照附加一次模块读取时间也无法修复。只把这件事列入 P0 待核实，尚不足以支撑后续“严格有效”的接口定义。

修订要求：在 P0 确定逐来源的证据等级和只读可实现入口。区分 `cacheWrittenAt`、`quoteObservedAt`、`sourceAt` 与 `originKind`；不能证明原始报价接收过程的缓存种子只能做诊断。已有事件回调可捕获本模块收到的行情时间，但不能冒充交易所源时间或完整的连接健康证据。若确需扩展只读元数据，应单独评估共享路径和冻结边界，保持 FOK 计算及提交行为不变。

验收反例：旧 clobPrice 被保留但缓存 time 更新；HTTP 种子晚于 WS 抵达；book 纠偏与采集混合；未变价的业务回写。上述情况都不能无条件获得新的严格行情年龄。

### A02 合并扫描可能跨过失效行情并错误累计持续时间

位置：执行方案第 140 至 153、182 行。

方案要求合并 250ms 内的变价事件，同时要求任一次无效或不满足都立即归零。若运行时只保存脏盘口、到期读取最新缓存，中间的失效状态会被覆盖。

构造反例：0ms 开始满足，900ms 排名失守，950ms 恢复满足，1000ms 批处理只读到恢复后的价格。若按 0ms 累计，会错误触发“连续满足 1 秒”；实际最近一次满足仅持续 50ms。

修订要求：允许合并 UI 重绘和纯统计更新，但检测输入必须按观察到的事件顺序保留价格、锁盘和失效转移；或者使用等价的保守中断标记，任何无法完整处理的区间结束连续计时。对扫描式来源只能宣称“在各次有效观察中持续满足”，不能声称证明扫描间的全部市场状态。

验收反例：一个批次内满足、失守、恢复；同价锁盘再解锁；队伍方向翻转后恢复；队列丢事件。四者均不能续接原持续区间。

### A03 决策时间与采样分辨率不足以复现模拟入场

位置：执行方案第 140、149 至 151、213 至 222、249 至 255 行。

方案以 1 秒持续条件决定活跃，又设置 0.5/1/2 秒延迟入场，但未规定延迟是从首次候选还是从确认活跃开始。若先等满 1 秒再从首次候选加 0.5 秒取价，就用了当时尚未知晓的持续结果，形成前视偏差。

此外，每地图每秒最多一组截面不能精确复现 0.5 秒时的行情。取 1 秒后第一条快照、再允许 2 秒容忍，可以成为一个明确的粗粒度模型，但它不是精确的 0.5 秒执行延迟。相同问题会影响首次触发、同图一次入场和回访的因果顺序。

修订要求：明确保存 `candidateAt`、`confirmedAt`、`decisionAt`、`scheduledEntryAt`、`actualObservationAt`、`effectiveDelayMs`。可操作决策不早于确认时刻；目标馆选择只使用 decisionAt 当时可见的集合和价格，不能取整个 episode 期间的最高溢价。对延迟入场采用在线定时捕获并持久化不可变快照，或保留有序的关键报价变更日志；1Hz 只用于背景对照和压缩，不承担亚秒回放。分别定义“入场时条件仍成立才模拟”及“固定发单后观察报价”的研究政策，不允许事后择优切换。

验收反例：候选不足 1 秒结束；确认前有好价、确认后撤价；0.5 秒与 1 秒报价不同；主线程延迟 2 秒恢复。每条模拟记录均能证明选择和价格在实际决策时已经可见。

### A04 记录清理会在研究完成前删除关键证据

位置：执行方案第 222 至 228、259 至 267 行。

方案设置最多 50 万条记录，并在触顶时直接清理旧记录；研究目标却需要至少 14 天、200 场比赛、500 个 episode，以及结果追溯和时间切分。现稿只有人工导出能力，没有持久归档成功再删除的契约。

按每地图每秒一条、持续记录且不压缩计算：

| 同时观察地图数 | 50 万条约可保留时间 |
| --- | ---: |
| 1 | 5.79 天 |
| 10 | 13.89 小时 |
| 50 | 2.78 小时 |
| 100 | 83.33 分钟 |

事件、回访和 200MiB 限制可能使实际保留时间更短。静默压缩可能降低使用量，但当前没有压缩率证据和最坏情况约束。记下“数据已淘汰”不能恢复原始报价、探索集或待结算记录。

修订要求：把 IndexedDB 定义为有界缓冲，并明确可核验的归档流程、连续批次编号、校验和、覆盖区间和重复导入规则；归档未确认前暂停新研究采样并标记缺口，或者采用明确的固定容量研究批次。保护未结算记录、首次决策快照、配置版本和分析集归属；完成归档后才回收原始数据。若浏览器不能支持所需周期，应调整研究规模或另行设计采样存储，不能宣称仅靠当前上限完成长期验证。

验收反例：100 地图高频变化超过 83 分钟、归档失败、浏览器重启、配额不足、结果晚到。已纳入研究的关键样本仍能从归档完整重建。

### A05 对照设计混合了嵌套样本与无共同支持的控制变量

位置：执行方案第 238 至 245、255、263 至 269 行。

主策略 A 是基础集合 B 的子集，直接把 A 与包含 A 的 B 作独立组比较会重复使用样本。方案虽要求单列 B 中未入 A 的样本，但同时要求控制“领先幅度”。独占最高由 leadPct 的符号及容差决定，在同一精确领先幅度上通常无法同时找到入 A 与未入 A 的样本；按该变量精确匹配无法识别排名条件的增量价值。

此外，A 与 B 若分别取各自首个合格 episode，可能选择不同时间、不同方向或目标馆，不能把结果差直接归因为排名条件本身。

修订要求：将问题拆为两项。策略比较使用同一预先定义的比赛地图机会池，分别回放“只要求溢价”和“另加高赔排名”的完整决策政策，按比赛聚类比较政策结果，保留不下注与不可观察状态。描述性条件比较使用 A 与互斥的 B\A，并控制决策前可获得且有共同支持的游戏、时间段、赔率区间、目标馆和数据质量；leadPct 作为策略变量或分层展示，不要求在其确定处理状态的值上作精确匹配。避免将观察性差异表述为因果证明。

验收要求：基础组与主策略组各自的决策分母、未入场数量、相互重合情况和按比赛聚类的差异均可复现。同一条样本不会被当作两个独立观测贡献置信度。

## 3 P2 需在对应阶段完成前修订的问题

### A06 地图和盘口状态的资格判定缺少可实现契约

位置：执行方案第 13、101、120 至 124、174、284 行。

方案要求地图未结束、结算一致并把 `ViewBet` 当作主要入口，但当前 `ViewBet` 不保留 `BetRowDto.Status`，没有明确的地图已结束字段；`isLive` 仅在地图与 liveRound 相等时设置，非 live 不等于尚未开始。`ViewBetItem.sourceStatus` 与赔率条目的 `isLock` 又是不同层次的信息，`getOdds` 本身不判断前者。

仅检查地图编号大于 0 和两侧有效数字，无法证明该地图尚可观察或该盘口属于指定获胜玩法。反过来，也不能未经平台语义核对，一律拿聚合 Locked 否定某个有效单侧报价。

修订要求：P0 输出逐游戏、逐平台的市场资格和状态判定表，区分盘口开放、暂时封盘、已结束、未开图、未打图、身份变更及未知；为冲突状态规定保守优先级。核对玩法和结算规则的映射结果应版本化，未核实只进诊断。不能仅以 `isLive !== true` 把过去地图当成赛前样本。

### A07 未区分跨馆潜在套利和场馆概率口径差异

位置：执行方案第 71 至 95、197、238 至 245 行。

示例的 PM 高赔 3.00 与 RAY 相反侧 1.52 已满足：

```text
1 / 3.00 + 1 / 1.52 = 0.991228... < 1
理论双腿毛回报率 = 1 / 0.991228... - 1 ≈ 0.885%
```

这是报价层面的潜在双腿套利，不保证费用、深度、受理和实际成交后仍可套利。若不标记该类状态，可能把既有跨馆价差带来的效果解释为独特的单边筛选价值。原方案只隔离 PM 内部 `S < 1`，没有同等清晰的跨馆标记。

此外，高赔排名受各馆利润率及 PM 买卖价差影响；只存 PM 的 S、不报告各目标馆双边隐含概率和，会削弱对排名增量价值的解释。

修订要求：为原始信号增加 `crossImplied = 1/H + 1/T` 和潜在套利分类，保留原信号定义，研究时分别报告套利区间与非套利区间；不能把标记接到经典 FOK 的拒单链路。目标馆双侧齐备时同时报告其 overround 与归一化概率差，bid/depth 缺失时保持未知。数学归一化只用于敏感性分析，不能升级为真实胜率。

### A08 样本外判定规则与多参数选择尚未固定

位置：执行方案第 263 至 269 行。

现稿要求稳定正向证据和置信区间，但没有固定主要指标、置信水平、最小有意义优势、候选参数数量，以及验证集在 60/20/20 划分中承担什么作用。多个游戏、场馆、溢价和延迟组合中挑最佳结果，即使最后只看一次保留集，也可能因选择与样本不足得出不稳定结论。

每条赔率不同的样本也不能仅用一个未定义的“盈亏平衡胜率”判断策略；最大回撤需明确单位本金、并发持仓和按决策时间或结算时间的记账方式。

修订要求：P4 采样前固定一个主要报价模拟 ROI 和一个排名条件增量指标，指定聚类置信区间方法与水平，声明最低优势及允许的缺失率。探索集选参数，验证集只用于预定的筛选或稳健性检查，最终参数和适用范围在保留集之前锁定；报告全部已尝试组合。逐单使用对应赔率和成本计算损益，给出资金记账规范。200 场比赛或 500 个 episode 只能作为收集目标，不自动成为统计放行条件。

### A09 持久化和观察队列缺少背压与失效规则

位置：执行方案第 165 至 167、182、224、328 至 330 行。

限制 IndexedDB 总记录数、UI 行数和最终内存目标，不等于限制待写队列、导出缓冲、待回访任务和事件积压。存储事务变慢或长期配额错误时，如果队列继续增长，模块仍可能影响主线程和现有行情消费者。

现有降赔运行时已经有队列长度和单任务批量限制，可供设计参考，但不能照搬其扫描生成的时间作为真实行情接收时间。

修订要求：分别规定待处理事件数量与字节数、单次处理时间、待写批次、回访并发、导出分块和最长阻塞预算。溢出时记录明确的数据缺口并使受影响连续区间失效；禁止丢事件后继续宣称完整观察。定义 quota、事务失败、旧版本数据库、导出取消和关闭模块时未完成写入的处理。

## 4 已通过的设计检查

- PM 高低侧定义、同队比较、赔率溢价公式及主客对称逻辑正确。
- `fairLow = 1 + L/H` 的归一化推导正确；示例的 3.45%、4.83%、2.07% 和 PB 参考收益约 -0.22% 已复算。
- 将赔率溢价与真实 EV 分开，不对单边收益扣除未发生的 PM 交易费用，方向正确。
- 不把缺失报价当成 0，不在缺馆时静默缩小比较集合，历史与当前报价分开，原则正确。
- 默认关闭、独立扩展、无需签名器、不增加订阅或 HTTP 深度请求，以及不把观察条件加入经典 FOK 拒单链路，符合仓库约束。
- 明确把真实下注留在后续独立阶段，当前可以先核对数据和研究可行性。
- 前端测试路径可由现有 Vite 测试配置匹配；根 package.json 中所列类型检查、边界和 FOK 保护命令存在。命令存在不表示本次已经运行通过。

## 5 修订顺序与完成标准

先修 A01、A06，明确数据到底能证明什么；再修 A02、A03，固定观察事件与决策时序；随后修 A04、A09，确保研究证据能够留存且资源受控；最后修 A05、A07、A08，锁定分组、分类和结论标准。

P0 应补交一张字段能力表，至少列明每个场馆的原始价格来源、接收时间、源时间、状态、连接证据、市场资格、结果身份，以及缺失时的分类。不能把未解决的 P1 自动带到后续阶段，靠 UI 标签补救。

P1 至 P3 的新增验收反例应覆盖本报告列出的时间线、来源混写、亚秒采样、归档失败与积压。策略验证必须先写入可执行的分析契约，再开始最终保留集采样；对不确定的参数和数据等级记录版本，不回填旧样本。

完成上述修订不意味着策略获得盈利证明；它意味着观察结果可以被复现、质量限制明确、后续验证不会因已知设计缺口而失真。
