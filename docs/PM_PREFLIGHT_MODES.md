# PM FOK 预检：经典预检与动态复核预检

[changmen 扩展] 当前实现截至 2026-10-16。默认、缺失及非法配置均使用经典预检（`legacy`）；动态复核使用 `optimized`。保存配置后对新 FOK 尝试生效，每个尝试冻结方式，切换偏好不改变在途尝试。GTC 不读取此开关。

本轮按用户要求缩短动态复核的成交判断路径：核心只等待最新订单簿，校验冻结限价内能否买足本轮金额。保留本地已知锁盘、赛事终局和最新不利报价的否决。经典预检的查询、判断、默认设置和提交语义不变。

## 当前流程

| 阶段 | 经典预检（默认） | 动态复核预检 |
| --- | --- | --- |
| 候选阶段 | 冻结方式，不预热 | 冻结方式，不再预热 Gamma |
| 钱包 signer | 账号加载、解锁时预热；预检保留原有自动初始化、等待在途初始化和失败后重新尝试能力 | 账号加载、解锁时初始化，交易路径不初始化或等待初始化 |
| 自动套利提交准备 | 校时在 PM 预检中与其他任务并行 | 启动任何一条腿预检之前读取现成 signer、完成校时；失败则两腿都不检查 |
| 手工及失败腿重试 FOK 准备 | 沿用原流程 | 账号网关在附加检测报价前准备校时；直接调用 adapter 的调用方须先准备 |
| 入口检查 | 本地赛事终局、输入、单次尝试 | 相同；已知锁盘也可在拉簿前拒绝 |
| 订单簿 | 每轮读取 HTTP `/book` | 相同，不引入旧订单簿缓存或 WS 卖一代替完整深度 |
| Gamma 市场 | 每轮调用查询，无专用短缓存 | 不查询 |
| Gamma 赛事 | 沿用原 45 秒条件补查 | 不查询 |
| CLOB 市场接单状态 | 每轮查询，明确拒绝时拦截 | 不额外查询；订单簿明确报停单仍拒绝 |
| 深度与价格 | 限价内逐档累计，校验金额、tick、最小份数、深度倍数 | 相同 |
| 异步等待 | 拉簿、状态检查、校时、钱包准备全部结束后汇总 | 只等待本轮订单簿；准备不齐立即失败，不补等校时或钱包 |
| 拉簿后的复核 | 沿用原流程 | 再读本地赛况、锁盘、更新的卖价 |
| 提交前 | 核验准备结果、绑定、钱包、校时、tick | 相同，并保留双腿发送前、PM 提交入口及发送锁后的本地复核 |

经典的 45 秒仅是是否补查 Gamma 赛事的条件：没有本地赛况则补查；已有快照超过 45 秒，且已开赛、已结束或临近开赛时补查。它不是等待 45 秒。经典保留极端价格软拒，CLOB 未知状态沿用原语义。

[changmen 扩展] 2026-10-16 兼容修复：经典 FOK 在凭据有效但 signer 缓存为空时可自行准备，不再要求用户重新加载账号或再次解锁。准备与原有拉簿、校时并行；锁定、账号撤销或凭据变化仍使本轮失效。GTC、动态 FOK 和实际提交阶段不增加自动初始化。历史赛果另在后台补查，下一轮正常订单同步保存，不占用自动下注的余额就绪门控。

动态复核不再要求 Gamma 在 2 秒内、CLOB 明确允许接单才通过，也不再做 Gamma 0.10/0.90 冷门过滤。这是本轮明确改变的策略：用当前订单簿判断价格和足额深度，其他本地明确否决仍生效。未知状态不等于确认可交易；预检不承诺实际撮合时一定成功。

## 成交判断和时效

两种方式仍共用 `fok/preflight.ts` 的盘口计算：校验资产和版本，按价格排序卖盘，过滤检测上限以外的卖单，逐档累计可用金额；深度倍数启用时检查对应缓冲量；根据冻结检测上限对齐 tick，并校验实际签单份数。金额或账号、路由、报价在预检期间改变均拒绝，准备结果单次消费。

动态复核的本地报价检查只能否定旧结果：锁盘直接拒绝；比本轮 book 接收时间更新且高于冻结限价的卖一拒绝。价格不变不证明数量仍足够；本轮没有新增持续完整深度缓存，也不在提交前重新拉簿。明确本地终局即使发生在拉簿或发送锁等待期间也会拦截。

自动双腿仍并行预检，等待两腿完成后才提交；传统腿优先时仍先提交传统腿，成功后才提交 PM。`checkTimeout` 仍在双腿预检返回后判定，本轮未修改该公共行为。

## 准备与计时边界

`prepareOptimizedFokExecution` 只读取已有 signer，并准备校时。自动套利在 `checkArbLegs` 启动任一场馆检查前执行，仅作用于动态 FOK 的真实执行腿；9999 仅检查腿跳过。校时缓存有效时无需网络查询，最长约 2 分钟。若准备期间账号或钱包被更换/撤销，本轮失败。

双腿准备完成后使用独立的 `pmDynamicPrepared` 标记避免在并行预检内再次等待。`requireClobConfirmation` 只表达市场状态策略，不能据此跳过准备；失败腿重试即使携带此参数，也须在获取本轮盘口前完成动态提交准备。经典及 GTC 不消费这个准备分支。

准备耗时以 `outbound_prepare`、`stage=before_pair_check`、`preflightMode=optimized` 单独记录，自动流程带 `linkId`。人工调用也记录此准备阶段，但没有双腿；阶段名表示在成交预检之前。冷启动准备仍消耗机会时间，不能从整条链路统计中抹去。此次改变的是传统腿报价核验发生在准备完成之后，避免传统腿先检查好再等待校时。

动态热路径在开始拉簿前只读检查 signer、校时；准备缺失直接拒绝，不兜底发起网络准备。经典及 GTC 的公共并发路径保留原顺序。成功后的订单簿年龄、签名、提交与成交确认仍分别计时。

## 验证与可复现对比

本轮保留修改前的预检入口及状态检查为测试夹具，仅供离线回放和只读 A/B 探针使用，生产入口不导入这些夹具。

- 离线固定时延：同一盘口计算为 250ms、状态查询最慢 1800ms时，修改前等到 1800ms，修改后 250ms 返回。独立冷校时 600ms 计入准备，不能宣称整个尝试只有 250ms。
- 实际公开接口：同一盘口交替运行修改前/后，详细记录见 [本轮对比](./audits/pm-fast-preflight-20261016.json)。只读探针不签单、不下单，不覆盖真实账户和双腿执行。
- 经典、动态共用价格/深度/最小份数/冻结参数回归，并检查两种方式隔离、GTC 独立行为以及准备完成前不会启动传统腿检查。

`scripts/verification/pm-fast-fok-increments.json` 登记本次精确增量与测试基线哈希；还原后继续通过既有账户、优化方式、公共预检及原 FOK/VPS 基线，不替换旧注册表。经典赛况模块与服务端 `pm_sport` 输入链不修改。

开发浏览器复测：Vite 的 `/devtools/pm-preflight-latency.html`。Node 复测：在 `client/web` 运行 `PM_PREFLIGHT_LIVE=1 PM_PROBE_COMPARE_FAST=1` 对应的 `pmPreflightLatency.live.test.ts`（PowerShell 使用 `$env:` 设置）；可指定 `PM_PROBE_EVENT_ID`、`PM_PROBE_MARKET_ID`、`PM_PROBE_ROUNDS`。默认测试跳过真实网络探针，报告保存在 `output/pm-preflight-latency/`。

此前测量见 [早期诊断记录](./audits/pm-preflight-latency-20261016.json)，其中的 Gamma 策略与耗时描述属于本轮改造前，不代表当前动态实现。
