## 已实现的消费者保护

`ORDERS_EXECUTION_COMPAT` 默认关闭，未修改环境开关。设为 `1` 时，在监听及后台任务开始前只读验证 schema；缺列、错误类型/默认值、无效约束/索引、变更的校验/删除函数、错误视图或禁用删除触发器都拒绝启用。新 DDL 未加入自动迁移链，交易调用不会执行它。

增量迁移不修改、改名或删除旧字段，也不改原主键/唯一键/外键。生产只安装七列及明确获准的 37 条非权威副本，资格保持 TRUE，没有 FALSE 行或控制源切换。未安装控制删除保护，旧硬删及财务集合保持。下述视图、删除保护和启动验证为本地完整阶段二实现，尚未部署或在生产启用；实际平台下注全流程和完整切换仍须后续验收。

财务消费者使用可更新的 `orders_financial` 视图，只包含 `financial_ready=TRUE` 和原 DTO 列集。用户/账号/日期/模式列表、COUNT/分页、排行/月报、Pending/PF 账本、后台诊断及 PM 两侧 JOIN 都在 SQL 中先过滤；原公式、金额、阈值、排序和业务资格保持。控制 payload 不经 SELECT * 暴露给旧财务消费者。

普通及 GTC 列表保存保留原新增/更新资格，但不能把 FALSE 原单晋升或插入同 hash 大小写副本。客户端写入列集没有控制列。真正晋升仍在原 `resolveGtcFinancialOrder` 和“正成交或 FAILED”资格内，与原 INSERT/ON CONFLICT 合成一条 SQL，**不增加查询、await 或数据库往返**；目标主键、库内 hash 拼写及完整控制不改。重复身份的标量查询或执行身份冲突使原事务失败；零成交、费用未知、缺助手、无效财务结果不能晋升。

按 id 删除采用一条排序加锁 CTE：普通财务行物理删除，含控制的原单仅隐藏财务，返回实际财务删除数。重复删除和原先 FALSE 不计数，BIGINT id 保留字符串精度。控制、主键及执行更新时间保留；再次满足原资格时，旧行为相当于“删除后新 INSERT”，所以旧财务账本按原 INSERT 默认值初始化，不能仅因控制存在恢复财务。BEFORE DELETE 触发器拒绝硬删控制及 profile 级联删除；用户生命周期要单独规划，不能以财务删除绕过。

普通 inserted hook 仍只在成功 COMMIT 后对真实新财务 INSERT 调用；UPDATE、未知控制、回滚及 COMMIT 失败不调用，通知异常隔离保持。原 GTC mutate 和专用列表 writer 本来不调用普通 inserted hook，FALSE→TRUE 不新增通知。专用 GTC 保存保持执行 ID 排序；兼容启用后首次读取就用 FOR UPDATE，避免 SHARE→UPDATE 升级，默认模式保持原锁。财务晋升沿用原 ON CONFLICT 的目标更新锁。

75 个活动运维脚本的 181 个 SQL 字面量使用同一财务关系；自建 pg client 的脚本也先验证。完整原源码可逐文件精确还原，参数和默认 SQL 不变。旧硬删工具触及控制时失败；归档脚本没有作为活动工具改造，不应直接用于新 schema。
