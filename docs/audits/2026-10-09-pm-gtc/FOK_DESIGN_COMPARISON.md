# 当前 FOK 与加入 GTC 前设计的详细对比

日期：2026-10-09。对象：当前工作区。性质：只读代码审计及离线差异复现；本轮未修改业务代码。

后续修复状态（2026-10-10）：用户授权修复 F01 / F02 后，已恢复加入 GTC 配置前的 RAY 收尾/监控，并隔离 GTC 成交历史。旧版入口和收尾差异测试均通过。本报告保留修复前证据，以下“当前”指 2026-10-09 审计快照；修复后的结果和未覆盖边界见 [修复报告](./FOK_ISOLATION_FIX_2026-10-10.md)，不能将本报告的历史反例误读为修复后仍存在。

**[changmen 扩展]** 本报告核对 changmen 自身的版本差异，不推断 A8 服务端实现。

后续共享层修复（2026-10-10）：F03 / F04 已按原单身份分流，旧 SQL、分组工具和提前卖出算法恢复基线，并完成临时 PostgreSQL 对照。当前验收结果见 [共享边界隔离验收](./FOK_SHARED_ISOLATION_2026-10-10.md)，以下结论继续作为修复前审计快照保留。

**验收结论：目前不能判定“当前 FOK 与加入 GTC 前绝对一样”。** PM 原有 FOK 适配器函数、主要构单和提交流程一致，但存在已经复现的 RAY 确认时序差异，以及 GTC 成交写入 FOK 共用限制状态的影响。还存在按订单类型增加的数据库和订单分组分支，不能用“FOK 文件没改”替代整个流程的隔离证明。

此前“282 个执行相关文件中 276 个没变”的准确含义是：相对 **V1 前工作区快照** 没变。该快照的 RAY 逻辑已经不同于旧提交，所以这个数字不能证明“与没有 GTC 时的设计完全一样”。

本次交叉核对 306 个文件，其中相对主提交基线 267 个内容一致、39 个有变化（包含测试、类型、展示和导出配置）。提交比较统一换行，函数体比较忽略注释、排版。新增 GTC 文件另行阅读，不算作旧文件相同。

比较行为时固定配置、账号、盘口、时钟及初始历史状态；真实交易导致余额和仓位变化是业务事实。这里重点检查新增执行路径是否额外改变旧 FOK 的算法、确认时序或使用的内部控制状态。

## F01：RAY 确认时序实际不同

位置：`client/web/src/stores/betting/autoBet/phases/finalizeArbBet.ts:152–165`；`client/web/src/extensions/arbBet/rayRejectMonitor/runtime.ts:26`。

旧版 PM＋RAY：

```text
settle → 注册 RAY 监控 → 补单检查 → 成功标记 → 刷新/同步/收尾
```

当前 PM＋RAY：

```text
注册 RAY 监控（initialDetectionPending=true）
→ settle（期间可由新增 1 秒定时器查单）
→ 更新 RAY 监控（initialDetectionPending=false）
→ 补单检查 → 成功标记 → 刷新/同步/收尾
```

运行旧版和当前实际 `finalizeArbBet`，其依赖采用相同 mock：PM＋OB 调用序列一致；PM＋RAY、RAY＋PM、RAY＋RAY 三种组合不一致。双 RAY 由原来的两次注册变为确认前两次、确认后两次。

还存在以下来源相同的差异：首次等待阶段允许对 active 账号查单、增加场馆比赛/盘口及时间窗口匹配约束、保存观察到的单条记录、刷新及绑单顺序变化、首次检测期间抑制后台自动补单及随后交接。

这些变化可能是有意改善 RAY 拒单观察，并不据此断言它们本身有错。但在用户要求“相对旧版本完全一样”时，它们明确不满足验收。它们在开始实施 GTC 时已经存在，不能简单归因为 GTC 引入，也不能在本次只读比较中擅自回退。

## F02：GTC 写入 FOK 共用的限制状态

位置：`client/web/src/orderModes/gtc/runtime.ts:39–50`；`client/web/src/stores/betting/successMarkers.ts:27–43`；`client/web/src/shared/betTiming.ts:73–113`。

`markGtcLegOnce` 调用原 `markSuccessfulBet`，写入：

- `BETCOUNT:<accountId>:<betId>:<side>`；
- `BETACCOUNT:<betId>:<side>`；
- 同账号、同盘口、同方向的 lastOdds 内存状态。

FOK 的最大下注次数、已用账号/同场限制、lastOdds 筛选仍读取这些数据。旧 GTC 订单在用户切回 FOK 后继续核对，计次函数未根据当前模式切断写入。

离线复现固定当前模式为 FOK、账号最大下注次数为 1、启用 lastOdds、准备以赔率 1.8 下注。旧 GTC 原单确认成交 5 份、本金 2.5、手续费 0 后：

| FOK 使用的状态/检查 | GTC 成交写入前 | 写入后 |
| --- | --- | --- |
| 同账号/盘口/方向计次 | 0 | 1 |
| lastOdds | 无 | 2 |
| 最大下注次数检查 | 通过 | 不通过 |
| 当前赔率 1.8 的 lastOdds 检查 | 通过 | 不通过 |
| 已用账号集合 | 空 | 包含该账号 |

该复现执行实际 GTC 计次、实际 successMarkers 和实际 betTiming，仅账号和存储外设使用 mock。它证明的是内部限制状态的影响，未发送交易或依赖真实余额变化。

GTC 将真实成功下注纳入统一账号限额可以是一项业务选择；但若坚持“GTC 对 FOK 完全没有影响”，就必须明确隔离计次、已用账号和 lastOdds。仅增加 `PM_GTC_V1_COUNT` 去重键并未隔离随后写入的三个旧状态。

只在切回 FOK 后停止计次也不足以保证隔离：此前 GTC 已写入的状态仍存在；简单清空则可能同时删除真实 FOK 历史。需要按来源分开存储和读取。

## F03：数据库属于有条件兼容，不能称零改动

位置：`server/db/rds/orders_store.js:109–135`；DTO 在 `server/backend/core/account/order/dto.js:94`。

共享 SQL 新增检查其他账号已保存的同 orderId GTC canonical 记录，并对已有 GTC 行保护 Link、provider、odds、bet_money 和原始成交字段。没有 GTC 标记、也没有同订单号的跨账号 GTC canonical 行时，FOK 更新列仍走原 EXCLUDED 赋值规则，DTO 也不添加 GTC 字段。

不过 SQL 文本、查询计划和混合数据分支实际变化。本轮没有连接真实 PostgreSQL 执行旧/新事务、并发和性能差异测试；因此证据只支持“普通 FOK 数据条件下规则兼容”，不支持“所有数据库行为及性能绝对相同”。

若要求共享持久化路径也保持旧版，应将 GTC 专属写入/保护规则移入其专属保存入口，并另行验证一般场馆同步如何维护 GTC 原单。

## F04：按组处理存在 GTC 条件分支

位置：`client/web/src/extensions/arbBet/arbEarlyLockSell.ts:132`；`client/web/src/shared/orderLink.ts:95`。

纯 FOK 订单组没有 GTC 标记，新增条件不触发，保持原规则。但减仓检查使用“组内任意记录带 GTC 标记就跳过整组”。如果同组数据中同时出现普通 FOK 记录和 GTC 记录，FOK 记录的组级处理也会变化。

本轮没有复现正常创建的两个独立组会发生 Link 碰撞；这里记录的是代码明确存在的混合组条件边界，不能描述成已发生的线上故障。严格验收还需要证明分组身份不会混用，并验证共享展示/减仓逻辑不会处理到另一模式的订单。

## 已完成的验证与限制

1. PM `bet.ts` 原有 29 个函数/方法的函数体与主基线全部一致；只新增 GTC 读取预检结果的函数。完全没有 GTC 选项的基线与主基线之间该文件也没有差异。
2. 对 `checkBetting`、`placeBet`、`executeArbBet`、`runManualBet` 去除新增 GTC 分支、按 FOK 选择原条件后，AST 函数体均与旧版一致。手动弹窗转换为带选择器的 Vue 节点属于已知 UI 变化，比较时还原消息表达式；此项不证明 UI 字面一致或新增初始化完全没有耗时。
3. 实际旧/新自动入口完成 16 个相同外设和时钟的差异测试：默认、遗留激活、未正式激活/外账号激活、prepare/check 返回空、各阶段异常、单腿 9999、非 PM 组合、赛前及折叠过滤、9999 预检失败和异常释放。调用顺序、数据、指标及错误收尾一致。
4. 自动入口的 finalize 依赖在上述 16 场景中是 mock，不能用入口通过证明真实收尾相同。因此单独执行旧/新真实 finalize，得到 F01 的不同结果。

## “完全一样”验收尚缺什么

若以旧提交为严格基线，至少需要处理 F01 和 F02：保留旧 FOK 的 RAY 时序，或明确将 RAY 改动作为独立版本差异；将 GTC 成交历史与 FOK 内部筛选状态按来源隔离，并验证切换前后都不污染。

F03、F04 需要证明共享层的混合数据边界兼容，或将相关新规则收敛到 GTC 专属路径。新增手动选择器和旧 GTC 挂单持续查询是已经要求的功能变化，应与 FOK 交易行为保持一致的验收口径分开。

用户提出“编排层调用，配置决定 FOK/GTC 执行路径，按钮由原订单类型决定”是合理的隔离方向。当前核心下单分支已经接近这个结构；剩余影响主要发生在共享收尾、共享成功标记和共享订单持久化/分组层，不能只检查 PM 请求体。
