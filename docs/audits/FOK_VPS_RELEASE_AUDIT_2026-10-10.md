## 已复现的不一致

`audit-fok-runtime-boundaries.mjs` 执行 VPS 捕获的手动入口与选号器、当前手动入口与实际选号器，以及当前订单 transport。FOK 外部提交用测试替身记录调用，不发往平台。保存故障检查使用 VPS 的实际 `handleSaveOrder` 和 `saveOrder` 函数，纯合并助手及数据库以固定替身隔离；不以财务助手替身证明财务等价。

### 手动共用账号轮转：通过，撤销原异常判定

两个同等可用 PM 账号为 101、102。没有任何成交、余额和订单数量变化：

- VPS 单次 FOK：使用 101；当前单次 FOK 也使用 101。
- VPS 先打开一次手动窗口并取消，再下 FOK：使用 102。
- 当前先打开手动窗口，选择 GTC 并取消，再下 FOK：同样使用 102。实际选号调用、取消及轮转状态序列与 VPS 对照一致。

用户明确 GTC 与 FOK 都是下注模式，可以共用账号选号状态。原 VPS 手动入口也在金额窗口前选号，取消仍推进轮转；这是原选号规则，并未因为 GTC 改写。独立执行路径不要求复制账号池或隔离所有公共状态。

此前将 VPS 的一次 FOK 操作与当前“取消一次 GTC，再下一次 FOK”的两次手动操作比较，操作次数不相同，不能据此认定破坏 FOK。这项发布阻塞已撤销，不修改产品选号逻辑。

### 1. 没有任何 GTC 订单也增加普通订单读写调用

正常 FOK 页的调用链为 `原订单读取 → GTC 身份查询`。普通保存也先查询 GTC 身份。原 VPS 没有这些查询。身份查询顺利返回时可保持结果对象和内容，但调用与等待已经不同，不能称完整运行一致。

### 2. GTC 身份查询不返回，会拖住 FOK 订单页

原订单读取已经完成，GTC 身份查询保持 pending。VPS 原读取会返回；当前 `getOrders` 仍不返回。`.catch(() => [])` 只能处理明确拒绝，不能处理尚未结束的查询。

### 3. 身份异常时额外严格读取改变普通保存结果

给两个版本相同的普通订单读取故障序列：第一次严格读取成功，第二次严格读取失败。

- VPS：`原保存 → 严格读取一次 → 普通 upsert`，保存成功。
- 当前：`GTC 身份查询异常 → 额外严格读取成功 → 原保存 → 第二次严格读取失败`，返回“保存订单失败”。

不能简单在身份失败时将未知历史订单全部当 FOK：原 upsert 覆盖 `raw`，可能丢失历史 GTC 身份或用未完成的成交快照覆盖成本。需要重新收敛订单身份的传递边界，避免让 FOK 依赖 GTC 专属 I/O，同时保留历史 GTC 的正确归属。

剩余三项未通过检查对应一个主要设计问题：**GTC 身份协调进入了普通 FOK 的读写路径，新增等待和故障影响。** 共用账号轮转不属于这类故障依赖。

## 既有差异的逐类复核

- `runA8ArbRound` 只改执行入口 import；原自动 FOK 实现不改。
- 手动入口拆出执行尾部，FOK 单路径专化与 VPS 对齐；相同手动操作次数下，公共前置选号与取消规则也与 VPS 一致。
- 普通 `api/order`、`orderStore`、`account/order_store`、原 DB 订单 writer、费用/币种/成本/盈亏助手，与 VPS 原源码一致。
- DTO、管理端订单映射和类型仅在历史 `pmGtcExecutionId` 存在时附加 GTC 字段；原订单计量算法不另建一套。
- 自动卖出扫描通过模式订单来源过滤历史 GTC 原单，原扫描体与卖出实现不改。新增 GTC 真实订单仍属于普通订单统计，不通过改变 FOK 原计数公式掩盖输入变化。
- 用户设置仅在已激活 GTC 的自动模式下核对 GTC 恢复，FOK 设置保存不调用该恢复门。
- 新 GTC 执行、历史、协调、adapter 分支位于独立模块，但模块文件位置独立不足以证明共享入口没有副作用。
- 管理端进度、日志、工作区展示，普通订单的附加详情与滚动容器属于新增 UI；没有声称其 DOM 与 VPS 字节一致。
- 共享包 exports、API actions 与 DB index 增加 GTC 入口，原 exports、依赖版本和锁文件保留。后端 package 的仓库地址元数据及测试命令差异不改变 FOK 执行。

另外，历史恢复仍监听 `gtcOrderProjection`；普通页面现在加载的是公共 `orderStore`，普通加载不会写回该旧投影。既有恢复测试构造旧投影，不能证明真实普通页加载历史单后的恢复链。此项属于历史 GTC 的恢复缺口，不用它解释或豁免上述 FOK 不一致。
