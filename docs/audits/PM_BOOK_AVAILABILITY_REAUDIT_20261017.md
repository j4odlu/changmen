## 两个根因与修复

前轮 160 次合成预检的本地候选为 46（28.75%）；114 次回退中，元数据未知 48、处理位置已前进 47、过期 9、等待快照 10。该口径是固定资产、合成金额/限价的来源模拟，不是真实用户命中率或双腿成交率。

### 元数据与深度有不同的生命周期

旧消费者仅从每 3 秒一个资产的 HTTP probe 学到约束，再等 1 秒报告交给主线程；16 个资产一轮约 48 秒。此前实际预检已得到的 HTTP 约束没有复用，消费者兴趣变化又会清空全部元数据，深度快照过期也会删除仍新鲜的约束。

本轮：

- 从**此前完成的动态 HTTP 预检**复制白名单标量 `version/tickSize/minOrderSize/negRisk`，在消费者内按原参数校验函数重新验证。原 HTTP 路径已按本次 token 验证资产；Worker 还要求本次开始时存在簿、市场一致、没有跨失效/兴趣代次、当前仍关注资产，且 HTTP 开始时间晚于元数据失效屏障。没有身份/代次证据则不复用。失败、tick 特殊路径、无快照、无效或过期参数不补缓存。
- 元数据年龄以原 HTTP **开始时间**为准；过晚、乱序完成不能覆盖更新的元数据。probe 也改为保守地按开始时间计龄。每次模拟仍在自己的 HTTP 开始前冻结元数据，本次成功结果不能反过来把本次回退改为本地候选。
- probe 仍每 3 秒、最多一个在途、5 秒取消；优先缺失/过期参数，再选最老参数，不增加请求频率。没有新增 HTTP 端点、WS 或预检现场等待。
- 元数据变更以一个合并微任务在当前 FIFO 批次结束后发布，省去最多 1 秒的定时报告滞后；报告与集合仍有原有大小上限。
- 兴趣变化只删除离开集合的缓存；深度 `snapshot_expired` 不自动删除独立 HTTP 约束，**不改变其原始时间**。深度仍不可读，必须等新 WS 完整快照、市场一致且全部年龄检查通过才能使用。tick、连接、间隙、坏帧、处理预算失效等仍撤销元数据。HTTP 结果不会给 WS 建簿或刷新深度年龄。

元数据继续归动态消费者管理；公共订单簿核心不导入 HTTP、预检、账号或签名器。

### 在原预算内追上输入，不放行落后的簿

旧完整读在 Worker 回复返回途中，只要主线程收到任一新帧，就立即 `stream_advanced`。该共享流包含其他资产，连续输入造成大量可恢复的异步往返竞争。

现在收到落后响应时，将重读请求排在已经收到的**全部原始消息之后**。Worker 继续逐条按原 FIFO 处理，再读取当前完整簿。最多追加 3 次重读，共最多 4 次读取，仍共用一次原 20ms 截止时间和原 32 个在途额度；不重置 timeout，不提高队列/CPU/新鲜度上限，不在主线程另行解析行情，不省略消息，不重排增量。

最终接收及 `isCurrent()` **仍要求已处理位置等于当前全部输入位置**；目标资产更新须读到更新后的深度，其他资产消息也须处理后才能接受。继续前进而追不上、超时、失效、释放或断线均回退。`catchups/recovered/exhausted/timeouts` 记录成本与原因；`recovered` 是完整读成功追上的数量，不必然等于通过后续计算的候选数。

未改变：接收年龄 1 秒、完整快照 60 秒、元数据 60 秒、源时间落后最多 5 秒/超前最多 1 秒，以及 Worker 原处理预算。没有把本地接收位置冒充交易所连续序号。

## 结论和边界

**两个主要未命中机制已修复并获得测试、真实浏览器旁路证据。可继续限定 1 位直连动态用户的受控生产旁路观察；本轮不发布、不替用户开启，不扩大既有灰度范围。真实本地预检仍 NO-GO。** 经典 FOK 原路径及默认方式不变，实际动态预检也仍 HTTP。

继续灰度只能在另行获准发布后由用户显式开启本地簿及动态对照。先观察前台；本轮没有重跑新重读/元数据链路的原生后台、冻结、休眠与 24h，也未做全页+Worker 总 CPU/堆 A/B。可比计算仅 58 条，未满足真实机会样本量、长期覆盖、全尝试加权延迟和双腿成交收益门槛。旧后台证据不能代替本轮新增接口的后台性能验收。

后续主要瓶颈是原有新鲜度限制下的静默盘口与完整快照缺失。维持回退，不放宽年龄、不拿 BBO/成交更新深度时间，也不擅自补订阅/重连。若可比差异出现、队列/CPU失效持续增加、原行情明显变慢或经典异常，立即关闭“本地订单簿”；只停诊断可关闭“动态预检对照”。关闭不停止原 PM-M、不增加或替换原 HTTP。没有真实快路径开关。
