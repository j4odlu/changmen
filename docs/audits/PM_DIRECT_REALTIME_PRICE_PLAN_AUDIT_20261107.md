[changmen 扩展] 2026-11-07。状态：**审计完成；原方案需收敛后再实施**。审计对象为 [PM_DIRECT_REALTIME_PRICE_PLAN_20261107.md](../PM_DIRECT_REALTIME_PRICE_PLAN_20261107.md)。本轮核对官方文档、已安装 SDK 源码及公开 API，并进行离线模拟；没有修改行情或交易业务代码，没有真实网络性能或官网浏览器实测，没有提交、push 或部署。

## 1. 结论与用户确认的目标

用户已明确：对齐的是**同一 token 的官网订单簿可买价格，即卖一 best ask**，不是官网赛事列表的概率数字，也不是任意金额的整笔成交均价。

基础功能可以收敛为：

```text
官方 Market WS → 接受当前 token 的最新有效 best ask → 写入现有 fo → 响应式显示
```

原项目已经有这条链路，其网络部分也具备心跳、重连及行情事件解析。当前工作首先是修好已有链路的正确性和订阅行为，不需要把完整深度簿、主动恢复队列、交易重试策略一起重建。

审计发现 **3 项 P1、4 项 P2**。P1 是方案实施前必须闭合的设计问题，P2 是会扩大范围或降低方案可靠性的设计问题；它们不等于已经证实对应生产事故。最小改造建议见第 6 节；后续实施以本次明确目标和修订方案为准，不能直接照原 P0～P5 全量执行。

## 3. 分级发现

### F1 [P1] 未评估已安装 SDK，重复建设网络管理能力

原方案位置：第 2、7、11、12 节。

**证据：**安装版本已经提供资产并集、增减订阅、连接复用、心跳、自动重连和重订。官方文档的公开入口是 PublicClient 的 market 订阅。本轮离线模拟确认其中 7 项公开运行行为。原方案只写“不为本方案升级整套 SDK”，没有列出“当前版本已能做什么”，就安排了大量自建管理职责。

**影响：**把已有协议能力误当作全新基础设施问题，增加状态、发送队列、恢复任务和停止补偿的维护成本；容易出现 SDK 与原 transport 各自拥有网络生命周期的双连接实现。

**修订要求：**先比较“修好现有唯一连接”和“由 SDK 接管唯一官方连接”两个小方案；不能默认两套同时运行。SDK 的订阅、重连职责只需一个所有者。已安装版本足以做本次能力验证，不把整套 SDK 升级当作前置任务。

**能力边界：**SDK 不会替应用合并 HTTP 种子，不会修复 fo 写入规则，也不会替 UI 区分 rawAsk 与 buffer cap。MarketSubscription/SubscriptionHandle 的已检查公开类型未提供 CLOB 连接开闭、原始帧和连接代次回调；不能把源码内部类的方法当成可直接 import 的公共扩展点。若直接迁入 SDK，还须证明原 fallback、tick 输入、marketStream 只读旁路和连接状态可继续正确工作。故本结论不是“换 SDK 就自动解决全部问题”。

### F2 [P1] 对照价格与页面显示值的契约仍未闭合

原方案位置：第 1、9.1、10 节。

**证据：**用户现在明确要对齐 best ask。原第 9.1 节仍要求保持现有主赔率展示，而现有 `priceQuote.ts` 会把 rawAsk 调整成百分比或 +1 tick cap，然后由 cap 取倒数。原文只要求在诊断详情里提供原始价，没有定义页面上“用来与官网比较”的值。

例如：rawAsk=0.35，+1 tick 后 cap=0.36，交易显示赔率=2.777；官网同一 token 卖一应与 0.35 比较。若拿 1/2.777 比较，页面会被永久判定不同步，实际上是口径不同。

**影响：**即使行情完全正确，用户仍可能看到与官网不一致的数字；也可能为使数字相同而误删交易缓冲、改写原冻结价格。

**修订要求：**定义一个直接显示/读取 rawAsk 的实时价格字段，明确它等于本 token 当前被接受的官方卖一；现有执行 cap 和派生赔率保留原交易作用并标明含缓冲。若采用赔率作为对照值，原始赔率与缓冲赔率要明确区分。数字同步验收不使用缓冲价、手续费折算价、官网列表概率或超出卖一数量的整笔报价。

这不要求新增一套大面板；正式实施只需明确现有单元格、轻量旁显或详情中的固定对照位置，并确保从当前 rawAsk 派生。

### F3 [P1] 纠偏排序依赖尚不存在的元数据，且当前时钟风险有确定性复现

原方案位置：第 6.2、12 节。

**证据：**第 6.2 节要求预检捕获请求起点的 revision，返回时携带可信源时间再建立屏障。现有 `PolymarketPriceAboveDetectionError` 只携带 bestAskPrice 与 detectionMaxPrice，`fok/preflight.ts` 创建异常时也未传请求版本或 book 时间。第 12 节未明确列出取得这些元数据的实际执行入口。

当前 `notePolymarketLiveBookQuote` 把本机墙钟写入同一张时间表，随后 `shouldApplyPolymarketWsQuote` 用交易所时间与之比较。隔离检查证明，本机快 5s 时，当前官方事件会被该门槛拒绝。该复现只说明代码存在时钟敏感性，没有证据证明用户机器当时存在 5s 偏差。

**影响：**实现者可能用响应到达时间代替源时间，延续旧问题；也可能让 HTTP、WS 进入无法明确裁决的双写状态，复杂恢复进一步掩盖价格为何被丢弃。

**修订要求：**先明确最小可执行规则及数据如何从现有预检入口传到纠偏入口，再决定是否需要额外类型。至少做到：连接代次隔离；源时间只与同源时间比较；请求开始后已有新 WS 写入时，迟到 HTTP 不直接盖掉它；无可比较时间不假造绝对时序。补充“本机快/慢、重连回包、请求期间新报价”的确定性回归。新增元数据不得改动 cap、金额、预检返回语义或提交行为。

### F4 [P2] 顶层价初始化条件遗漏 price_change，可能引入不必要的等待

原方案位置：第 5.1、5.2、7.2 节。

**证据：**官方 price_change 每个变化项可以带 best_ask/best_bid。当前解析器已经读取这些字段。原模型的 `initializedBy` 只允许 book/complete_bbo，第 7.2 节只明确这两种初始化方式，未说明包含有效 best_ask 的 price_change 能否直接使 ask 就绪。

**影响：**如果按该类型严格实施，应用已经收到当前官方卖一，却可能继续 waiting、发 HTTP 或退订重订；报价反而比现有简单更新路径更迟。卖一展示也不需要等待买一同时可用。

**修订要求：**顶层 ask 就绪按“当前连接已经收到明确、有效的 ask”判断，book、BBO 和 price_change 都可以提供它；每侧独立更新。完整深度簿的快照前置要求继续留在原 Worker 中，不能扩散到顶层价显示。

### F5 [P2] 自动补簿与退订重订恢复被提前设为首期必需

原方案位置：第 7.3、8、11/P2、14 节。

**证据：**目前确认的是种子覆盖、空盘过滤、订阅消息与 SDK 标准行为不同、时钟混用风险。尚无实际官方直连原始帧证据证明，改正标准订阅后仍必须执行持续的局部恢复。原方案已经规定 HTTP 队列、并发、速率、两轮退避、cycle、补偿及多个时间阈值。

**影响：**为了处理尚未确认的缺报机制，主动制造退订窗口、额外 HTTP/WS 竞态和取消补偿；使一次价格修复扩大为恢复调度工程。

**修订要求：**首期保留连接状态、逐资产有没有收到报价的可观察性，以及标准重连重订；自动 HTTP 补缺和 unsubscribe/subscribe cycle 降为后续有证据才启动的扩展。安静资产不触发恢复。人工只读核对可以保留，但不自动成为另一价格写入者。

### F6 [P2] 同价重试抑制属于交易策略范围，不能作为显示同步前置

原方案位置：第 9.2、11/P3、13、15 节。

**证据：**原方案会改变新套利尝试准入，并以 priceRevision/失败 cap 抑制后续尝试。正常显示同步只需要修正当前 rawAsk、传播明确空侧、让 UI/建腿读取现有共同入口，不需要新建交易抑制规则。

**影响：**预检提示可能减少，但价格未必更实时；同时引入“何时解除抑制”的新正确性问题。仅价格版本不足以表达其他腿、配置和账户等交易条件改变。原文虽然已经提示该风险，仍把它列入本期完成要求。

**修订要求：**本期保留已存在的冻结报价与 HTTP 预检规则，先验证纠正后的 rawAsk 是否及时进入新尝试。只有修复后仍有可复现的重复触发问题，才单独设计重试控制，并对其业务范围做完整回归。

### F7 [P2] 新的完整状态层和验收体系超出最小必要范围

原方案位置：第 4、5、10、11、12、14 节。

**证据：**UI 与建腿现已共同读取 `oddsStore.getPmQuoteEntry`，BetRow 也已按 oddId 响应式更新；不是每次都等 30s 或整表刷新。原方案新增一套状态与 store 投影，包含双侧来源、多个 revision、代次、suspect、恢复队列、功能门控、旁路录制及六个阶段；指标中的具体毫秒和覆盖率阈值没有本机基线支撑。

**影响：**重复缓存的所有权更难解释，改造面和开关组合明显扩大。固定指标和采样门槛可能成为先完善观测平台、再修已知覆盖问题的障碍。

**修订要求：**优先在现有单写入口及 PM 条目中增加够用的来源/连接代次/是否有价元数据，保留原始价和派生报价边界。只在现有模型确实无法表达时新增小型纯函数模块，不预设整套状态服务。首期记录四类证据：输入卖一与 fo 一致、fo 与 UI 一致、种子/旧回包没有覆盖、实际接收到显示的延迟。高负载 P99 和长时间覆盖统计作为后续性能验证，不能伪称官方 SLA。

## 5. SDK 采用方式的判断

| 选择 | 能解决什么 | 仍要自行解决什么 | 审计建议 |
| --- | --- | --- | --- |
| A：保留现有唯一 transport，按官方协议/SDK行为修订阅与报价写入 | 改动最小，保留现有 fallback、tick、原始流及连接状态接口 | 资产差集、清价、种子保护、纠偏时序 | 当前问题优先采用；不是继续保留错误的重复 market 帧 |
| B：让 SDK 公共 market 订阅替换官方分支的唯一 transport | 复用连接、订阅、心跳、重连等已实现能力 | fo/UI 合并；与原 fallback、raw stream、连接生命周期的衔接；包体和队列行为验证 | 可减少后续网络维护，但先做小型集成验证，再决定是否替换 |
| C：在原连接旁边再启动 SDK 订阅来“补实时” | 短期可能看到更多帧 | 双写、重复订阅、不同连接顺序、资源与生命周期 | 不采用 |

SDK 的每个 PublicClient 有自己的管理器；不能在每个组件创建 client，再把这些连接误称为“SDK 会自动全局共享”。公共异步迭代器输出为 `type/payload/bestAsk`，原网络帧解析器处理的是 `event_type/best_ask`；B 方案需要明确一次标准化适配，不能把 SDK 事件 JSON 化后直接喂旧解析器。

SDK 会对事件做 schema 校验，并过滤不匹配输入；它不是本地订单簿维护器，也不提供对原应用所有状态的自动正确性保证。对 SDK 的使用应限定到已验证的公开能力，不能导入未导出的内部 manager、劫持全局 WebSocket 或建立隐式第三方连接。

## 6. 建议的最小修订方案

### S1：把“官网卖一”固定为可测量字段

- 同一比赛、盘口、方向和 token 对照；明确官网订单簿卖一，并记录卖一数量。
- CHANGMEN 对照字段直接取 rawAsk；缓冲 cap 和套利显示赔率保持原公式，不反推三位赔率还原原价。
- 快照/book 的 asks 从有效档位取最小值；BBO 和 price_change 直接接受当前 best_ask；成交价不写入这个字段。
- 保留现有按 oddId 更新及 UI/建腿共用入口，不增加全表刷新。

### S2：修复现有报价写入与订阅

- 修正 HTTP 初始化覆盖、预检纠偏来源和 clean 后的元数据保留；明确空卖盘清价，并关闭旧 fallback 复活路径。
- 官方连接的首次 market 与后续 operation subscribe/unsubscribe 分开，按消费者并集维护最小差集；重连按最新集合重订。
- 每个 token 有有效 ask 即可更新页面；记录缺报，不要求先建完整本地簿或双侧全齐。
- 修复时钟混用及旧连接/旧 HTTP 回调写入；预检所需的最小关联元数据在实际入口明确定义。
- 原 FOK/GTC 判断、cap、金额、提交、确认继续沿用；不新增自动补簿和交易重试抑制。

### S3：只读验证与完成判断

必须通过的确定性场景：

1. 官方连续报价从 0.28→0.35→0.34，fo 和对照字段按同序更新；价格下降也不能被“只许纠偏变贵”的规则永久挡住。
2. 0.28 种子→0.35 纠偏→旧种子刷新/clean，最终不退回 0.28。
3. 明确空卖盘到达时，旧价被清除；其后新卖单到达可重新显示。
4. 新增 token 收到正确增量订阅；移除只发对应退订；多消费者之间不互相误退。
5. 断线重连、旧回包迟到、本机快/慢时间均不能复活旧价或永久拒绝新价。
6. 原始 0.35、+1 tick cap 0.36、派生赔率 2.777 分别对应正确字段，冻结尝试不跟价改写。
7. 关闭该页面/功能后无重复连接和遗留资源；原转发分支仍可使用既有逻辑。
