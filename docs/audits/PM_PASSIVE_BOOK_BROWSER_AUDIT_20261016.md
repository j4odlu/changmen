## 验证范围

- Windows 的真实 Brave 浏览器，UA 为 Chromium 155；独立本机源 `127.0.0.1:5581`。没有操作已登录业务页、生产开关、凭据或订单。
- 从现有电竞 collector 的公开市场发现函数取得候选，按 24h 成交量排序，使用 118 个 token 的原 PM-M 行情订阅；前 16 个作为旁路候选。它代表一组实际电竞流量，不等同于 river 当前列表或全量生产峰值。
- 加载当前 `realtime/ws.ts`、行情 Hub、被动桥接客户端与实际构建产物 `shadow.worker-DwRTGGat.js`。Worker 哈希记录在 JSON。实际 WS 直连官方，所有 HTTP 仅公开 GET。
- 测量到原行情 Hub 的报价回调，不包含完整登录应用的渲染、`fo`/RDS 写入或真实双腿提交。固定基线及相关行为回归另行验证这些共享边界；本次没有真实成交率证据。
- 计时工具在测试页面记录原 `onmessage` 耗时、报价回调时延及 20ms 定时器抖动。冷接入与晚接入是同一条真实连接上的连续阶段；A/B 因果比较使用相同原始消息的 ABBA 回放。

## 真实流量结果

| 阶段 | 时长 | 原始帧 | 原行情报价 | 新建行情 WS / 订阅发送 | 旁路结果 |
| --- | ---: | ---: | ---: | --- | --- |
| 冷接入，先创建旁路后启动原行情 | 90.93s | 53,014 | 101,618 | 1 / 1（原行情） | 第 2.016s 采样已 `stream_overflow` |
| 关闭旁路，连接继续 | 15.21s | 13,695 | 25,672 | 0 / 0 | 原行情持续 |
| 同一连接中途开启旁路 | 90.87s | 60,595 | 116,301 | 0 / 0 | 第 1.016s 采样已 `stream_overflow` |

三个阶段内部均未观察到原行情关闭或重连；最后由测试主动关闭自建连接。开启、关闭和故障没有产生额外订阅。冷、晚接入各创建并终止 1 个 Worker，结束后无自动重建。失败发生在“8 条未 ACK 消息”上：冷接入仅转发 8 帧、191,960 字符；晚接入仅转发 8 帧、8,103 字符，远低于 2,000,000 字符总上限。

两个开启阶段以每 2 秒对 16 个候选做纯诊断读取，各 720 次，共 1,440 次；**可用读取 0/1,440、采样报告中的可用缓存资产 0/16**。这些读取立即以无 HTTP 深度的结果结束，只测 miss/失效原因；不是实际预检、HTTP 请求或成交尝试。旁路已停止，不能用该数字推断“官方不发送快照”。报告中的 `http_resolved=720` 是夹具完成信号，不是 HTTP 性能证据。

同样，`counters.stream_overflow=721` 包含一次桥故障和后续 720 次带该结果的诊断完成，**不是溢出 721 次**。统计故障次数应结合 Worker 终止次数及 failure 转换。

## 官方快照供给与旁路覆盖必须分开

原始帧录制有 20,000,000 字符上限。保存了前约 56.22 秒的 33,155 帧、19,999,948 字符；没有把它当作完整 197 秒录制。

- 214 个完整 `book` 事件覆盖全部 118 个源资产，包括 **16/16 个旁路候选**；同时有 31,108 个 `price_change` 事件。
- 以首帧为起点的 1 秒分桶峰值为 **1,194 帧/秒**，单帧最大 187,695 字符。
- 16 个候选中有 8 个在该录制窗口仅收到一次完整 book。其后是否有刷新没有录到，不能证明 60 秒快照期限之后仍可持续使用。
- 在放缓突发的相同消息回放中，实际 Worker 两轮均维护到 **16/16** 个簿。这证明协议及核心能消费该批数据，不证明原实时到达节奏下的可用率，也不等于新鲜度/元数据门槛全部满足。

四轮完整报价序列 SHA-256 相同：`92b00238633b230c2c374831b7b8404b28630f065c1096eef984dc9310c024c3`。在本机计时分辨率内未看到 P95/P99 回归；**不是零开销证明**，也不是低端设备、后台标签页或整页 CPU/内存基准。

另将前 100 帧在同一任务中连续送入，复现 `stream_overflow`：旁路终止，原报价仍输出 274 条；没有新增订阅、重连或交易错误。该故障用例不是正常流量吞吐基准。

实时开启阶段大部分时间实际已停旁路，因此不能拿其约 0.1ms 的总阶段 P95 宣称持续开启无开销。取证序列化可进入长任务数组，本报告不使用这些数组作实时长任务归因，也不据此宣称内存/CPU 已达生产标准。回放中的 HTTP probe 与旧 WS 时间戳无法对齐，不能拿它验证实盘对账一致率。

## 阻断原因与下一轮门槛

1. **有界桥的突发承载不足。** 正常官方到达节奏已在冷、晚接入复现 8 条未 ACK 队列溢出。失败安全性通过，持续观测能力未通过。需在动态旁路内验证有界批量传递、ACK/排队节奏等处理；必须保留顺序、接收时间、代次隔离、字节和年龄上限及原行情优先。
2. **共享流限速语义不适配。** `PassiveBookFeed` 当前在筛选候选事件之前对整个 PM-M 输入执行 500 帧/秒限制，而本轮实测峰值 1,194。即使桥不再提前退出，超限仍可能使候选簿反复失效。这是源代码与实测负载的联合推断，本次未声称存活的实时 Worker 已测到该计数。
3. **持续有效覆盖率仍未建立。** 接收过完整快照与满足读簿新鲜度、60 秒快照期限、元数据有效期是不同指标。不能用节流回放的 16/16 替代实测，也不能为提高命中率主动重订/重连 PM-M 或用 HTTP 种 WS 簿。

下一轮先处理旁路吞吐适配，再做至少 30 分钟真实浏览器复测，覆盖冷/晚接入、候选变化、快照期限、原连接自然或受控断线恢复、切回经典与后台场景。放行旁路灰度前至少要求：正常代表性流量不再自动停旁路；有持续可比较样本并分别报告资产、时间、诊断尝试分母；同消息报价完全一致；无新增 WS/订阅/重连；HTTP 保真与经典固定基线继续通过。提高 8 条/500 帧限制本身不能作为修复验收，也不能扩大主线程解析或占用来换取命中率。

本轮不授权后续发布或自动开启。即使将来旁路灰度获准，真实预检仍 HTTP；交易快路径和双腿成交率提升需要独立验证及授权。
