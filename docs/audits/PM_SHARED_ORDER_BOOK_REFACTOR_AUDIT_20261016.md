## 实现与职责

```text
原 PM-M → 原报价处理（保持原样）
       → 现有只读原始流 → PmOrderBookService → 单 Worker 中的 BookStore
                                               ├─ 动态对账消费者
                                               └─ 只读深度投影接口（未接 UI）
```

- `client/web/src/runtime/pmMarketData.ts` 是应用会话所有者。原 `pmDynamicWsPreflight.ts` 保留轻量安装入口，改为门控并懒加载该所有者；`installClientCore.ts` 本轮无需再次修改。
- `realtime/orderBook/service.ts` 持有源观察、唯一 Worker、有界 FIFO、资产准入与租约。它只读 `esport` 已登记资产，最多维护 16 个；既有资产可供多个消费者复用，优先保留已接纳的活跃请求，其余容量维护预留资产。
- `bookStore.ts` 持有不可变簿历史、完整性证据校验和深度投影；`passiveBookFeed.ts`、`bookReducer.ts`、`orderedWorkerMailbox.ts` 原算法与限制不变。源码依赖测试证明簿存储核心不依赖预检、账号、HTTP、订单或网络所有者。
- `polymarket/marketData.worker.ts` 是组合入口，装配核心和可选诊断消费者。保留单 Worker，JSON 解析、归并、HTTP 簿解析和比较仍在 Worker；旧 `shadow.worker.ts` 已移除。
- `WsBookShadowRuntime` 注入只读簿端口，不再创建 feed、拥有簿历史或执行 feed reset/stop。可比差异改为提交证据，由核心验证代次、资产与时间对齐后失效。
- `WsBookShadowWorkerClient` 只持有租约和诊断通道，不再创建/终止 Worker 或直接观察源。候选与账号变化仅更换消费者 scope；账号 token 变化本身不销毁公共簿。

深度接口 `acquirePmDepthView()` 不会启动服务，只能从已授权会话取得租约。可更新本地兴趣、读取有限深度、订阅变化、释放自己；没有 stop/reset/订阅/重连权限。返回 sessionId、streamEpoch、簿 generation/revision、年龄、状态和不可变双边数组，默认 20 档、最大 50 档，精确保留十进制字符串与排序，截断标记明确。最多 4 个租约、32 个在途读取、每租约 4 个监听，释放/故障/代次变化会结束未完成的读取。没有消费者监听时不运行投影通知定时器。

## 经典隔离、开关与回滚

两个本地开关都默认关闭，旧旁路开关不自动启用新的总开关：

| 总开关 `changmen:pm:local-book` | 消费者开关 `changmen:pm:ws-book-shadow` | 合格直连动态会话行为 |
| --- | --- | --- |
| 未设/非 `1` | 任意 | 不启动服务或消费者 |
| `1` | 未设/非 `1` | 仅公共簿服务，无动态候选 watcher、HTTP probe |
| `1` | `1` | 公共簿 + 动态旁路对账；真实预检仍 HTTP |

资格仍要求已登录 ready、显式 optimized、官方行情、HTTP/提交直连和合格 PM 账号。经典/default/非法、退出或总开关关闭均停止整个服务；仅关闭消费者开关保留公共簿。线路或最后一个合格账号失效停止服务。Worker 故障保留失败状态，不启动循环重试，不开第二条 WS。

**本轮没有执行生产开启。** 将来获准灰度后，开关仅在明确目标浏览器设置；同页直接改 localStorage 后刷新。完整回滚为删除总开关并刷新；跨页 storage 变化和应用退出会同步撤销本页授权。只关闭消费者开关只能停止对账，不是停止公共簿。关闭不会取消或重写已由原交易流程开始的 HTTP/订单操作。

预检模式仍决定预检规则，不是单纯切换数据来源。经典和动态实际预检均为 HTTP。未修改签名器准备、经典拒单条件、价格/金额/深度、双腿顺序、确认、补单、绑定、后端、VPS 或数据库。

## 代码复审重点与处理

| 风险 | 本轮处理与证据 |
| --- | --- |
| 假拆分：动态仍控制 Worker/feed | 所有权移入 service/store；生产组合入口独立。真实隔离 Worker 测试验证卸载诊断后簿 revision 和深度保留 |
| 只开服务仍发 HTTP | Worker 中诊断消费者按 attach/detach 创建/停止；测试观察无消费者阶段零 fetch，挂载后 probe，卸载后停止 |
| 动态对未订阅资产发 probe | 主线程只将实际接纳的候选传给 Worker；源资产移除后同步缩小消费者资产，新增回归覆盖 |
| 第二个动态消费者被拒后抢占全局观察入口 | 显式记录 consumer_unavailable；拒绝分支不注册/注销已有观察槽，新增回归证明第一个消费者继续收到实际 HTTP 观察 |
| 一个消费者挤掉其他消费者的簿 | 服务统一准入，共享资产复用；容量拒绝明确返回，不挤掉活跃租约 |
| 陈旧 HTTP 或深度响应污染新会话 | scope、源代次、服务 generation、读 session 标签及核心完整性证据验证；释放/代次变化结清读请求 |
| 深度调用方修改共享状态 | Worker 投影有限副本，主线程冻结；不暴露可变 Map 或核心控制句柄，精确小数排序回归通过 |
| 原报价负载回退到逐帧控制/JSON 解析 | 原有批量 FIFO 不变，热帧不扫描账号/配置；源名单定期及控制变化时核对，Worker 内解析 |
| 失败后重启风暴或残留定时器 | 服务失败终止并释放观察/队列，显式新会话才重建；消费者注销停止 probe、比较、监听；无人监听停止投影通知 |
| 为通过兼容检查替换基线 | 551 项固定原始文件哈希仍保留，没有修改基线或豁免目录 |

普通消费者监听器应保持轻量；JavaScript 同步回调无法硬抢占。异常监听会隔离并移除，通知频率和数量有界，不宣称“任意慢回调零主线程成本”。后台调度和字符串复制成本仍需实测。
