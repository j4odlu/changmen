# PM 本地订单簿及动态旁路：实施后审计

> 本文保留**修复前**的五项发现和当时的“不放行”结论。五项问题已修复，当前结论及证据见 [五项修复与重新审计](./PM_WS_BOOK_SHADOW_REAUDIT_20261016.md)：仅允许直连动态用户小范围旁路观察，实际预检仍 HTTP，不开启真实下单快路径。

[changmen 扩展] 审计日期：2026-10-16（Asia/Taipei）。基点：`2bdf3773f5270d96a807d5d077bcd42f6724b1ee` 加当前未提交改动。

**结论：不批准当前版本在生产启用旁路，更不能启用真实下单快路径。** 默认关闭可以继续保留开发；现有经典 FOK 继续使用原执行路径。本次仅审计、复现和记录，没有修改交易或行情实现，没有部署或真实下单。

## 1. 四项要求的结论

| 要求 | 结论及证据边界 |
| --- | --- |
| 经典 FOK 不能受影响 | 原 `fok/`、`submission/preflight/legacy/` 和 `pmBuyPreflight.ts` 无本轮 diff；只有 optimized 分支调用观察插槽。默认/非法模式仍 legacy。369 项相关回归及 551 项固定基线核验通过，未发现已覆盖交易语义的回归。但新增代码仍经公共安装入口注册轻量监听，生产包未做到完全隔离加载；旁路启用时的 CPU 开销与同页业务共用线程，不能表述为“所有场景零影响”。 |
| 本地订单簿是独立模块 | `polymarket/realtime/orderBook/` 核心仅有簿重建、连接和本目录依赖，无预检/账号/签名/下单依赖，代码模块边界成立。但公开状态可被消费者修改，尚不满足可信多消费者服务要求。 |
| 动态预检是其消费者 | 依赖方向正确：动态 `wsBook/bookRuntime.ts` 消费行情核心，核心不反向依赖动态预检。当前消费者仅做影子比较，真实动态预检仍消费 HTTP；不能说真实预检已经由 WS 驱动。 |
| 能否生产 | 不能以当前证据放行生产启用。存在下列五项问题，且没有浏览器持续压力、多个资产、后台标签页或真实双腿 A/B 验收。 |

独立行情模块不等于已有一个跨页面/多消费者共享的行情服务。本轮没有新增全局共享连接，这符合原先保护经典链路的范围；未来需要共享时，应单独设计订阅所有权和消费者隔离。

## 2. 已确认的问题

### A1 — P1：20ms 预算是事后检查，不能限制交易线程阻塞

位置：`realtime/orderBook/bookReducer.ts:77`、`directBookFeed.ts:85–90`；动态同步观察在 `submission/preflight/optimized/pmFastPreflight.ts:57`。

每个增量价位都 `new Map(old[side])`，一次 2,000 条变更会复制 2,000 次整侧深度。feed 直到 JSON 解析和整帧重建结束后才检查 20ms，再发布或失效。因此它限制的是“接受结果”，不是“CPU 占用”。消费者的同步比较还发生在预检返回之前，且不计入 feed 的 20ms 检查。

本机独立复现：2,000 档、2,000 条增量，帧长 122,079 字符，小于允许的 1,000,000 字符；三次同步处理分别为 **137.33、139.79、129.22ms**。这是合成压力输入的本机结果，不是正常行情 P95，但足以证明 20ms 并非硬预算。浏览器主线程启用旁路后，同页传统腿、UI、计时与在途交易回调都可能等待。

修复要求：先消除逐价位整簿复制，每帧每资产每侧至多建立一次工作副本；将重处理移出交易关键线程或引入可取消、分段的工作预算。旁路比较不能把大块计算塞在 HTTP 返回至预检完成的必经同步段。以接近资源上限的多资产输入测最长主线程任务、队列积压及双腿编排延迟。

### A2 — P2：线路短暂切换后，runtime 存在但 WS 永久停住

位置：`wsBook/bookRuntime.ts:64–67`、`client/web/src/runtime/pmDynamicWsShadowWorker.ts:21–24`。

复现：直连运行 → 在 1 秒线路轮询之前切离直连 → WS 回调发现不允许并执行 `feed.stop()` → 在下次轮询前切回直连。前端看到 `runtime` 仍存在直接返回；重新传入同一候选列表也被 runtime 的相等判断提前返回。10 秒后仍只有已关闭的旧 socket，没有新连接，但 HTTP probe 计时器仍运行。

影响：旁路无声停止收行情，报告仍能显示 shadow；如果将来用于 fast path，会持续 miss。该问题不改变当前 HTTP 预检结果。

修复要求：公开并核对 feed 的连接/停止状态，不能用“runtime 对象存在”代表“运行正常”；同一候选的 reconcile 必须具备恢复能力。补充线路快切及页面后台恢复的端到端测试。

### A3 — P2：一个没有快照的 token 会反复清空整组健康资产

位置：`realtime/orderBook/directBookFeed.ts:55`、`wsBook/bookRuntime.ts:50–53`。

复现：订阅 token 1 和 2；token 1 正常返回完整簿，token 2 始终无快照。9 秒时整连接因 `books.size < assets.size` 关闭，所有健康簿、metadata 和在途 probe 全部失效；重连后再次复现。此前 72 秒实测只订阅一个资产，无法覆盖这个场景。

影响：已结束/不存在/无返回的候选拖累同组其他市场。16 个资产的预热和 metadata 有效覆盖可能长期无法建立。

修复要求：区分连接故障与单资产缺失；对缺失资产隔离、退避或独立重新订阅，保留健康资产完整状态。单资产仍应 miss 并保持原 HTTP。验证 1 个失效 token 加 15 个健康 token 的持续运行。

### A4 — P2：模块发布的是可变内部对象，消费者能污染后续簿

位置：`realtime/orderBook/bookReducer.ts:3–7`、`directBookFeed.ts:90`。

外层是 `ReadonlyMap`，但 `LocalOrderBook` 字段本身可赋值，且发布对象与内部状态是同一引用。复现无需绕过 TypeScript：消费者执行 `book.asks = new Map([["0.5", "999999"]])`；随后另一价位的正常增量继续基于这份内部对象合并，虚构的 999999 数量留在后续发布中。

当前动态旁路没有发现这样的写入，因此不能把它报告成已发生的交易污染。但作为用户要求的独立可复用行情模块，这是上线前必须修复的接口缺陷。只写 `ReadonlyMap` 或只冻结外层 Map 都不能提供运行时的深层保护。

修复要求：内部写状态与消费者读视图分离；类型和运行时都禁止反向写入，同时避免每次读取引入大规模复制。用两个消费者验证一个消费者的操作不会改变另一个消费者和后续增量的值。

### A5 — P2：重建期间的尝试被从时长样本中删除，统计分母不完整

位置：`wsBook/bookRuntime.ts:91–100`、`bookRuntime.ts:140–146`。

复现：已记录 `attempt_seen=1` 的真实执行角色 HTTP 尝试在等待期间发生断线；HTTP 成功返回后，因为 generation 改变，finish 直接返回，只增加 `attempt_discarded_epoch_or_route`。最终 `httpMarketMs.count=0` 且样本数组为空，尝试 ID、HTTP 耗时和结果均丢失。

影响：失败、恢复期或慢请求更可能跨代次，延迟分位数只描述留下来的样本，不能用来评价全部动态尝试或真实收益。报告虽有丢弃数量，仍无法按尝试关联补回时长；`httpMs` 的取值点还在同步比较之后，混入了部分比较成本。

修复要求：只丢弃失效簿证据，保留每个合格尝试的身份、HTTP 完成时刻、耗时、结果及未对齐原因；把 HTTP 等待、取证、比较和调度成本分列。缺少身份的样本保持未关联，不按 token/时间推测。

## 3. 经典 FOK 和生产打包的补充核验

- 经典 `runPmBuyPreflight` 的 HTTP、guard、clock、signer 并发路径未被替换；冷 signer 自动准备仍有行为测试覆盖。
- optimized 观察槽不被 legacy 或 GTC 分支调用；已捕获模式不随用户后续切换改变。
- core 不调用公共 `fo`/tick 写入口，HTTP 对照使用独立公开 GET，不调用自动线路降级或提交接口。
- `pm-ws-shadow-increments.json` 只登记三个接入文件的精确差异；旧 FOK/VPS 基线没有重录。保护检查验证原模块保留，但不意味着新增实现没有 bug。
- **纠正“经典模式不加载新核心”的表述**：源码 worker 采用动态 import，但 `vite.config.ts:133` 将 PM 模块归入同一 `venue-polymarket` chunk。实测生产产物 `venue-polymarket-DxMzXhQQ.js` 同时含 reducer、feed 和 runtime 的代码。经典 gate 能阻止实例化和新增网络/计时器，不能保证完全不下载/解析这部分代码。未做与旧包的体积差分，不推断具体启动延迟增量。

## 5. 修复后的放行次序

1. 优先处理 A1 的算法开销和线程隔离，修复 A2/A3 生命周期与故障影响范围；A4/A5 同批完成，保留默认 off。
2. 把本次复现转换为“期望正确行为”的正式回归，保持原基线不变；重跑经典 signer 冷启动/撤销/切换、FOK 行为、VPS、类型及构建检查。
3. 在真实浏览器只开 shadow：16 资产、长时运行、行情高峰、断线、线路切换、后台标签页、注销和账号变化；测资源、完整样本覆盖率和旁路对原 HTTP/双腿流程的额外延迟。
4. 以上通过后才讨论受控生产 shadow 灰度。真实 fast path 还需同簿执行算法等价验证及另行授权的实盘实验，不能通过改一个开关直接上线。

因此，本轮回答不是“已经无影响、可以生产”，而是：**经典交易语义有回归证据，独立模块和消费者方向成立；旁路实现仍有明确缺陷，生产启用结论为不通过。**
