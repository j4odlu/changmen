## 隔离条件及执行顺序

1. 另行明确获准后，在专用本机 PostgreSQL 实例管理连接上审查执行 `create-test-db.sql`。用 `psql -X -v ON_ERROR_STOP=1`，不连接生产 RDS。脚本固定创建 `changmen_orders_phase2_test_v1` 库和非特权角色 `changmen_orders_phase2_test`；存在即失败，不能复用已有库、自动删除或终止其他会话。角色登录密码由操作者单独设置，不保存到仓库。它是一次性测试库，每次完整重跑需新建干净的同名库，旧库处置须另行审查。
2. 设置仅用于本次测试的 `PM_GTC_TEST_DATABASE_URL`，地址限 `127.0.0.1`、`localhost` 或 `::1`；必须固定库名/角色，禁止 URL query 参数覆盖连接设置。入口不读取 backend `.env`，不使用任何 `DATABASE_URL*` 或 PG 凭证作为回退。
3. 默认命令 `node scripts/migrations/pm-gtc-orders/integration/run.mjs --plan` 只输出计划。本轮已获用户授权执行专用入口 `node scripts/migrations/pm-gtc-orders/integration/run.mjs --execute-isolated`，仅在全新专用本机库执行 DDL/DML；未来重跑仍须满足同样的隔离条件。
4. 执行入口只启动专用串行 Vitest 配置，传入内部执行令牌，剔除应用/其他数据库测试凭证。默认 Vitest 不发现 `postgres.integration.mjs`，已有环境变量不会自动触发执行。实际服务端还需确认本机地址、库名、非特权角色、数据库注释标记及 PostgreSQL >=14，然后才允许创建最小测试基表和执行原 `phase2-schema.sql`。
5. 原 DDL、运行时 helper、writer、GTC 契约和财务资格代码直接复用。唯一替换是 `common.js` 连接池入口；pg 查询及服务端事务不是 mock。测试不启动 backend、collector、浏览器或场馆 HTTP，不发送通知；hook 只注册本地观察函数。
6. 并发测试使用独立连接及 `pg_blocking_pids` 证实阻塞，不凭固定 sleep 判断成功。语句/锁/连接及用例均有超时；失败清理释放等待门、取消本测试连接语句、回滚并回收连接。测试夹具重置仅在严格校验专用库之后 TRUNCATE 三个夹具表，无 CASCADE，不作为业务删除工具。

最小 profiles 仅提供订单 FK；orders 的列类型、identity、默认值及唯一键对齐 `001_baseline.sql` + `009_orders_changmen_bet.sql`。它不等于完整生产数据库快照，不替代使用真实脱敏结构的后续演练。测试库重置使用 TRUNCATE 是隔离夹具清理；生产删除保护验收通过原 DELETE 路径执行。
